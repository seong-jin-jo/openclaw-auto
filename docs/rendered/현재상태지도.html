학습 정보 구조 제안

2026-08-19 · 세션 안이다. 넷 다 정했고 근거를 뒀다. 이 구조가 틀렸다면 어디서 터지는지도 아래에 적었다

내가 정한 넷

정한 것 왜
1 하네스는 두 벌. 공유는 브랜드 사실과 절대 금지선 둘뿐 studio는 어느 계정에 언제 올리는지 몰라도 되고, openclaw는 어떤 훅이 먹히는지 몰라도 된다
2 공유 헌법은 openclaw가 저장하고 요청에 실어 보낸다 studio가 계정별 창고를 가지면 개발자용으로 못 판다. 그리고 새벽 크론이 studio를 안 부른다
3 저장은 항목 단위 항목마다 승인받고 근거를 달고 충돌을 검사하기로 이미 정했다. 문서 한 덩어리로는 한 줄만 빼거나 승인할 수 없다
4 금지선은 절대. 조립에서 빼고 출력에서 다시 검사 지시문 우선순위만으로는 안 지켜진다는 실측 연구가 있다

이 구조면 실제로 이렇게 돈다

하나. 온보딩에서 공유 헌법이 생긴다

사용자가 노션 링크를 넣거나 몇 가지를 고른다. openclaw가 읽어서 항목을 뽑고 사용자가 승인한다.

브랜드 사실 · 승인됨 · 근거: 노션 회사소개 2026-08-19 읽음
  "1인 개발자가 만든 도구다. 대상은 예비 창업자다."

금지선 · 승인됨 · 근거: 사용자가 직접 씀
  "매출 수치를 노출하지 않는다."
  "경쟁사 실명을 쓰지 않는다."

이 셋이 공유 헌법이다. openclaw가 갖는다.

둘. 제작 요청이 studio로 간다

사용자가 제안 카드를 누르면 openclaw가 이렇게 보낸다.

요청: 짧은 영상 하나
이번 조건: 출력 언어 한국어
공유 헌법:
  브랜드 사실 2줄
  금지선 2줄
창작 하네스:
  워크스페이스 스타일 3줄
  창작 취향 4줄 (openclaw가 보관 중인 것)
소재: 없음

studio는 계정을 모른다. 받은 것으로만 만든다. 개발자 고객도 똑같이 보내면 된다.

셋. studio가 조립해서 모델에 보낸다

[브랜드] 1인 개발자가 만든 도구다. 대상은 예비 창업자다.
[금지선] 매출 수치를 노출하지 않는다. 경쟁사 실명을 쓰지 않는다.
[창작 규칙] 타인의 저작물을 그대로 쓰지 않는다.
[스타일] 담백한 1인칭. 짧은 문장.
[이번 조건] 출력 언어 한국어.
[취향] 첫 3초에 상황을 먼저 보여주는 시작을 고른다.

조립 전에 금지선과 부딪히는 취향 항목을 뺀다. 모델이 답하면 금지선 위반을 다시 검사한다. 조립한 지시문 전체를 저장한다.

넷. 사용자가 고르면 취향이 자란다

후보 B를 골랐다. openclaw가 그 사실을 studio에 신호로 보낸다. studio가 요약을 다시 만들어 돌려준다. openclaw가 보관한다.

창작 취향 · 승인 대기 · 근거: 8월 10일 후보 B, 8월 7일 후보 B · 표본 선택 4회
  "첫 3초에 상황을 먼저 보여주는 시작을 고른다."

사용자가 승인해야 다음 제작에 실린다.

다섯. 발행 준비는 다른 하네스를 쓴다

같은 작업물인데 조립되는 게 다르다.

[브랜드] 1인 개발자가 만든 도구다. 대상은 예비 창업자다.
[금지선] 매출 수치를 노출하지 않는다.
[운영 규칙] 광고 표기 의무를 지킨다.
[채널 규격] Threads 500자. 해시태그 5개 이하.
[운영 취향] 말투는 친절체.

studio를 안 부른다. 캡션과 해시태그는 openclaw 일이다.

여섯. 새벽 3시 크론

자동 댓글이 돈다. openclaw 하네스만 읽는다. studio가 멈춰 있어도 돈다. 이게 이 구조를 고른 가장 큰 이유다.

항목은 이렇게 생겼다

필드가 아니라 의미로 적는다. 스키마는 회장과 합의 전에 안 쓴다.

무엇 예
어느 하네스 공유 / 창작 / 운영
사람이 읽는 문장 "첫 3초에 상황을 먼저 보여주는 시작을 고른다"
어디서 나왔나 8월 10일 후보 B 선택, 8월 7일 후보 B 선택
언제 관찰했나 7월 28일부터 8월 10일
표본 선택 4회
한계 같은 주제 안에서만 관찰됨
승인 상태 승인됨 / 대기 / 거절됨
판 번호 7판
언어 한국어

이 구조가 틀렸다면 어디서 터지나

내가 먼저 공격해본다.

하나. 요청이 커진다. 매 요청에 헌법과 취향을 실어 보낸다. 취향이 스무 줄이 되면 요청마다 스무 줄이 간다. 지금은 괜찮지만 취향이 백 줄이 되면 문제다. 대응: 취향 요약에 상한을 두고 넘치면 사용자에게 뺄 것을 묻기로 이미 정했다. 다만 상한 수치는 실측 전이라 못 정한다.

둘. studio가 취향을 못 본 채로 요약을 만든다. studio는 상태가 없으니 과거 신호를 모른다. 요약을 만들려면 신호 이력이 필요한데 그것도 openclaw가 갖는다. 그러면 요약 요청 때 이력을 통째로 보내야 하고, 그게 클 수 있다. 대응 후보 둘. openclaw가 이력을 간추려 보내거나, studio가 신호 이력만은 갖는다. 후자면 상태 없음이 깨진다. 여기가 이 구조의 제일 약한 곳이다.

셋. 두 하네스가 어긋난다. 공유 헌법을 사용자가 고쳤는데 openclaw만 알고 진행 중인 studio 작업은 옛것으로 만들어진다. 대응: 요청에 헌법 판 번호를 같이 실어 보내고, 결과에도 남긴다. 어긋나면 화면에 표시한다.

넷. 개발자용 판매가 실제로 될지 모른다. studio를 상태 없이 만드는 이유가 그건데, 그 시장이 있는지 아직 안 봤다. 없다면 studio에 창고를 두는 게 더 단순했을 수 있다. 이건 대응이 없다. 가정이다.

아직 못 정한 것과 왜 못 정했나

무엇 왜 못 정했나
층별 분량 상한 수치 실제 요청을 돌려본 적이 없다. 취향이 몇 줄까지 붙는지 모른다
취향 요약을 다시 만드는 주기 신호가 얼마나 자주 들어오는지 모른다
조립 결과 보관 기간 저장 비용과 되짚기 필요를 아직 안 재봤다
관측 저장소를 누가 갖나 트렌드 수집은 openclaw인데 제안 카드는 생성에서 쓴다. 양쪽 다 근거가 있어 실제 흐름을 보고 정해야 한다

이 넷은 추측으로 메우면 나중에 전부 다시 뒤집힌다. 실측하거나 실제 화면을 보고 정하는 게 맞다.
