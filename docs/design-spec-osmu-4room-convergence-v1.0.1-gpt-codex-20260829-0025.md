# OSMU 네 방 디자인 수렴 명세 v1.0.1

## 0. 문서 지위

이 문서는 생성실, 편집실, 발행실, 성과실의 구현 정합을 한 번에 판정하기 위한 design stage 실행 명세다. 새 제품 결정을 만들지 않는다. 회장 확정 요구, 현행 디자인 시스템, 정본 프로토타입을 구현과 QA가 같은 방식으로 읽게 만드는 것이 목적이다.

- 라인: OSMU
- 단계: design
- 상태: 승인 후보
- 기준 시각물: `docs/prototype/openclaw-auto-4room-v64.html`
- 감사 기준선: `docs/prototype/openclaw-auto-4room-v63.html`
- 현행 디자인 시스템: `DESIGN.md` v33
- 상류 제품 입력: `docs/prd-openclaw-service-v8.2.1-gpt-codex.md`
- 요구 정본: `docs/requests/회장-확정-요구사항-대장.md` R01부터 R207
- 구현 대조일: 2026-08-29 KST

### 이 문서가 해결하는 결함

`docs/qa/osmu-v24-design-conformance-matrix-v1-gpt-codex.md`는 v24 보수 범위가 PASS여도 네 방 전체 v63 정합 12행은 NG라고 판정했다. 발견된 문제는 단순히 화면이 덜 예쁜 것이 아니다. 승인 핀, 최신 디자인, 구현, QA 증거가 서로 다른 판을 가리키고 있고, 그 사이를 연결할 화면별 design_spec이 0개였다. 이 상태에서는 개발자가 어떤 차이를 결함으로 고쳐야 하는지, 어떤 차이는 상류 결정을 기다려야 하는지 구분할 수 없다.

이 명세가 생기면 네 방의 화면 구조, 반응형 변형, 데이터 상태, 기능 계약을 같은 수락 기준으로 검증할 수 있다. 회장 관점에서는 디자인 NG가 무기한으로 남는 대신, 구현 수정과 재촬영으로 닫을 수 있는 유한한 목록이 된다.

## 1. 진실원 우선순위와 판 충돌 처리

### 1.1 우선순위

1. 회장 확정 요구 대장 R01부터 R207
2. `DESIGN.md` v33의 토큰, 셸, 반응형, 금지 패턴
3. v64 프로토타입의 네 방 화면과 상태
4. v63 프로토타입과 2026-08-28 QA의 감사 기준
5. 최신 구현 소스
6. PRD v8.2.1의 비충돌 범위

v64는 v63 전량을 계승하고 백엔드 실계약에 맞춰 첫 댓글 미지원, 중지 미지원, 성과 제안 근거와 표본 문턱을 보정한 최신 시각 정본이다. 따라서 새 기능 결정이 아니라 v63의 사실성 보정으로 취급한다.

PRD v8.2.1에 남은 미승인 결정 D-08, D-09, D-10과 PRD 자체의 `in-review` 표시는 이 명세로 확정하지 않는다. 해당 항목은 네 방 정합 판정에서 제외한다.

### 1.2 현재 판 충돌

| 층 | 파일이 가리키는 판 | 판정 |
|---|---|---|
| `pipeline-state.osmu.md` approved_artifacts | DESIGN v18, prototype v38 | 오래된 승인 핀 |
| 같은 파일의 후기 design 기록 | DESIGN v29, prototype v63 | 감사 기준은 있으나 승인 핀과 불일치 |
| 실제 `DESIGN.md` | v33 | 최신 디자인 시스템 |
| 실제 정본 프로토타입 | v64 | 최신 화면과 백엔드 사실성 |

발견: 단계 상태가 한 파일 안에서도 서로 다른 판을 가리킨다. 이 때문에 build가 승인된 옛 핀을 따르든 최신 디자인을 따르든 한쪽에서 불일치가 생긴다.

의미: 구현 수정 전에 controller가 approved_artifacts를 실제 승인된 최신 판으로 다시 고정해야 한다. 이 명세는 그 결정을 대신하지 않고, 핀 교정에 필요한 정합 근거를 제공한다.

가장 큰 원인은 C4와 design_spec 부재다. 여기에 `DESIGN.md` v33의 발행 이력 레일 규칙과, R183을 반영해 이력을 제거한 v64가 충돌한다. 요구 정본이 상위이므로 이 명세는 v64의 이력 제거를 따른다. v24 보수는 성과 중복, 본문 복원, OAuth 표면을 고쳤지만 전체 정합 기준을 실행 가능한 값으로 고정하지 못했다. 그 결과 후속 구현이 맞아져도 C3 때문에 NG가 남고, 다른 화면은 C1과 C2가 섞여 우선순위를 잃었다.

## 3. 공통 디자인 계약

### 3.1 브랜드와 토큰

- 브랜드 형용사: 절제된, 증거 중심, 사람다운
- 색상: `DESIGN.md` v33의 background, surface, text, muted, blue action, red exception, orange waiting, green confirmed 토큰만 사용한다.
- 글꼴: Pretendard. 크기 단계는 12, 13, 15, 17, 21px만 사용한다. 한 화면의 대표 숫자나 제목 32px은 한 번만 허용한다.
- 간격: 4, 8, 12, 16, 24, 32, 48px만 사용한다. 블록 간격 24px, 카드 안쪽 24px, 본문 바깥 32px을 기본값으로 한다.
- 모서리: chip 6px, control 8px, card 12px, pill 99px 토큰만 사용한다.
- 모션: fast 120ms, base 200ms, slow 320ms. `transition: all`은 금지하고 reduced motion을 존중한다.
- 최소 조작면: 핵심 터치 조작은 44x44 CSS px 이상이다. 최소 WCAG AA 기준 24x24를 넘기면서 모바일 오조작을 줄이는 제품 기준이다.

### 3.2 공통 셸

| 폭 | 주축과 순서 | 고정 값 | 스크롤 소유자 |
|---:|---|---|---|
| 1440 | shell column, body row, main row | 좌측 224px 또는 56px, 담당 304px, 바깥 본문 max 1280px | 본문 또는 명시된 내부 목록 |
| 1024 | shell column, body row, main row | 좌측 56px, 본문과 담당 70:30, 담당 최소 240px | 본문 또는 명시된 내부 목록 |
| 390 | shell column, main column | 상단 safe 24px, 담당 시트 peek 152px, half 58%, full `100% - 8px` | 기기 전체가 아니라 본문 내부 |

공통 순서는 헤더 1층, 헤더 2층 네 단계, 사이드바와 본문, 상시 담당이다. 네 방의 본문 머리는 같은 정렬선과 같은 높이를 쓴다. 단계 이름과 설명은 헤더가 소유하며 본문에서 큰 제목으로 반복하지 않는다.

390에서 담당은 접혀 사라지지 않는다. 살짝 상태에서도 마지막 말 한 줄, 입력칸, 보내기가 보여야 한다. 본문은 시트 peek만큼 아래 여백을 확보한다. `Escape`는 한 단계만 접는다.

### 3.3 공통 상태

모든 방은 다음 다섯 상태를 같은 위치에서 표현한다.

| 상태 | 화면 계약 |
|---|---|
| empty | 빈 숫자를 0으로 만들지 않는다. 첫 행동 하나와 담당의 질문을 둔다 |
| loading | 기존 골격을 유지하는 skeleton을 쓰며 셸과 단계 맥락을 지우지 않는다 |
| normal | 이 명세의 기본 장면 |
| error | 원본 보존 사실, 실패 지점, 한 번의 재시도를 오류가 난 자리에서 보여 준다 |
| overflow | 상위 3개와 전체 수를 먼저 보이고, 긴 글은 의미 단위 clamp 또는 다음 장면으로 넘긴다 |

### 3.4 금지 패턴

- 빈 대형 입력 폼으로 첫 화면을 시작하지 않는다.
- 디스플레이 안에 선택 버튼, 진행 멘트, 근거 장문을 중복하지 않는다.
- 카드 안의 카드와 설명용 회색 박스를 중첩하지 않는다.
- 내부 엔진명, route, code, 영어 상태명을 제품 문구로 노출하지 않는다.
- 값이 없는 성과를 0으로 쓰지 않는다.
- 플랫폼이 지원하지 않는 입력이나 행동을 비어 있는 활성 제어로 그리지 않는다.
- 표시 없는 가로 넘침, 기기 전체 가로 넘침, 12px 미만 글자를 허용하지 않는다.
- em dash와 en dash를 쓰지 않는다.

## 4. 화면별 정합 명세

### 4.1 생성실 `/studio?room=create`

#### 목적과 순서

사용자는 담당의 질문에 답하고, 디스플레이에서 결과를 확인한다. 선택은 대화창이 소유하고 디스플레이는 읽기 전용이다.

1. 헤더의 현재 만드는 갈래
2. 확인된 예시와 누적 정보
3. 후보 A, B, C의 실제 결과 미리보기
4. 선택한 한 편과 편집실 인계 상태
5. 상시 담당의 질문, 선택지, 직접 입력

#### 배치

- 1440: 디스플레이 3열 `repeat(3,minmax(0,1fr))`, 열 간격 24px, 오른쪽 담당 304px.
- 1024: 후보 격자는 3열, 담당은 전체 작업영역의 30% 이하이며 최소 240px.
- 390: `후보 A`, `후보 B`, `후보 C` 탭과 선택한 카드 한 장만 보여 준다. 선택 탭은 보기 전환이며 제품 선택 확정은 담당 대화에서 한다.
- 후보 카드는 실제 내용 장면, 제목, 형식, 예상 길이처럼 결과 판단에 필요한 값만 가진다. 설명용 빈 회색 사각형은 허용하지 않는다.

#### 구현 차이

| 관찰된 구현 또는 QA 장면 | 정본 | 수정 판정 |
|---|---|---|
| 큰 입력 폼과 내부 설정이 첫 화면을 차지 | 담당이 먼저 묻고 디스플레이는 결과를 보여 줌 | C1, C2 |
| 예시와 누적 정보가 큰 별도 패널로 반복 | 필요한 정보만 compact 장면으로 분리 | C2 |
| 후보가 텍스트 목록 또는 placeholder | 세 개의 실제 결과 미리보기 | C2 |
| 디스플레이에서 직접 선택 행동 | 선택은 담당 대화만 소유 | C1 |

#### 수락 기준

- CR-01: 첫 진입에서 빈 raw prompt 입력 폼이 본문의 주인공으로 보이지 않는다.
- CR-02: 후보 3개가 1440과 1024에서 3열, 390에서 한 장과 3개 보기 탭으로 렌더된다.
- CR-03: 후보 선택 확정 동작은 담당 대화 안에서만 가능하다. 디스플레이 카드는 읽기와 확대만 제공한다.
- CR-04: 담당 선택 뒤 같은 상태를 읽는 후보에 `선택됨` 텍스트와 테두리가 함께 반영된다.
- CR-05: 후보가 0개면 첫 갈래 질문, 1개에서 3개면 전부, 4개 이상이면 전체 수와 상위 3개를 보여 준다.
- CR-06: 80자 제목, 4줄 근거, 11개 후보에서도 셸 가로 넘침이 0이다.
- CR-07: loading과 error에서도 네 방 단계와 담당 입력이 사라지지 않는다.

### 4.2 편집실 `/studio?room=edit`

#### 목적과 순서

사용자는 결과물을 재생하면서 목차, 현재 장면, 자막, 속도, 첫 컷, 나레이션, 컷 순서를 고친다. 플랫폼별 제목, 캡션, 해시태그, 첫 댓글은 발행실이 소유한다.

1. 헤더의 현재 만드는 갈래
2. 왼쪽 목차와 장면 순서
3. 가운데 실제 재생기
4. 재생기 아래 compact 아이콘 도구 줄
5. 고른 도구의 편집 칸
6. 전체 대본
7. 원본 내려받기와 발행실 인계
8. 상시 담당

#### 배치

- 1440: 목차 214px, 재생기 `minmax(0,1fr)`, 담당 304px. 전체 대본은 목차와 재생기 아래 본문 폭을 쓴다.
- 1024: 목차와 재생기를 같은 행에 유지하되 본문 최소폭 0을 강제한다. 담당은 최소 240px.
- 390: 목차를 먼저, 재생기, 도구, 고른 편집 칸, 대본 순서로 한 열에 둔다. 담당 시트가 마지막 조작을 덮지 않는다.
- compact 도구는 한 번에 하나만 열린다. 아이콘에는 보이는 이름이나 접근 가능한 이름이 있다.

#### 구현 차이

| 관찰된 구현 또는 QA 장면 | 정본 | 수정 판정 |
|---|---|---|
| `구조 초안` placeholder가 결과물 자리를 차지 | 실제 재생기와 현재 장면 | C2 |
| 같은 설정을 큰 문장형 버튼으로 반복 | 한 줄 compact 아이콘 도구 | C2 |
| 장면 순서를 보여 주지만 사람이 재정렬할 수 없음 | 명시적 위, 아래 이동과 키보드 대안 | C1 |
| 저장한 본문은 복원되지만 장면별 변경의 영속 계약이 불명확 | 저장 뒤 재진입해 같은 장면, 대본, 순서 복원 | C1 |

#### 수락 기준

- ED-01: 1440과 1024에서 목차가 재생기 왼쪽, 담당이 오른쪽에 있으며 열 순서가 뒤집히지 않는다.
- ED-02: 실제 재생 영역은 16:9 또는 현재 콘텐츠의 확정 비율을 유지하고 placeholder 문구만 표시하지 않는다.
- ED-03: 도구는 자막, 속도, 첫 컷, 나레이션, 컷 순서, 원본만 포함한다. 플랫폼 캡션, 해시태그, 첫 댓글 입력은 0개다.
- ED-04: 도구를 누르면 고른 도구 한 칸만 열리고, 다른 도구를 누르면 이전 칸은 닫힌다.
- ED-05: 장면 재정렬은 pointer와 keyboard로 가능하고 결과 순서가 즉시 목차, 재생기, 대본에 반영된다.
- ED-06: 저장 후 방 이동, 재진입, 새로고침 세 경로에서 본문, 현재 장면, 장면 순서가 복원된다.
- ED-07: 긴 대본 30장면에서 전체 페이지 가로 넘침 0, 목차와 대본의 자체 세로 스크롤은 명시된 영역만 소유한다.
- ED-08: 원본 내려받기와 발행실로 보내기는 전체 편집 항목 아래 같은 출구 줄에 있다.

### 4.3 발행실 `/studio?room=publish`

#### 목적과 순서

사용자는 갈래별 실제 플랫폼 모습을 한 화면에서 대조하고, 각 플랫폼의 값만 독립적으로 고친 뒤 저장, 검토 요청, 지금 발행, 예약 중 하나를 실행한다.

1. 갈래 묶음: 텍스트, 영상 9:16, 카드뉴스
2. 묶음 안 플랫폼 미리보기 벽
3. 플랫폼별 제목, 표시 이름, 캡션, 해시태그, 첫 댓글
4. 저장, 검토 요청, 지금 발행, 예약 띠
5. 상시 담당

#### 배치

- 각 플랫폼 칸은 320px 고정이며 주축은 row, `flex-wrap: nowrap`, `align-items: flex-start`, `overflow-x: auto`다.
- 640px 미만에서는 한 칸이 본문 폭을 쓰고 scroll snap을 적용한다. 제목 줄에 `옆으로 밀어 더 보기`를 표시한다.
- 플랫폼을 하나만 남기는 탭 방식으로 바꾸지 않는다. 같은 묶음의 플랫폼이 동시에 존재해야 비교할 수 있다.
- 올린 기록은 발행실 본문에 두지 않는다. R183과 v64가 제거를 확정했고, 현재 `DESIGN.md` v33의 232px 이력 레일 규칙은 후속 문서 보정 대상이다.

#### 구현 차이

| 관찰된 구현 또는 QA 장면 | 정본 | 수정 판정 |
|---|---|---|
| 긴 세로 카드가 계속 쌓여 1440 캡처가 3000px 이상 | 갈래별 320px 가로 미리보기 벽과 이력 레일 | C2 |
| 회색 placeholder가 실제 플랫폼 외형을 대신 | Threads, Instagram, Shorts, Reels, TikTok, X, Facebook의 실제 순서와 구성 | C2 |
| 영상 채널 캡션이 같은 상태를 공유 | 플랫폼별 독립 draft | C1 |
| 지원하지 않는 채널도 첫 댓글 입력을 표시 | 사유를 적은 미지원 chip, 활성 입력 0 | C1 |
| 백엔드가 중지할 수 없는 상태에 중지 버튼 표시 | 현재 가능한 행동만 노출 | C1 |

#### 수락 기준

- PB-01: 텍스트, 영상 9:16, 카드뉴스 세 묶음이 보이고 각 묶음의 플랫폼이 320px 미리보기 벽 안에 함께 존재한다.
- PB-02: 390, 1024, 1440에서 기기 전체 가로 넘침은 0이고, 넘침은 `.pv-wall` 내부만 소유한다.
- PB-03: 미리보기는 실제 플랫폼의 정보 순서와 비율을 재현하되 상표 자산을 복제하지 않는다.
- PB-04: 플랫폼 A의 캡션을 바꿔도 플랫폼 B부터 G의 캡션 값은 변하지 않는다. 제목, 표시 이름, 해시태그, 첫 댓글도 같은 독립 계약을 따른다.
- PB-05: 첫 댓글 미지원 플랫폼은 활성 textarea가 0개이며 `이 채널은 첫 댓글 자동 게시를 지원하지 않습니다`와 같은 사실 설명을 표시한다.
- PB-06: 연결, 발행, 중지 능력은 실제 backend capability와 일치한다. 불가능한 행동은 disabled button으로 약속하지 않고 사유를 표시한다.
- PB-07: 글자 수 초과는 해당 플랫폼 칸 머리와 필드에서 함께 보이고 다른 플랫폼을 막지 않는다.
- PB-08: 발행실 본문에 `올린 기록`, `불러오기`, 232px history rail이 0개다.
- PB-09: 저장, 검토 요청, 지금 발행, 예약은 한 행동 띠에 있고 승인 인박스와 발행 캘린더를 본문 탭으로 반복하지 않는다.
- PB-10: Instagram 5장 캐러셀, 세로 영상, 500자 캡션, 24개 해시태그를 넣어도 카드 조작과 담당 시트가 겹치지 않는다.

### 4.4 성과실 `/studio?room=performance`

#### 목적과 순서

사용자는 최근 30일의 판정 한 문장을 먼저 읽고, 그 근거와 다음 행동을 확인한다. 수집되지 않은 값은 0이 아니라 미수집이며, 제안은 근거 종류와 표본 문턱을 밝힌다.

1. 기간과 플랫폼 필터
2. 판정 한 문장
3. 핵심 지표 4개
4. 보조 지표 6개 한 줄
5. 무엇이 통했나와 계보
6. 다음 행동 제안 3개
7. 댓글과 반응
8. raw detail 접힘
9. 상시 담당

#### 배치

- 1440과 1024: 핵심 지표 4열, 제안 3열.
- 390: 핵심 지표 2열, 제안 1열. 보조 지표는 이름과 값을 함께 보존한다.
- 첫 사용자 온보딩은 비어 있을 때 다음 행동을 설명하는 얇은 문맥이다. 판정과 같은 크기의 두 번째 주인공이 되지 않는다.

#### 구현 차이

| 관찰된 구현 또는 QA 장면 | 정본 | 수정 판정 |
|---|---|---|
| 온보딩, 파이프라인, 최근 활동, 채널 상태가 성과 본문에 중복 | 판정, 근거, 제안, 반응을 중심으로 한 단일 성과실 | C2, v24 보수 뒤 재검증 |
| 큰 지표와 패널이 반복돼 3000px 이상 | 핵심 4개, 보조 6개, 나머지 접힘 | C2 |
| 값이 없는 칸을 0으로 표시 | 미수집 | C1 |
| 제안 근거가 불명확하거나 내부 enum 노출 | 우리 검증 기록, 트렌드 신호, 가설 세 문구 | C1, C2 |

#### 수락 기준

- PF-01: 정상 상태 첫 viewport에서 판정 문장, 핵심 지표 4개, 제안 첫 줄이 보인다.
- PF-02: 게시 0건 상태의 모든 성과 값은 `미수집`이며 0으로 보이는 성과 값이 없다.
- PF-03: 핵심 지표는 1440과 1024에서 4열, 390에서 2열이다.
- PF-04: 보조 지표 6개는 이름과 값이 한 쌍으로 보이고 동일 정보를 큰 카드로 다시 반복하지 않는다.
- PF-05: performance 근거는 `우리 검증 기록`, trend는 `트렌드 신호`, hypothesis는 `가설, 우리 검증 기록 아님`으로 표시한다.
- PF-06: 우리 검증 기록은 표본 문턱 5건을 노출하고 미달이면 `표본 부족, n/5`로 표시한다.
- PF-07: loading은 판정과 지표 골격을 유지하고, error는 원본 보존과 재시도를 오류 위치에 표시한다.
- PF-08: raw 응답, 에이전트 로그, 채널 상태 전체표는 기본 접힘이며 판정과 제안을 밀어내지 않는다.
- PF-09: 댓글 100건에서도 처음 3건과 전체 수가 먼저 보이고 나머지는 점진 공개된다.

## 5. 네 방 연결 계약

| 출발 | 전달물 | 도착 | 보존 조건 |
|---|---|---|---|
| 생성실 | 선택된 후보와 선택 기록 | 편집실 | 원본 후보를 덮어쓰지 않음 |
| 편집실 | 편집 결과, 대본, 장면 순서 | 발행실 | 플랫폼별 문구를 섞지 않음 |
| 발행실 | 플랫폼별 payload와 발행 결과 | 성과실 | 부분 성공과 실패를 플랫폼별 보존 |
| 성과실 | 근거가 붙은 다음 제안 | 생성실 | 사람 승인 전 취향 규칙으로 확정하지 않음 |

dead-end 0 기준은 각 방의 정상, empty, error에서 다음 행동 또는 이전 방 복귀가 하나 이상 보이는 것이다. 오류가 나도 원본과 현재 방 맥락을 잃지 않는다.

## 6. 구현과 QA 인계 기준

### 6.1 수정 우선순위

1. C1 기능 계약: 선택 소유권, 편집 영속성, 장면 재정렬, 플랫폼 값 독립, 미지원 capability, 성과 미수집과 근거 라벨
2. C2 구조: 생성 실제 미리보기, 편집 재생기와 compact 도구, 발행 320px 벽과 이력, 성과 단일 위계
3. 공통 셸과 390 상시 담당 시트
4. 시각 마감: 8pt 간격, 타이포 단계, 텍스트 clamp, 실제 플랫폼 외형

기능 계약을 먼저 고쳐야 같은 장면을 캡처할 수 있다. 시각 차이를 먼저 닫아도 상태가 공유되거나 저장이 안 되면 사용자의 실제 여정은 계속 실패한다.

### 6.2 고정 캡처 행렬

| 방 | 390 | 1024 | 1440 | 데이터 상태 |
|---|---|---|---|---|
| 생성실 | 필수 | 필수 | 필수 | 후보 3개 normal |
| 편집실 | 필수 | 필수 | 필수 | 6장면, 저장 본문 복원 |
| 발행실 | 필수 | 필수 | 필수 | 7플랫폼, 플랫폼별 값 다름 |
| 성과실 | 필수 | 필수 | 필수 | 최근 30일 normal |

추가 상태 캡처는 생성 loading과 error, 편집 overflow, 발행 글자 수 초과와 미지원 capability, 성과 게시 0건을 남긴다. 모든 캡처는 같은 commit, 같은 seed, 같은 브라우저 배율에서 prototype과 actual을 짝으로 둔다.

### 6.3 자동 측정

- 390, 1024, 1440의 `documentElement.scrollWidth === clientWidth`
- 모든 핵심 조작의 bounding box가 44x44 CSS px 이상
- 방별 공통 상단의 x, y, height가 같은 폭에서 동일
- 12개 기본 캡처에 console error 0
- 색상, spacing, radius 리터럴은 design lint 0
- 제품 UI에서 `지금 여기`, `다음`, 내부 engine명, em dash, en dash 0
- 발행실 플랫폼 필드 독립 상태 테스트 PASS
- 저장 후 재진입과 새로고침 복원 테스트 PASS

## 7. 벤치마크 반영

Buffer 공식 도움말은 여러 채널을 한 composer에서 만들되 `Customize for each network` 이후 각 네트워크 값을 별도로 수정하고, 채널별 실제 게시 모습을 preview로 보여 준다. 이 원리를 발행실의 공통 원본과 플랫폼별 독립 draft, 실제 미리보기에 차용했다. Buffer의 composer 화면 자체는 우리 네 방 셸과 담당 대화 계약이 달라 복제하지 않았다.

W3C WCAG 2.2는 pointer target 최소 24x24 CSS px 또는 충분한 간격을 요구한다. 우리 제품은 모바일 담당 시트와 compact 도구에서 오조작 위험이 커서 44x44를 제품 기준으로 올렸다. inline text link 같은 표준 예외는 유지한다.

- Buffer Scheduling Posts: <https://support.buffer.com/article/642-scheduling-posts>
- W3C WCAG 2.2 Target Size Minimum: <https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html>
- W3C WCAG 2.1 Target Size Enhanced: <https://www.w3.org/WAI/WCAG21/Understanding/target-size>
