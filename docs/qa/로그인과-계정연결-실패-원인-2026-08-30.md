# 로그인과 계정 연결 실패 원인 조사

## 한 줄 결론

**로그인은 깨져 있지 않다. 깨져 있는 것은 채널 계정 연결이다.**
운영 DB에는 회장 workspace(`badd844f-...`)와 그 아래 Threads·Instagram 계정 레코드가 실제로 존재한다.
그것은 과거에 로그인이 성공했고 계정도 한 번 연결된 적이 있다는 뜻이다.
지금 두 계정은 `connectionStatus: invalid` / `connectionError: oauth_token_invalid` 상태이고,
재연결을 시도하면 **Threads long-lived token 교환 단계에서 실패**한다.
그 실패 사유는 **우리 코드가 provider 응답을 통째로 버려서 지금까지 아무도 알 수 없었다.** 그것을 이번에 고쳤다.

증거 등급 표기 규칙: 아래 모든 항목에 `[관찰]`(내가 직접 실행해 응답을 본 것) 또는 `[추론]`(코드만 읽고 판단한 것)을 붙였다.

### 로그인 관련 코드 결함 1건 (고쳤음)

`dashboard/src/app/login/page.tsx:43-51` (수정 전)
OAuth 콜백이 `?error=` / `#error=`를 달고 돌아오면, 코드는 sessionStorage 마커만 지우고
**화면에 아무 말도 하지 않았다.** 사용자에게는 "버튼을 눌렀는데 로그인 화면으로 되돌아왔고
아무 설명이 없다"로만 보인다. 회장이 말한 "로그인은 여전히 안되잖아"의 가장 유력한 후보다. [추론]

수정: 콜백 error 사유를 화면에 띄우고, 읽은 뒤 URL에서 제거하되 `returnTo`는 보존한다.

### 회장이 직접 확인해야 하는 외부 설정 1건

`redirect_to` 허용 여부는 서버에서 확인할 수 없다. 실측으로 확인했다:
Supabase `/auth/v1/authorize`는 허용목록에 없는 `redirect_to`(예: `https://evil.example.com/login`)를 줘도
**차단 없이 그대로 302를 내준다.** 검증은 그 뒤 `/auth/v1/callback` 단계에서 일어난다. [관찰]
따라서 코드나 서버 응답만으로는 허용목록 상태를 알 수 없고, 콘솔에서 눈으로 봐야 한다.

확인 경로:
1. https://supabase.com/dashboard 접속
2. 프로젝트 `gvtsyyltgwqplrqegrxo` 선택
3. 왼쪽 메뉴 **Authentication** → **URL Configuration**
4. **Site URL** 이 운영 주소(`https://<운영도메인>`)인지 확인
5. **Redirect URLs** 목록에 아래 두 줄이 있는지 확인. 없으면 추가:
   - `https://<운영도메인>/login`
   - `https://<운영도메인>/login?**` (returnTo 쿼리가 붙어 돌아오므로 와일드카드가 필요하다)
6. 같은 메뉴의 **Sign In / Providers → Google** 이 Enabled 인지 확인

5번의 와일드카드가 빠져 있으면, 로그인 코드가 붙이는 `?returnTo=...` 때문에 정확일치에 실패해
Supabase가 Site URL로 되돌려 보낸다. 그러면 위 결함 1과 겹쳐서 **아무 메시지 없는 로그인 실패**가 된다. [추론]

## 2. 채널 계정 연결 실패

### 관찰된 실패 지점

운영 로그 (최근 24시간, `connect` 관련 전체):

```
[connect-callback][exchange-fail] threads threads 장기 토큰 교환 실패
```

이 한 줄이 전부다. 24시간 안에 연결 시도는 Threads 1회뿐이었다. [관찰]

이 문자열의 출처:
- 로그 지점: `dashboard/src/app/api/connect/[provider]/callback/route.ts:139`
- 사유 생성 지점: `dashboard/src/lib/social-connect.ts:516` (수정 전)

즉 **short-lived token 교환은 성공했고, long-lived token 교환에서 실패했다.** [관찰 + 코드 근거]
(short 단계에서 실패했다면 사유 문자열이 "단기 토큰 교환 실패"였을 것이다.)

### 앱 자격증명은 문제가 아니다

운영 컨테이너의 `THREADS_APP_ID`/`THREADS_APP_SECRET`으로 Meta 엔드포인트를 직접 두드려 봤다. [관찰]

| 요청 | 응답 |
|------|------|
| `GET graph.threads.net/access_token?grant_type=th_exchange_token&client_secret=<운영값>&access_token=BOGUS` | `400 {"error":{"message":"Invalid OAuth access token - Cannot parse access token","code":190}}` |
| `POST graph.threads.net/oauth/access_token` (운영 client_id/secret, code=BOGUSCODE) | `400 {"error":{"message":"Invalid verification code","code":1,"error_subcode":36006}}` |

두 응답 모두 **토큰/코드가 잘못됐다**고 말하지, 앱이 잘못됐다고 말하지 않는다.
Meta는 app id/secret이 틀리면 그 사실을 먼저 말한다. 따라서 자격증명 자체는 유효하다. [관찰]

또한 우리 요청 형식이 현행 규격과 일치함을 공식 문서로 확인했다:
엔드포인트 `GET /access_token`, 파라미터 `grant_type=th_exchange_token` + `client_secret` + `access_token`,
전제조건은 "만료되지 않은 short-lived token" 과 `threads_basic` 권한.
우리 코드(`social-connect.ts` PROVIDERS.threads)는 이 셋을 모두 만족한다. [근거 확인]

### 그래서 왜 실패했나: 지금은 알 수 없다. 그것이 결함이다.

수정 전 `exchangeCode()`는 long-lived 응답의 **status code도 body도 버리고**
`` `${p.label} 장기 토큰 교환 실패` `` 라는 고정 문자열만 남겼다.
남은 가능성 3가지를 로그로 가릴 수가 없다:

1. Meta가 에러를 반환했다 (권한 미승인, short token 만료, 앱 모드 문제)
2. Meta가 `access_token`은 줬는데 `expires_in`을 안 줬다 → 우리 fail-closed 검사에 걸림
3. 응답이 JSON이 아니었다

**이것이 이번 판에서 고친 가장 중요한 결함이다.** 다음 시도부터는 사유가 로그에 남는다.

### 고친 코드

| 파일:줄 | 무엇을 고쳤나 |
|---------|---------------|
| `dashboard/src/lib/social-connect.ts` (`metaExchangeError` 신설) | 교환 실패 사유에 HTTP status + provider message를 싣는다. 우리 비밀값은 넣지 않는다 |
| `dashboard/src/lib/social-connect.ts` (short 단계) | Meta의 두 에러 형식 중 `{error:{message}}`를 못 읽던 것을 고쳤다. 기존엔 Graph 계열 에러가 전부 사유 없는 문자열로 뭉개졌다 |
| `dashboard/src/lib/social-connect.ts` (long 단계) | 위와 동일 + `expires_in` 누락으로 fail-closed된 경우를 별도 사유로 구분한다 |

### 실패한 연결이 계정 레코드를 남기는가: 아니다

코드를 끝까지 따라간 결과, `exchangeCode`가 실패하면 콜백은 `upsertChannelAccount`에 **도달하지 못하고**
바로 실패 화면을 반환한다(`callback/route.ts:136-142`). 즉 이번 교환 실패는 레코드를 만들지 않았다. [추론, 코드 경로 확인]

지금 남아 있는 Threads·Instagram 레코드는 **과거에 성공적으로 연결됐다가 토큰이 revoke된 것**이다.
운영 API 실측: [관찰]

```
threads   : connected=false, connectionStatus="invalid", connectionError="oauth_token_invalid", reconnectRequired=true
instagram : connected=false, connectionStatus="invalid", connectionError="oauth_token_invalid", reconnectRequired=true
```

즉 화면은 "연결됨"으로 거짓말하고 있지 않다. **"재연결 필요"로 정직하게 표시된다.**
코디네이터가 우려한 "연결된 것처럼 보이는데 쓰면 죽는 상태"는 아니다. 이 점은 정정한다.

### 로그가 수십 번 반복되는 이유

`token_expired` 알림은 `dashboard/src/app/api/channel-config/route.ts:225`에서 발생한다.
이 지점은 **읽기 엔드포인트(GET)** 안이다. 대시보드가 채널 설정을 폴링할 때마다
invalid 상태 계정 1건당 `severity: error` 알림이 1건씩 발생한다. [관찰 + 코드 근거]

이것은 장애 신호가 아니라 **알림 설계 결함**이다. 상태가 변하지 않았는데도 폴링 횟수만큼 error가 쌓여
진짜 장애를 로그에서 덮는다. 이번 판에서는 고치지 않았다(연결 복구가 우선이고, 알림 중복 억제는
`reportFailure` 계약 자체를 손대야 해서 범위가 다르다). 후속 과제로 올린다.

## 3. 발행 실패 사유가 `unknown`인 이유 (고쳤음)

`dashboard/src/lib/observability.ts` `classifyPublishFailure()`는
`(4xx)` 형태의 괄호 숫자, 네트워크 오류 문자열, `미지원` 세 가지만 분류하고 나머지를 전부 `unknown`으로 뭉갰다.
토큰이 무효라서 실패한 경우가 여기 걸린다. **실패의 가장 흔한 원인이 가장 정보 없는 라벨을 받고 있었다.** [관찰 + 코드 근거]

수정: `auth_invalid`(토큰/권한 문제)와 `decrypt_failed`(서버 키 문제)를 분류 대상에 추가했다.
이제 운영 로그만 보고 "재연결하면 되는 문제"인지 "서버 설정 문제"인지 구분된다.

## 4. 생성 경로가 실제 LLM을 부르는가: 부르지 않는다

**판정: 지금 배포된 A/B/C 후보 생성은 LLM을 한 번도 호출하지 않는다. 전부 문자열 템플릿이다.** [관찰, 코드 직독]

근거:

- `dashboard/src/lib/studio/generation/service.ts:225` `buildCandidates()`
  A/B/C 세 후보의 제목·근거·개요가 하드코딩 배열이다.
  제목은 `` `${topic}: 문제부터 여는 안` `` 처럼 주제 문자열만 끼워 넣는다.
  이 함수와 그 호출 경로(`runtime.ts` → `service.ts`) 전체에 Anthropic/LLM 호출이 **한 줄도 없다.**
  `grep -n "runClaudeCli|anthropic|claude|LLM"` 결과 0건이다. [관찰]

- `dashboard/src/lib/studio/generation/derivation.ts:172` `buildDerivationPayload()`
  글/카드뉴스/영상 파생도 전부 템플릿이다.
  - 글: 제목 + 근거 + 개요를 줄바꿈으로 이어붙임
  - 카드뉴스: 개요 항목을 슬라이드로 나열, `image_url`은 전부 `null`
  - 영상: `asset_url: "pending:render"` 고정. 실제 렌더 없음

- 화면 문구 `dashboard/src/components/studio/StudioRooms.tsx:325`
  "실제 미디어 생성은 준비 중입니다" 는 정확한 설명이다. 화면은 거짓말하고 있지 않다.

**단, 과금 설계는 짚어야 한다.** `derivation.ts`의 기본 단가는 카드뉴스 300, 영상 1200 (minor unit)이다.
바깥 API를 부르지 않는 템플릿 생성에 단가가 붙어 있다. 지금 운영에서 실제 청구가 일어나는지는
확인하지 않았다. **[미검증]** 회장 판단이 필요한 항목이다.

## 6. 회장이 지금 해야 할 것

1. **Supabase 콘솔 URL Configuration 확인** (1절의 6단계). 이것만 서버에서 확인이 불가능하다.
2. **이 변경을 배포한 뒤 Threads 재연결을 한 번 더 시도.** 그때 컨테이너 로그에
   `[connect-callback][exchange-fail] threads Threads 장기 토큰 교환 실패 (HTTP 400): <Meta가 준 진짜 사유>`
   가 남는다. 그 한 줄이 남는 순간 원인이 확정된다.
3. **판단 필요**: 템플릿 생성에 붙은 파생 단가(카드 300 / 영상 1200)를 실제 LLM 연동 전까지 0으로 둘 것인가.

## 7. 셀프심문

**질문: 회장이 지금 이 주소에 접속하면 로그인이 되는가. 나는 그것을 실제로 확인했는가,
아니면 코드를 보고 그럴 것이라고 믿는 것인가.**

자답: **끝까지 확인하지 못했다.** 나는 로그인 버튼을 실제로 눌러 Google 로그인 화면까지 도달하는 것을
브라우저로 밟아 확인했다(캡처 2장). 그러나 Google 계정 선택 이후 Supabase 콜백을 거쳐
`/api/me`가 200을 주고 대시보드로 진입하는 구간은 **회장 Google 계정 없이는 밟을 수 없어 밟지 않았다.**
따라서 "로그인 됩니다"라고 말하지 않는다.

내가 말할 수 있는 것은 이것뿐이다:
- 서버, DB, Supabase authorize, Google 도달까지는 [관찰]로 정상이다.
- 회장 workspace와 채널 계정이 DB에 실재하므로 이 경로는 **과거에 통과한 적이 있다** [관찰].
- 그 사이 구간이 지금 깨졌다면 가장 유력한 후보는 Supabase redirect URL 허용목록이고,
