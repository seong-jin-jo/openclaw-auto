# 제품 구조 결정서 (PRD 위임 입력용)

> 용도: `studio-service` PRD와 `openclaw-service` PRD를 쓰는 워커의 **기반 산출물**. 이 문서를 벗어난 임의 재해석 금지.

## 0.5 1차 목표 (회장 2026-08-15)

**openclaw-service를 완성하고, studio-service API를 구현해서, 해줘단타와 제로원 인사이트의 콘텐츠를 만들어 여러 채널에 발행한다.** 이것이 지금의 목표다. 이 목표에 기여하지 않는 작업은 후순위다.

우리 자신이 첫 사용자이고, 그렇게 만든 콘텐츠가 곧 제품의 증거물이 된다.

## 0. 30초 요약

제품은 서비스 2개다. `studio-service`는 화면 없는 제작 API(headless), `openclaw-service`(상품명 marketing agency 계열)는 화면과 인증·결제를 갖고 studio를 API로 사서 쓰는 소비자 제품이다. 엔진 코드는 둘 다 오픈소스로 공개한다. 데이터베이스는 서비스마다 하나씩 총 2개다.

## 2. 서비스 경계

기준은 **창작 결정이냐 채널 적응이냐**다.

| 작업 | studio-service | openclaw-service |
|---|---|---|
| 무엇을 말할까, 어떤 톤·화풍 | O | X |
| 컷 분해, 편집 지시서 작성 | O | X |
| 소재 생성(이미지·영상·음성) | O | X |
| 자막·용어칩·오버레이 합성 | O | X |
| 취향 학습과 제안 | O | X |
| 브랜드킷·금지선 보관 | O | X |
| 채널 비율 크롭, 캡션 길이 자르기, 해시태그 | X | O |
| 예약, 발행, 계정 관리 | X | O |
| 조회·저장·댓글 성과 수집 | X | O |
| 화면, 회원, 인증, 결제 | X | O |

**주의:** openclaw-service의 "다듬는다"는 채널 규격 적응이지 창작 편집이 아니다. 자막을 새로 얹거나 컷을 바꾸는 것은 studio 몫이다.

## 3. studio-service 외부 접점 5개

모든 학습 신호는 **입구 하나**로 받는다. 공통 봉투는 `{ tenant, source, kind, subject_ref, payload, observed_at }`.

| 접점 | 방향 | 설명 |
|---|---|---|
| 신호 넣기 | 들어옴 | 온보딩 브랜드킷, 발행 성과, 외부 트렌드, A/B/C 선택, 제안 채택을 모두 이 봉투로 받는다 |
| 제작 요청 | 들어옴 | 주제와 규격을 받아 A/B/C 변형을 만든다 |
| 선택 기록 | 들어옴 | 어느 변형을 골랐는지. 내부적으로는 신호의 특수형 |
| 취향 상태 조회 | 나감 | 현재 취향 프로파일. 이것을 호출하는 쪽이 화면에 그린다 |
| **소재 반입** | 들어옴 | 유저가 이미 가진 미디어(롱폼 원본, 기존 이미지·영상)를 재료로 등록한다. 2026-08-15 추가 |

### 소재와 학습신호는 다른 것이다 (혼동 주의)

| 구분 | 무엇 | 예 |
|---|---|---|
| 소재(asset) | 만들기의 **재료** | 롱폼 원본 영상, 기존 이미지, 승인된 목소리, Soul ID |
| 학습신호(signal) | 취향을 바꾸는 **사건** | "2번 후보를 골랐다", "이 게시물 저장률이 X였다" |

A/B/C에서 유저가 영상 세 개 중 하나를 고를 때 studio로 넘어가는 것은 **영상 파일이 아니라 선택한 변형의 식별자와 그 변형의 파라미터**다. 파일 자체는 신호가 아니다. 그래서 신호 봉투는 미디어가 늘어나도 그대로 유지된다.

**예외 하나:** 유저가 자기 기존 콘텐츠를 올리며 "이런 느낌으로 만들어 줘"라고 할 때. 이것은 신호처럼 보이지만 실제로는 참조 소재다. 프로파일에 반영하려면 **소재에서 축(색감, 속도, 톤, 컷 길이)을 뽑아 신호로 환원하는 변환 단계**가 필요하다. 이 변환기를 두면 애매함이 사라진다.

### 롱폼을 숏폼으로 쪼개기는 studio 몫이다

어느 구간을 자를지 고르는 것은 창작 판단이다. 자를 후보 구간 세 개를 내고 유저가 고르게 하면 A/B/C 루프와도 그대로 맞는다. 입력이 "주제"가 아니라 "기존 영상"일 뿐이므로 위 소재 반입 접점으로 받는다.

openclaw-service는 **이미 완성된 영상을 그대로 발행**하는 것까지만 한다. 쪼개기가 필요하면 studio를 호출한다.

**핵심 규칙: 생성 경로는 신호를 직접 읽지 않고 취향 프로파일만 읽는다.** 신호 종류가 늘어도 생성 코드는 그대로다.

**의존 방향: openclaw-service → studio-service 단방향.** studio는 openclaw를 호출하지 않는다. 성과도 openclaw가 밀어 넣는다.

## 3.5 제작 방식 선택 (회장 2026-08-15)

A/B/C 샷건과 **다른 축**이다. 샷건은 같은 방식 안에서 변형 세 개를 내는 것이고, 제작 방식 선택은 **축 자체를 고르는 것**이다.

| 방식 | 무엇 | 원가 성격 |
|---|---|---|
| 나레이션과 정지 이미지 | 음성에 이미지와 자막만 얹는다. 영상 생성 없음 | 최저. 이미지 4에서 6장과 음성 1분 |
| 혼합 | 핵심 컷만 영상화하고 나머지는 정지 | 편당 약 1,635원에서 1,823원 |
| 풀 영상 | 컷마다 영상 생성 | 컷당 8에서 12크레딧이라 가장 비싸다 |

**고객이 고른다.** 그리고 고르게 할 때 **비용, 소요 시간, 언제 좋고 언제 나쁜지, 실제 사례**를 함께 보여준다. 저비용 프리뷰로 볼지 완성본으로 볼지도 같은 방식으로 고객이 고른다.

**두 가지 제약을 반드시 지킨다.**
1. **기본값 하나를 추천으로 제시한다.** 첫 사용자에게 선택지를 세 개 이상 펼치면 백지공포 페르소나가 마비된다. 추천 하나를 먼저 보여주고 나머지는 "다르게 해보기"로 접어 둔다.
2. **사례 근거에 출처를 표시한다.** "잘나가는 채널은 이렇게 했다"를 근거 없이 쓰면 우리가 비판한 미검증 제안 엔진이 된다. 초기 근거는 우리 실험 로그(힉스필드 약 800크레딧)와 공개된 사례이며, 어느 쪽인지 화면에 표시한다.

## 3.6 미디어 경계 (회장 2026-08-15 질의, 기준 1회 개정)

**확정 기준: studio가 미디어 바이트를 다루는 유일한 곳이다.** openclaw는 완성 파일을 받아 채널에 올리고 메타데이터(캡션, 해시태그, 예약 시각, 계정)만 만든다. 비율 크롭조차 studio에 요청한다.

| 작업 | 소유 |
|---|---|
| 자르기, 크롭, 재인코딩, 자막 합성, 재렌더 | studio 전부 |
| 어디를 자를지 고르기(후크 구간 판별, 후보 3개 제시) | studio. 창작 판단 |
| 채널별 제목, 소개, 해시태그, 첫 댓글 등 **모든 창작 텍스트** | studio. 2026-08-15 정정 |
| 채널 규격 정보 제공(글자수 상한, 해시태그 개수, 지원 비율), 예약 시각, 어느 계정, 발행 실행 | openclaw |
| 유저가 올린 완성 영상을 손대지 않고 그대로 발행 | openclaw. 파일 첨부일 뿐이다 |
| 유저가 올린 영상을 쪼개거나 변환 | studio. 소재 반입 접점으로 받는다 |

**왜 기준을 바꿨나.** 처음에는 "픽셀을 다시 그리는가"로 잡았는데, 롱폼을 숏폼으로 쪼개는 경우가 애매했다. 원본이 변형되지 않고 길이만 잘리므로 어느 쪽으로도 읽혔다. 판단 기준이 애매하면 구현에서 매번 다시 다툰다. **편집 코드가 두 곳에 생기는 것이 최악**이므로, 미디어를 만지는 곳을 한 곳으로 못박는다.

**대가:** 단순 크롭에도 API 왕복이 한 번 생긴다. 파일은 저장소 주소로 주고받으므로 전송 비용은 없다. 대신 openclaw가 순수한 발행 엔진으로 남아 오픈소스로도, Ayrshare 같은 발행 API로도 성립한다.

## 3.7 입력 설계와 선택 피로 감소 (회장 2026-08-15, "이게 진짜 킥")

> 회장 원문: "선택 피로를 줄여준다는 게 진짜 핵심이 될 것 같다. 해줘단타 만들면서도 대본 어떻게 구성할지, 어떤 스타일로 할지, 구성 어떻게 할지 다 백지였다. 벤치마킹도 직접 해야 했다."

**설계 원칙: 유저에게 백지를 주지 않는다. 항상 고를 것을 준다.**

### 유저가 넣는 것 (입력 유형)

| 유형 | 예 | 어떻게 받나 |
|---|---|---|
| 선택 | 업계, 목적, 스타일, 제작 방식 | 화면에서 고른다. 백지 입력창이 아니다 |
| 참고 자료 | 자기 위키, 노션 정리, 메모장 글, 강의 자료, 자주 받는 질문 | 붙여넣기 또는 연결. 소재 반입 접점 |
| 소재 | 롱폼 원본, 사진, 로고, 목소리 샘플 | 파일 등록. 소재 반입 접점 |
| 평가 | A/B/C 중 선택, 제안 카드 채택 여부 | 클릭. 학습 신호가 된다 |

**참고 자료는 이 제품의 해자 후보다.** 시그마인은 홈페이지를 크롤링하지만 우리는 고객 내부 지식을 받는다. 자기 지식이 들어간 만큼 옮기기 어려워진다.

### 단계별 진행 (백지 제거의 구체적 방법)

```
1) 업계와 목적을 고른다
2) 그 업계에서 잘 되는 채널과 영상을 모아서 보여준다   ← 벤치마킹 노동을 제품이 대신함
3) "이런 스타일" 예시를 여러 개 제시한다
4) 각 예시에 예상 비용과 예상 소요 시간을 붙인다      ← 힉스필드에는 없는 것
5) 고르거나, 못 고르겠으면 추천을 받는다
6) 용감하게 하나 골라 만들어 본다
7) 성과와 트렌드를 보고 다음 추천이 바뀐다
8) 클릭과 답변만으로 계속 굴러간다
```

**핵심은 4번과 2번이다.** 힉스필드를 열면 무엇을 써야 할지도 얼마가 들지도 모른다. 우리는 **선택하기 전에 비용과 결과를 예상하게 해 준다.** 그리고 벤치마킹을 대신해 준다. 이 둘이 "직접 만들지 않아도 예상할 수 있게" 만드는 장치다.

### 노련한 마케터가 옆에 앉은 것처럼 (회장 2026-08-15, 질문 엔진의 화법 규약)

> 회장 원문: "마케팅 지식이 없는 사람한테도 그 결정에 필요한 질문들을 던지는 거야. 타깃이 이런 사람 맞냐, 이게 더 낫지 않냐, 선택 선택 답변, 반박도 하고. 노련한 마케터가 고객한테 선택만 요구하는 것."

**질문의 화법이 제품의 성패를 가른다.** 같은 것을 물어도 이렇게 다르다.

| 나쁜 질문 (백지를 던짐) | 좋은 질문 (선택을 요구함) |
|---|---|
| "생각하시는 브랜드 컨셉 있으세요?" | "선택하신 산업에서는 보통 이렇게 합니다. 우리 데이터로는 이걸 추천해요. 결정해 보세요. 다른 생각 있으면 적어 주세요" |
| "타깃이 누구세요?" | "이 업종은 보통 두 부류를 노립니다. 어느 쪽이 더 가깝나요?" |
| "톤앤매너를 알려 주세요" | "이 두 예시 중 어느 쪽이 마음에 드세요?" |

**규약 네 가지**

1. **먼저 답을 제시하고 고르게 한다.** 빈칸으로 묻지 않는다.
2. **왜 그렇게 추천하는지 근거를 붙인다.** "이 업종에서는 보통", "우리 데이터로는"까지 말한다.
3. **반박한다.** 유저 선택이 목적과 어긋나면 그대로 따르지 않고 다른 안을 제시한다. 노련한 마케터는 고개만 끄덕이지 않는다.
4. **자유 입력은 항상 열어 둔다.** 선택지에 없으면 적을 수 있어야 한다. 다만 그것이 기본 경로는 아니다.

**목표는 결정 피로와 백지공포를 동시에 없애는 것이다.** 백지공포는 선택지를 줘서, 결정 피로는 추천과 근거를 줘서 없앤다.

### 추천 기본값의 형태 (회장 정정 반영)

추천은 값 하나가 아니라 **예시 여러 개**다. "이런 스타일을 원하면 이 방식, 저런 스타일을 원하면 저 방식"으로 짝지어 보여준다. 그래야 고르는 능력만으로 결정할 수 있다.

### studio가 받을 수 있는 것을 넓게 연다 (회장 2026-08-15)

**모델은 마케터가 클라이언트에게 이것저것 물어보고 만드는 방식이다.** 마케터는 "브랜드 자료 주세요"라고만 하지 않는다. 참고할 만한 계정, 좋아하는 광고, 하지 말아야 할 것, 고객 후기까지 받는다. studio도 그래야 한다.

| 받을 것 | 예 |
|---|---|
| 참고 링크 | "이 계정처럼 만들어 줘"라며 붙이는 소셜 게시물 주소, 영상 주소 |
| 문서 | 노션, 위키, 메모장, 강의 자료, 자주 받는 질문 |
| 파일 | 롱폼 원본, 사진, 로고, 목소리 샘플 |
| 답변 | 업계, 목적, 톤, 금지선에 대한 선택과 서술 |

**참고 링크는 특별히 유용하다.** "이런 느낌"을 말로 설명하기는 어렵지만 링크 하나 붙이기는 쉽다. 고르는 능력만 요구하는 입력이라 우리 타깃과 정확히 맞는다.

**참고 링크 활용 범위 (회장 2026-08-15 판단)**: 참고해서 비슷하게 만드는 것을 막지 않는다. 무엇이 허용되는지는 **각 플랫폼 정책과 저작권법이 정하는 것**이지 우리가 대신 판정할 일이 아니다. 우리는 요구사항대로 만들어 준다.

**세션이 제안했던 최소선 두 가지도 회장 판단으로 철회한다**(2026-08-15). 재배포와 상표 복제 역시 플랫폼과 권리자가 판정할 일이지 우리가 대신 막을 이유가 없다. **판정자를 자처하지 않는다.**

**단 하나만 남긴다: 유료 출시 전에 법률 검토를 한 번 받는다.** 지금은 우리가 쓰는 단계라 노출이 없지만, 돈을 받고 남에게 제공하는 순간 책임 구조가 달라진다. 그때 실제로 위험한 것이 있는지 확인하고, 없으면 그대로 간다. 이건 기능 제한이 아니라 확인 일정이다.

### 우리 자신을 위한 피드백 루프 (회장 2026-08-15)

유저가 결과물을 보고 취향을 쌓듯이, **우리도 서비스 운영에서 배워야 한다.** 두 루프를 분리해 둔다.

| 루프 | 누구의 학습 | 무엇을 쌓나 |
|---|---|---|
| 테넌트 루프 | 유저 개인 취향 | 취향 프로파일. 그 유저에게만 적용 |
| **운영 루프** | 우리 제품 | 어떤 제작 방식이 어떤 상황에서 잘 됐나, 어떤 프롬프트가 실패했나, 재시도율은 얼마인가 |

**운영 루프가 제안 엔진의 근거가 된다.** "이 컷은 이렇게 하는 게 좋습니다"의 출처가 우리 실험 로그일 때만 경쟁사가 못 베낀다.

**따라서 1단계부터 로그를 남긴다.** 최소한 이 다섯 가지다. 요청 파라미터, 사용한 제작 방식, 크레딧 소모, 재시도 횟수와 사유, 유저 선택 결과. 나중에 붙이려면 과거 데이터가 없어 처음부터 다시 쌓아야 한다.

**개인정보 경계**: 운영 루프에는 테넌트를 식별할 수 있는 내용을 넣지 않는다. 집계와 패턴만 쌓는다.

### 노하우를 수치로 돌려주는 것이 진짜 사용 동기다 (회장 2026-08-15)

> 회장 원문: "유저가 우리한테 제공하는 게 단순히 금액이 아니라, 계속해서 마케팅적으로 통하는 콘텐츠를 만드는 데 도움이 되는 노하우를 제공해 주는 데에 의미가 있지 않을까. 이것도 증명이 되면 강력한 사용 동기일 것 같다."

**목표: "이렇게 하면 목적 달성에 좋더라"를 점수로 말할 수 있게 된다.**

| 단계 | 무엇 | 지금 가능한가 |
|---|---|---|
| 1 | 우리 실험 로그로 제작 방식별 결과를 비교 | 부분 가능. 힉스필드 실측이 있다 |
| 2 | 고객 산출물의 성과를 모아 방식별 점수화 | 고객이 생겨야 가능 |
| 3 | 외부 인기 콘텐츠와 대조해 상대 점수 제시 | 트렌드 수집과 연결 |

**이것이 유료를 유지하는 이유가 된다.** 크레딧만 파는 관계는 더 싼 곳이 나오면 끝난다. 노하우가 쌓여 돌아오는 관계는 옮기면 손해다.

**그래서 점수는 반드시 근거와 함께 보여준다.** "이 방식이 좋습니다"가 아니라 "같은 목적의 사례 N건에서 이 방식이 이런 결과였습니다"로 말한다. 표본이 적으면 적다고 표시한다. 근거 없는 점수는 시그마인의 "알아서 최적화"와 같아지고, 그 순간 우리 차별점이 사라진다.

### 반드시 지킬 것

- 사례와 추천 근거에 **출처를 표시한다.** 우리 실험 로그인지, 공개된 사례인지, 아직 가설인지. 근거 없는 제안은 시그마인의 "알아서 최적화"와 같아진다.
- 예상 비용은 **범위로** 보여준다. 재시도가 있으므로 단일 숫자는 거짓이 된다.

## 3.8 studio의 두 가지 동작 모드: 생성과 편집 (회장 2026-08-15 지적)

> 회장 지적: "롱폼 쪼개기는 성격이 좀 다르다. 이런 느낌으로 만들어 달라가 아니고 이것 자체를 쪼개서 만들어 달라, 일종의 편집이다. 그리고 산출물이 나왔는데 조금 더 손보고 싶을 때도 새로 만드는 게 아니라 원본을 가지고 조금씩 편집하는 것이다."

**지적이 맞다. studio는 한 가지 일만 하는 것이 아니다. 두 모드를 가진다.**

| 모드 | 입력 | 무엇을 하나 | 취향 루프 |
|---|---|---|---|
| 생성 | 주제와 취향 프로파일 | 무에서 만든다. A/B/C 후보를 낸다 | 강제 선택으로 학습 |
| 편집 | 이미 있는 결과물과 수정 지시 | 원본을 유지하고 지시만 반영한다 | 수정 지시 자체가 약한 신호 |

편집 모드에서 유저의 수정 지시("자막을 위로", "이 컷을 짧게", "이 문구를 바꿔")도 취향의 증거다. 다만 A/B/C 같은 강제 선택보다는 약한 신호로 다룬다.

### 편집 모드가 두 갈래로 갈린다 (원가가 완전히 다르다)

| 갈래 | 편집 지시서가 있나 | 비용 | 언제 |
|---|---|---|---|
| **우리가 만든 것 수정** | 있다. 우리가 썼으니까 | **지시서 한 줄 고치고 다시 렌더. 소재 재생성 0장** | 1단계 필수 |
| 외부에서 반입한 것 편집(롱폼 쪼개기 등) | 없다. 남이 만든 파일이다 | 영상을 분석해 지시서를 역으로 만들어야 한다 | 2단계 |

**이것이 우리만 가진 강점이다.** 2026-08-14 실측에서 확인됐다. 편집 지시서가 있으면 결과물을 고칠 때 **소재를 다시 생성하지 않는다.** 자막 위치, 컷 길이, 문구는 렌더만 다시 하면 되고 크레딧이 들지 않는다.

경쟁 도구는 완성된 영상 파일만 남기므로, 마음에 안 들면 처음부터 다시 생성해야 한다. 즉 **저쪽은 수정이 곧 재생성이고 우리는 수정이 재렌더다.** 원가 차이가 여기서 벌어진다.

### 편집 비용 실제 (회장 2026-08-15 질의, 정확히 구분)

**크레딧이 안 드는 것** (전부 로컬 ffmpeg와 PIL, 외부 모델 호출 없음)

- 자막 크기, 글꼴, 색, 위치 변경
- 자막 문구 수정 (나레이션 음성을 바꾸지 않는 경우)
- 전환, 페이드, 줌 같은 이펙트 추가
- 컷 순서 변경, 컷 길이 조정, 컷 삭제
- 용어칩, 오버레이, 말풍선 배치 변경
- 채널별 비율 변경과 크롭

**크레딧이 드는 것** (소재 내용 자체가 바뀌므로 재생성 필요)

- 나레이션 문구 수정 (해당 컷의 음성만 다시 생성)
- 이미지나 영상 소재를 다른 그림으로 교체 (해당 컷만)

**즉 캡컷이나 다빈치리졸브로 하던 작업 대부분이 크레딧 0이다.** 픽셀을 배치하고 타이밍을 맞추는 일은 우리 코드가 하기 때문이다. 소재의 내용이 바뀔 때만, 그것도 바뀌는 컷만 과금된다.

**정직하게 덧붙이면**, 크레딧이 0이지 비용이 0은 아니다. 렌더링에 서버 시간이 든다. 다만 외부 모델 호출비에 비하면 작다.

### 이것이 두 번째 백지공포 해소다 (회장 2026-08-15)

첫 번째 백지공포는 "무엇을 만들지 모르겠다"이고, 우리는 선택지와 예시로 푼다. **두 번째는 "영상 편집을 할 줄 모른다"이다.** 캡컷이나 다빈치리졸브를 열면 대부분 막힌다. 편집 모드는 그 사람이 **말로 고치게** 해 준다. "자막 좀 키워 줘", "이 컷 짧게" 같은 말이면 된다.

**따라서 편집 모드를 1단계에서 빼면 안 된다.** 빼면 유저가 "조금 아쉽다"고 할 때마다 A/B/C를 다시 돌려야 하고, 그 순간 편당 원가가 세 배가 된다. 우리 원가 우위가 사라진다.

### 롱폼 쪼개기는 2단계로 미룬다

시장이 이미 성숙했다. OpusClip은 롱폼에서 바이럴 구간을 자동으로 찾아 자막까지 얹고, Vizard는 더 싸게 더 많이 뽑는다. 우리가 지금 이걸 만들면 성숙한 제품과 정면으로 붙는다.

**다만 빈틈은 있다.** OpusClip은 화면이 영어 중심이고 한국어 자막 정확도가 떨어진다. 우리가 한국어 정확성과 용어 하이라이트로 들어갈 자리는 남는다. 지금은 아니다.

**1단계 대응:** 유저가 기존 도구로 쪼갠 결과물을 가져오면, 우리는 그것을 **우리 스타일로 다듬는 것**만 받는다. 소재 반입 접점으로 들어온다.

## 3.9 채널 지식은 openclaw가, 채널별 생성은 studio가 (회장 2026-08-15 질의)

**질문:** 채널별 창작 텍스트를 studio가 만들면 studio가 모든 플랫폼 규칙을 알아야 하지 않나.

**답: 지식은 데이터로 넘기고, 생성만 studio가 한다.**

openclaw는 **채널 규격 카탈로그**를 노출한다. 글자수 상한, 해시태그 개수 제한, 지원 비율, 길이 상한, 첫 댓글 지원 여부 같은 것들이다. studio는 그 카탈로그를 읽고 규격에 맞춰 만든다.

이렇게 하면 플랫폼이 규칙을 바꿔도 **openclaw만 고치면 된다.** studio 코드는 그대로다. 플랫폼 지식이 두 곳에 복제되지 않는다.

### 규격은 학습 신호가 아니다. 요청에 실려 오는 제약이다 (회장 2026-08-15 지적)

**정정한다.** 앞에서 "studio가 카탈로그를 읽는다"고 쓴 것은 부정확했다. 그러면 studio가 openclaw를 호출하게 되어 단방향 의존이 깨진다.

**정확한 구조: openclaw가 studio를 호출할 때 요청 본문에 제약을 실어 보낸다.**

```
openclaw → studio  제작 요청
{
  주제, 취향 프로파일 참조,
  targets: [
    { 비율: 9:16, 최대길이: 60초, 캡션상한: 2200자, 해시태그상한: 30개 },
    { 비율: 1:1,  최대길이: 30초, 캡션상한: 280자,  해시태그상한: 5개 }
  ]
}
```

**studio는 플랫폼 이름조차 몰라도 된다.** "인스타그램"을 아는 것이 아니라 "세로 9대16, 캡션 2200자"만 안다. 그래서 새 플랫폼이 생겨도 studio 코드는 그대로다. 외부 개발자가 studio를 직접 쓸 때도 자기 제약을 넣으면 된다.

### studio가 받는 것은 세 범주다 (혼동 금지)

| 범주 | 무엇 | 어디에 쌓이나 |
|---|---|---|
| **제약(constraint)** | 비율, 길이, 글자수 상한 같은 규격 | 아무 데도 안 쌓인다. 그 요청에만 쓰인다 |
| **소재(asset)** | 롱폼 원본, 이미지, 로고, 목소리 샘플 | 자산 저장소 |
| **학습 신호(signal)** | 어느 후보를 골랐나, 성과가 얼마였나 | 취향 프로파일 |

규격은 신호가 아니다. 취향을 바꾸지 않는다. 요청 파라미터일 뿐이다.

### 마스터 하나에 채널 파생 여럿 (OSMU의 정석)

제작 요청 때 발행 목적과 대상 채널을 받는다. 다만 **소재는 채널 중립인 마스터로 만들고, 채널별 산출은 파생물로 뽑는다.**

```
마스터 1개 (소재 + 편집 지시서)
   ├── 세로 60초 + 채널A용 캡션·해시태그
   ├── 세로 15초 + 채널B용 캡션
   └── 가로 60초 + 채널C용 제목·소개
```

**이 구조의 이점: 채널을 나중에 추가해도 손해가 없다.** 처음에 두 채널만 골랐다가 나중에 하나 더 붙여도 마스터가 있으니 파생만 더 뽑으면 된다. 초기 선택이 틀려도 비용이 안 든다.

### 채널을 여러 개 고르면 크레딧이 더 드나

**거의 안 든다.**

| 파생 종류 | 비용 |
|---|---|
| 채널별 캡션, 제목, 해시태그, 첫 댓글 | 텍스트 생성이라 매우 쌈. 한 번 호출로 여러 채널 분을 함께 만든다 |
| 비율 변경(세로, 정사각, 가로) | 재렌더. 소재 재사용이라 **크레딧 0** |
| 길이 변경(60초, 30초, 15초) | 어느 컷을 쓸지만 다름. 소재 재사용이라 **크레딧 0** |

**즉 한 번 만들어 여러 채널로 뿌리는 것이 우리 구조에서는 거의 공짜다.** 경쟁사는 채널마다 다시 생성해야 한다. 편집이 재렌더인 것과 같은 이유이고, 같은 뿌리에서 나온 두 번째 강점이다.

### 단 "거의"라고 쓴 이유 (아직 미검증인 것)

**소재를 재사용할 수 있는 범위 안에서만 0이다.** 다음 두 경우는 재생성이 필요할 수 있고, 아직 실험으로 확인하지 않았다.

| 경우 | 왜 문제인가 | 상태 |
|---|---|---|
| 세로에서 가로로 극단적 비율 변경 | 세로로 만든 그림을 가로로 자르면 인물과 핵심이 잘려 나간다 | **미검증.** 안전 영역을 넉넉히 잡고 만들면 크롭으로 덮을 수 있다는 가설이 있으나 확인 안 됨 |
| 60초에서 15초로 줄이며 새 후크가 필요할 때 | 컷만 빼면 말이 끊긴다. 나레이션을 다시 만들어야 한다 | 그 컷의 음성만 재생성이므로 소액 과금 |

**따라서 실험 전에는 "다채널이 완전 무료"라고 주장하지 않는다.** 정확한 문장은 "소재를 재사용하는 범위에서는 추가 크레딧이 없다"이다. 세로와 가로를 함께 뽑는 실험이 끝나면 그때 수치로 말한다.

## 3.85 관심사 분리의 기준 세 가지 (회장 2026-08-15 요청, 판정용 정본)

무엇이 어느 쪽인지 헷갈릴 때 이 세 질문을 순서대로 던진다. 하나라도 studio에 걸리면 studio다.

| 순서 | 질문 | studio면 | openclaw면 |
|---|---|---|---|
| 1 | **유저의 소셜 계정 자격증명이 필요한가** | 필요 없다 | 필요하다. 토큰을 가진 쪽이 여기다 |
| 2 | **창작 정보(브랜드킷, 금지선, 취향 프로파일, 편집 지시서)를 읽거나 쓰는가** | 그렇다. 이 정보는 studio만 관리한다 | 아니다 |
| 3 | **미디어 바이트를 직접 만지는가**(자르기, 크롭, 재인코딩, 합성) | 그렇다 | 아니다. 파일을 옮기고 올리기만 한다 |

**적용 예시**

| 작업 | 1번 | 2번 | 3번 | 판정 |
|---|---|---|---|---|
| 채널별 캡션 생성 | 불필요 | 브랜드 톤 사용 | 없음 | studio |
| 비율 크롭 | 불필요 | 안전영역 규칙 사용 | 있음 | studio |
| 롱폼 쪼개기 | 불필요 | 후크 판단 | 있음 | studio |
| 예약 발행 | **필요** | 없음 | 없음 | openclaw |
| 성과 수집 | **필요** | 없음 | 없음 | openclaw |
| 자동 댓글과 좋아요 | **필요** | 없음 | 없음 | openclaw |
| 유저 업로드 파일 그대로 발행 | **필요** | 없음 | 없음 | openclaw |

**세 기준이 서로 보강한다.** 자격증명 기준은 보안 경계이고, 창작 정보 기준은 브랜드 일관성 경계이며, 바이트 기준은 구현 능력 경계다. 세 개가 같은 선을 그리면 그 선이 옳다.

## 3.10 openclaw의 본질은 무엇인가 (회장 2026-08-15 질의)

### 사실관계 먼저 (레포 실측, 2026-08-15)

**OpenClaw는 우리가 만든 것이 아니다. 제3자 오픈소스다.**

| 항목 | 실측값 |
|---|---|
| 정체 | `github.com/openclaw/openclaw`, MIT 라이선스, 버전 2026.6.2 |
| 자기 소개 | "Multi-channel AI gateway with extensible messaging integrations" |
| 우리 레포에서 | `openclaw/` 폴더에 통째로 들어와 있다(벤더링) |
| **우리가 만든 것** | `extensions/`(채널별 발행 도구 등 25종 이상), `dashboard/`(Next.js 화면), `studio/` |

**따라서 표현을 고친다.** "openclaw 엔진은 이미 오픈소스로 공개했다"는 부정확하다. 우리가 공개한 것이 아니라 **남의 오픈소스를 가져다 쓰는 것**이다. 우리가 실제로 공개할 수 있는 것은 **우리가 만든 extensions와 studio-engine**이다.

### 툴 레지스트리와 런타임이 무슨 뜻인가

| 용어 | 실제 의미 |
|---|---|
| 툴 레지스트리 | 에이전트가 호출할 수 있는 기능 목록. 우리는 `extensions/<이름>/openclaw.plugin.json`으로 등록한다. 등록하면 에이전트가 "이 글을 스레드에 올려" 같은 요청에 그 도구를 골라 쓴다 |
| 런타임 | 크론이 시각에 맞춰 깨우고, 에이전트를 실행하고, 모델을 고르고(주 모델과 대체 모델), 인증 프로필을 관리하고, 등록된 도구를 실행하는 실행 환경 |

즉 **OpenClaw가 우리에게 주는 것**은 이 네 가지다. 예약 실행, 에이전트 실행, 모델 라우팅과 대체, 플러그인 방식 도구 확장.

### 정정: 방파제는 OpenClaw가 아니라 우리 코드다 (레포 실측 2026-08-15)

앞에서 "openclaw가 토큰 수명과 재시도와 지표 정규화를 감당한다"고 썼는데 **틀렸다.**

실측 결과 그 일들은 **우리 코드에 있다.** `dashboard/src/lib/channel-accounts.ts`, `channel-connection.ts`, `publish.ts`가 연결과 토큰과 발행을 다룬다. 최근 커밋 이력에도 장기 토큰 만료 저장과 연결 실패 수정이 우리 쪽 작업으로 남아 있다.

**그러므로 방파제는 우리가 만든 자산이지 OpenClaw가 준 것이 아니다.** OpenClaw는 그 코드를 실행해 주는 껍데기에 가깝다.

### 툴 레지스트리를 통해서만 되는 일이 있나 (회장 질문에 정직하게)

**거의 없다.** 스레드에 글을 올리는 것은 우리가 직접 API를 호출하면 된다. 크론도, 모델 대체도 우리가 짤 수 있다. 툴 레지스트리의 고유 가치는 하나뿐이다. **언어 모델이 상황을 보고 어느 도구를 쓸지 스스로 고르게 하는 것**이다.

그런데 **우리 발행 파이프라인은 결정론적이다.** 승인된 글을 정해진 채널에 정해진 시각에 올린다. 여기서 모델이 도구를 고를 일이 없다. 즉 **툴 레지스트리의 고유 가치를 우리는 거의 안 쓰고 있다.**

### 그럼 왜 계속 쓰나 (근거를 정직한 크기로 줄인다)

| 진짜 이유 | 무게 |
|---|---|
| 우리가 만든 25종 이상의 확장이 이미 이 플러그인 규격으로 짜여 있다 | 큼. 갈아타면 전부 다시 짜야 한다 |
| 크론, 모델 라우팅과 대체, 인증 프로필이 이미 돌아간다 | 중간. 직접 짜면 몇 주에서 몇 달 |
| 채널 하나 추가가 폴더 하나 추가로 끝난다 | 중간. 우리가 정한 규격이어도 되지만 이미 있다 |

**즉 "OpenClaw여야만 한다"가 아니라 "이미 그 위에 지었으니 유지하는 것이 싸다"가 정확한 근거다.** 강한 종속 근거가 아니며, 나중에 부담이 되면 벗어날 수 있다. MIT라 복사해서 필요한 부분만 남겨도 되고, 회장 지적대로 이미 레포에 통째로 들어와 있어 상대가 사라져도 당장 멈추지는 않는다. **따라서 제3자 의존 위험은 내가 앞서 말한 것보다 작다.**

### 재정정: 회장 구상에서는 발행이 결정론적이지 않다 (2026-08-15)

내가 "발행은 결정론적이라 에이전트가 필요 없다"고 한 전제가 **회장 구상에서는 틀렸다.**

> 회장 원문: "발행 자체는 꼭 정해진 시간에 안 해도 된다. openclaw-service에서 알아서 판단해서 발행할 수도 있고, 성과나 트렌드에 따라 알아서 studio-service를 호출해 콘텐츠를 만들고 판단하고 발행하고 댓글을 관리한다는 게 더 장점 아닐까."

**이 구상이 곧 에이전트 루프다.** 성과를 보고, 트렌드를 보고, 지금 무엇을 만들지 정하고, 도구를 골라 실행하고, 결과를 보고 다음을 정한다. **툴 레지스트리의 고유 가치가 정확히 여기서 쓰인다.** 크론은 그 루프를 깨우는 장치일 뿐 본질이 아니다.

**그래서 OpenClaw를 쓰는 근거가 바뀐다.** "이미 지었으니 싸다"가 아니라 **"우리가 하려는 것이 원래 에이전트 루프다"**가 진짜 근거다. 앞 절의 축소 판단은 발행을 예약 실행으로만 볼 때의 이야기였다.

**다만 정체성은 다르다.** 우리 정체성은 OpenClaw가 아니다. 정체성은 studio의 취향 학습과 편집이고, OpenClaw는 그것을 자동으로 굴리는 실행 수단이다. 수단이 정체성이 될 필요는 없다.

### Hermes Agent와 비교 (회장 질의, 2026-08-15 조사)

Nous Research의 오픈소스 에이전트로, 메모리와 스킬과 크론 스케줄러를 갖추고 메신저로 결과를 보낸다. 즉 **OpenClaw와 같은 범주**다.

둘 다 자체 호스팅 오픈소스 에이전트 런타임이며, **설계 철학이 정반대**다.

| 축 | OpenClaw | Hermes Agent |
|---|---|---|
| 한 줄 | 통합의 **넓이** | 학습의 **깊이** |
| 강점 | 메시징 채널 25종 이상, 내장 스킬 100여 종, 다중 모델 지원 | 경험으로 자기 지시문을 스스로 고쳐 나가는 폐쇄 학습 루프 |
| 실측 사례 | 도구 계층에 구조화 출력 검증기가 있어 에이전트가 반환할 수 있는 것을 묶기 쉽다. 권한 승인, 격리, 자격증명 필터가 기본 | 비슷한 작업 10에서 20회 후 실행 속도가 2에서 3배 빨라졌다는 벤치마크 |
| 배포 | 자체 호스팅이 기본, 클라우드는 선택 | 호스팅 엔드포인트 쪽에 무게, 자체 호스팅은 유료 등급 |
| 약점 | 학습이 얕다 | 채널 넓이가 얕다 |

**우리에게 맞는 쪽은 OpenClaw다. 이유가 세 가지다.**

1. **우리 도메인이 정확히 다채널이다.** 우리가 25종 넘는 채널을 붙일 수 있었던 이유가 그쪽 강점과 겹친다.
2. **Hermes의 강점이 우리 제품과 겹친다.** 학습 루프는 studio가 하는 일이다. Hermes를 쓰면 학습을 두 곳에서 하게 되고, 우리 핵심 자산을 남의 런타임에 맡기는 셈이 된다. **우리가 팔려는 것을 런타임에 위임하면 안 된다.**
3. **안전 장치가 이미 있다.** 자율 발행을 하려면 에이전트가 무엇을 반환하고 무엇을 실행할지 묶어야 하는데, 구조화 출력 검증과 권한 승인이 기본으로 있다. 자율 판단 발행을 하려는 우리에게 이건 중요하다.

**전환 비용도 있다.** 확장 25종 이상을 다시 짜야 한다. 다만 이건 부차적 근거다. 위 2번이 주된 이유다.

**결론: OpenClaw를 유지한다.** 다만 정체성은 여전히 studio다.

### 라이선스 걱정 해소 (회장 2026-08-15 질의)

**MIT는 파는 것을 막지 않는다.** `openclaw/LICENSE` 실측 확인, "MIT License, Copyright (c) 2026 OpenClaw Foundation".

| 할 수 있는 것 | 지켜야 할 것 |
|---|---|
| 상업적 이용, 유료 판매 | 저작권 표시와 라이선스 전문을 함께 둔다 |
| 수정, 비공개 소스로 배포 | 그것뿐이다 |

**우리 소스를 공개할 의무가 없다.** 수정한 것을 공개할 의무도 없다. 앞서 내가 "팔 때 제3자 런타임을 함께 설치하라고 요구하게 된다"고 한 것은 **라이선스 문제가 아니라 포장과 사용 경험 문제**였다. 표현이 불명확했다.

**Hermes Agent의 라이선스는 아직 확인하지 않았다. 미검증이다.** 도입을 검토하게 되면 그때 확인한다.

### 우리가 OpenClaw가 하는 일을 직접 만들면 무엇이 어려운가 (회장 질의)

| 항목 | 난이도 | 이유 |
|---|---|---|
| 크론 스케줄러 | 쉬움 | 며칠이면 된다 |
| 모델 라우팅과 대체 | 중간 | 한도 초과, 오류 분류, 대체 순서를 다 다뤄야 한다 |
| 에이전트 루프 | 중간 | 모델 호출과 도구 선택과 실행과 반복. 만들 수는 있으나 안정화에 시간이 든다 |
| **구조화 출력 검증, 권한 승인, 격리, 자격증명 필터** | **어려움** | **자율 판단 발행에서 가장 중요한 부분.** 에이전트가 엉뚱한 것을 실행하거나 자격증명을 흘리지 않게 막는 장치다. 직접 만들면 사고를 겪으며 배우게 된다 |
| 확장 25종 재작성 | 큼 | 이미 돌아가는 것을 다시 짠다 |

**정직한 추정: 수 주에서 수 개월.** 더 중요한 것은 **그 시간이 우리 차별점에 쓰이지 않는다는 점**이다. 취향 학습과 편집 지시서는 그동안 멈춘다.

### studio-service는 에이전트 런타임을 쓰면 좋아지나 (회장 질의)

**쓰지 않는 것이 맞다. 이유는 성질이 반대이기 때문이다.**

| | openclaw-service | studio-service |
|---|---|---|
| 필요한 성질 | **판단**. 성과와 트렌드를 보고 무엇을 할지 정한다 | **재현성**. 같은 지시서면 항상 같은 결과가 나와야 한다 |
| 그래서 | 에이전트 런타임이 맞다 | 에이전트 자율성이 오히려 해가 된다 |

**재현성은 studio의 자산이다.** 같은 편집 지시서로 언제나 같은 영상이 나오기 때문에 편집이 재렌더로 끝나고 크레딧이 안 든다. 여기에 에이전트가 매번 다르게 판단하면 그 자산이 무너진다.

| 안 쓰면 불편한 것 | 대응 |
|---|---|
| 작업 큐, 재시도, 진행 상태 관리를 직접 짜야 한다 | 일반 작업 큐 라이브러리로 충분하다. 에이전트 런타임이 필요한 일이 아니다 |
| 소재 공급자를 상황에 따라 고르는 판단 | 규칙으로 고른다. "이 모션은 이 엔진" 같은 실측 규칙이 이미 있다 |

**정리: openclaw는 판단이 필요해서 에이전트, studio는 재현성이 필요해서 결정론.** 이 대비가 두 서비스를 가르는 또 하나의 기준이다.

### 그런데 studio도 LLM과 생성 모델을 쓴다. 그건 자율성 아닌가 (회장 2026-08-15 질의)

**LLM을 부르는 것과 에이전트가 자율적으로 도는 것은 다르다.**

| | LLM 호출 | 에이전트 자율성 |
|---|---|---|
| 무엇 | 입력을 주면 출력이 온다. 함수 호출에 가깝다 | 모델이 **다음에 무엇을 할지**와 **어떤 도구를 쓸지**를 스스로 정하고 반복한다 |
| studio에서 | 정해진 단계에서 정해진 산출물을 받는다. 대본을 받고, 컷을 나누고, 지시서를 쓴다 | 없다. 모델이 "지금 발행할까"를 정하지 않는다 |
| openclaw에서 | | 있다. 성과와 트렌드를 보고 무엇을 할지 정한다 |

**소재 공급자를 고르는 것도 자율 판단이 아니라 규칙이다.** 실측으로 만든 표를 따른다. 달력 되감기 같은 모션은 한 엔진, 버튼 앞 정지는 다른 엔진. 룩업 테이블이지 판단이 아니다.

### 정확히 말하면 studio는 "확률적 생성 + 결정론적 편집"이다

내가 "결정론적"이라고만 쓴 것은 부정확했다. 정확히는 구간이 갈린다.

| 구간 | 성질 | 같은 입력에 같은 결과가 나오나 |
|---|---|---|
| 연출층 (LLM이 지시서를 씀) | 확률적 | 아니다. 매번 다르다 |
| 소재층 (이미지·영상·음성 생성) | 확률적 | 아니다 |
| **편집층 (지시서 대로 픽셀을 그림)** | **결정론적** | **그렇다** |

**핵심은 이것이다. 확률적으로 나온 결과물을 지시서로 고정하는 순간부터 결정론이 된다.**

그래서 A/B/C를 뽑을 때는 확률성이 오히려 필요하다. 세 후보가 서로 달라야 고를 것이 생긴다. 그리고 **유저가 하나를 고른 순간 그 조합이 지시서로 굳고, 그 뒤로는 몇 번을 고쳐도 소재를 다시 만들지 않는다.**

즉 **확률성은 선택 전에 쓰고, 결정론은 선택 후에 쓴다.** 이 전환점이 우리 원가 구조의 정수다.

### 이 결정의 재검토 시점 (회장 2026-08-15 지시)

OpenClaw와 Hermes 중 무엇을 쓸지는 **기술설계 단계에서 한 번 더 검토한다.** 그때 확인할 것은 세 가지다.

1. Hermes Agent의 라이선스(현재 미확인)
2. 자율 발행에 필요한 안전 장치를 각각 얼마나 제공하는지 실제 코드로 확인
3. 그 시점에 우리 확장이 몇 개인지(전환 비용의 크기)

지금 결정은 "당분간 OpenClaw 유지"이며 되돌릴 수 있는 결정이다.

### 우리가 직접 안 짓고 OpenClaw를 쓰는 이유

1. **채널 하나 추가가 폴더 하나 추가다.** 새 채널을 붙일 때 플러그인 규격만 맞추면 런타임이 알아서 인식한다. 우리가 25종 넘는 채널을 붙일 수 있었던 이유다.
2. **크론과 에이전트 실행을 다시 짤 필요가 없다.** 스케줄링, 재시도, 모델 대체를 직접 만들면 몇 달이 든다.
3. **모델 라우팅이 이미 있다.** 주 모델이 한도에 걸리면 대체 모델로 넘어간다. 우리 설정 파일에 그대로 들어 있다.

### 대가와 위험 (반드시 기록)

| 위험 | 내용 |
|---|---|
| 상용 서비스가 제3자 런타임 위에 선다 | 그쪽이 갈아엎거나 멈추면 우리 발행이 멈춘다 |
| 벤더링한 사본의 갱신 규율이 필요하다 | 지금은 폴더째 들어와 있어 상류 변경을 따라가는 절차가 없다 |
| 라이선스 | MIT라 상업적 이용에 문제없다. 이건 위험이 아니라 확인 사항 |

이 위험은 PRD 리스크 장에 넣는다.

### studio-service는 OpenClaw 런타임을 쓰지 않는 편이 낫다 (앞선 판단 수정)

앞에서 "studio도 같은 런타임을 쓰면 된다"고 적었는데, 다시 보니 그 판단이 약하다. **수정한다.**

| 이유 | 설명 |
|---|---|
| 팔 수 있는 형태여야 한다 | studio를 개발자용 제작 API로 팔려는데 제3자 개인 비서 런타임을 함께 설치하라고 요구하게 된다 |
| 필요한 성질이 다르다 | 발행은 "정해진 시각에 외부 API를 두드리는" 일이라 에이전트 런타임이 맞다. 제작은 "지시서대로 결정론적으로 렌더하는" 일이라 일반 작업 큐가 맞다 |
| 위험이 번진다 | 런타임이 멈출 때 발행만 멈추는 것과 제작까지 멈추는 것은 다르다 |

**결론: openclaw-service는 OpenClaw 런타임 위에, studio-service는 자체 작업 큐로 짓는다.** 두 서비스가 런타임을 공유하지 않으므로 서로의 장애가 번지지 않는다.

**그래서 "openclaw를 발행에만 쓰면 낭비 아닌가"에 대한 답은 이렇다.** 낭비가 아니다. OpenClaw가 잘하는 일이 정확히 그것(예약 실행, 다채널 게이트웨이, 플러그인 확장)이고, 우리는 그 일에만 쓴다. 도구를 그 도구가 잘하는 데 쓰는 것은 낭비가 아니라 적재적소다.


**질문:** 예약과 발행과 성과 수집만 남으면 openclaw를 제대로 쓰는 것인가. studio가 직접 발행하는 편이 옳지 않나.

**답: openclaw의 본질은 발행 버튼이 아니라 외부 플랫폼과의 계약을 대신 감당하는 것이다.**

발행 자체는 API 호출 한 번이라 쉽다. 어려운 것은 그 주변이다.

| 실제로 어려운 것 | 왜 |
|---|---|
| 인증 토큰 수명 관리 | 플랫폼마다 만료 주기와 갱신 방식이 다르다. 이 레포에도 토큰 만료와 연결 실패를 고치느라 남긴 커밋이 있다 |
| 플랫폼별 예외 처리 | 호출 한도, 중복 게시 거부, 심사 지연이 전부 다르다 |
| 재시도와 중복 방지 | 실패했는지 성공했는데 응답만 못 받았는지 구분해야 한다. 잘못하면 같은 글이 두 번 올라간다 |
| 예약 실행의 신뢰성 | 정해진 시각에 반드시 돌아야 한다 |
| 성과 지표 정규화 | 플랫폼마다 이름과 의미가 다른 지표를 한 축으로 맞춰야 한다 |

**이 일은 끝나지 않는다.** 플랫폼이 API를 바꾸면 계속 따라가야 한다. 그래서 Ayrshare가 이것만으로 프로필당 월 149달러에서 599달러를 받는 사업을 한다. 층이 실재한다는 증거다.

### studio가 직접 발행하면 안 되는 이유

1. **studio가 유저의 소셜 계정 토큰을 갖게 된다.** 그러면 studio를 개발자용 제작 API로 팔 수 없다. 제작 기능만 쓰려는 개발사에 소셜 계정을 넘기라고 할 수 없다.
2. **이미 만들어진 유일한 자산을 버리게 된다.** openclaw는 채널 30종이 구현된 v3.0이다. studio는 아직 파이썬 스크립트다. 완성된 쪽을 버리고 다시 짓는 것은 손해다.
3. **플랫폼 변경의 충격이 제작 코드로 번진다.** 지금 구조에서는 플랫폼이 바뀌어도 studio는 아무 영향이 없다.

**결론: 지금 경계가 맞다.** openclaw는 "발행만 하는 얇은 것"이 아니라 **플랫폼 변화를 흡수하는 방파제**다. 그 덕에 studio가 창작에만 집중한다.

## 3.95 빠져 있던 범위: 운영자 화면과 지원 (회장 2026-08-15 지적)

지금까지 **유저 화면만 그렸고 우리가 볼 화면을 안 그렸다.** 두 서비스 각각 필요하다.

| 무엇 | studio-service | openclaw-service |
|---|---|---|
| 회원과 테넌트 관리 | 테넌트, 사용량, 상태 | 회원, 소셜 연결 상태 |
| 크레딧과 결제 | 충전, 차감 이력, 환불, 잔액 조정 | 상위 과금과 대납 정산 |
| 사용량과 원가 | 테넌트별 크레딧 소모, 공급자별 원가 | 채널별 발행량 |
| 장애와 알람 | 생성 실패율, 공급자 장애, 큐 적체 | 토큰 만료 임박, 발행 실패율 급증, 채널 정책 변경 의심 |
| 유저가 막힌 것 | 어느 단계에서 이탈했나, 실패한 요청 | 연결 실패, 발행 거부 사유 |
| 운영 루프 조회 | 방식별 성과 집계, 실패 프롬프트 | 채널별 성과 정규화 |

**알람이 특히 중요하다.** 토큰 만료는 유저가 모르는 사이에 발행을 멈춘다. 유저가 항의하기 전에 우리가 먼저 알아야 한다.

**유저 지원 경로도 정의한다.** 유저가 막혔을 때 어디로 연락하고, 우리가 그 요청과 이력을 어떻게 보는지. 1인 운영이라 자동으로 상태가 보이지 않으면 대응이 늦는다.

**이 범위를 두 PRD와 유저플로우에 반영한다.**

## 4. 인증과 과금

- 소비자는 openclaw-service에 한 번만 가입한다. 소셜 로그인 사용 가능.
- openclaw-service가 studio-service의 테넌트를 자동으로 만든다. 소비자는 studio의 존재를 몰라도 된다.
- 유저 자격증명은 studio로 넘어가지 않는다. 두 서비스 사이는 **서버 대 서버 API 키**다. 따라서 소셜 로그인과 충돌하지 않는다.
- 충전식 과금. 원가 근거는 `studio/docs/소재원가-검증표-2026-08-15.md` v1.1.0. 1편 직접 원가는 약 1,635원에서 1,823원, 권장 첫 충전팩은 1,000크레딧 33,000원, 1편 차감 144에서 162크레딧.
- studio-service 단독 판매는 **개발자용 API 상품**으로만 연다. 소비자용 단독 판매는 화면이 없으므로 성립하지 않는다.

## 5.5 페르소나와 시장 범위 (회장 2026-08-15)

**제품 범위는 좁히지 않는다.** 개발 지식, 금융 지식, 사업체 홍보, 소비형 숏폼, 개인 생각 전달, 가상 인플루언서, 순수 아트까지 전부 대상이다. 질문과 제안으로 방향을 만들어 가는 구조라 도메인에 종속되지 않는다.

| 서비스 | 페르소나 |
|---|---|
| studio-service (2단계, 화면 생긴 뒤) | 자기 콘텐츠를 한 번 만들어 보고 싶은데 무엇부터 할지 몰라 백지공포를 느끼는 사람 |
| openclaw-service | 대행사를 쓰기 싫은 사업자. 그리고 자기 콘텐츠를 여기저기 뿌리며 관리하고 싶은 크리에이터 |
| 마케터 | 필요에 따라 둘 중 아무거나 |

### 진짜 타깃: 판단은 되는데 정의는 못 하는 사람 (회장 2026-08-15, 이 제품의 핵심)

> 회장 원문: "누가 가져오면 좋다 안 좋다 평가하고, 유사한 것 가져왔을 때 어 그거야 괜찮네 이 정도 판단은 할 수 있는데, 직접 정의해서 만들라고 하면 어려운 사람들이 대상이다."

이것이 이 제품이 존재하는 이유다. 사람은 **고르는 능력과 만드는 능력이 다르다.** 대부분은 고르는 능력이 훨씬 앞선다. 기존 도구는 전부 만드는 능력을 요구한다. 힉스필드를 열면 무엇을 써야 할지도, 얼마가 들지도 모른다. 우리는 그 반대로 간다. **가져다 보여주고 고르게 한다.**

회장 자신이 해줘단타를 만들 때 겪은 것이 근거다. 대본 구성, 스타일, 화면 구성이 전부 백지였고 벤치마킹도 직접 해야 했다. 그 노동을 제품이 대신한다.

| 우리가 겨냥하는 사람 | 겨냥하지 않는 사람 |
|---|---|
| 이런 스타일로 **계속** 만들고 발전시켜야 하는 사람 | 챗봇에 한 번 입력하고 결과 나오면 끝낼 사람 |
| 좋고 나쁨은 판단하지만 백지에서 정의는 못 하는 사람 | 이미 자기 스타일과 제작 공정이 선 사람 |

### 서비스별 타깃 (회장 2026-08-15)

| 서비스 | 누구 |
|---|---|
| openclaw-service | 자기가 만든 제품을 알리고 싶은 바이브 코더, 예비 창업자, 스타트업 팀. 콘텐츠를 시리즈로 연재해 여기저기 뿌리고 싶은데 무엇부터 할지 모르는 사람(해줘단타가 이 경우) |
| studio-service (2단계) | 조별 과제에 이미지·영상·텍스트·음악을 쓰고 싶은 대학생, 포스터 한 장이 필요한 자영업자 등 더 다양함 |
| 마케터 | 필요에 따라 둘 중 아무거나 |

**단, 제품 범위와 초기 마케팅 얼굴은 다른 층이다.** 1인이 모든 페르소나에 랜딩페이지와 소재와 커뮤니티를 동시에 만들 수 없고, "다 됩니다"는 아무에게도 꽂히지 않는다. 그래서 **제품은 전방위로 짓되 초기 마케팅 얼굴은 하나만 고른다.** 고르는 기준은 우리가 실제 증거물을 가진 곳이다.

## 6. 포지셔닝

- 차별점은 "더 좋은 프롬프트"가 아니라 **일관성과 자산 축적**이다. 범용 모델이 좋아져도 그쪽은 일회성으로 끝난다. 우리는 같은 얼굴(Soul ID), 같은 목소리(고정 아이디), 같은 톤으로 100편을 뽑고 그 자산을 데이터베이스로 관리한다.
- 진입 문구 후보: 수십만원짜리 월 구독 대신 충전해서 조금씩 써 본다.
- 비교 대상: 시그마인은 "마케터 채용 대신"으로 서 있다. 문구가 겹치지 않게 잡는다.
- **"원클릭"이라는 말을 쓰지 않는다.** 고르게 해서 취향을 배우는 것이 우리 방식이다.

## 7. 경쟁 지형 (PRD에 반영할 것)

| 축 | Ayrshare | 시그마인 | 우리 |
|---|---|---|---|
| 무엇을 파나 | 개발자용 소셜 발행 API | 완제품 마케팅 자동화 | 제작 API와 그것을 감싼 소비자 제품 |
| 제작 | 없음 | 있음. 볼륨 중심 월 약 300건 | 있음. 편당 밀도와 취향 학습 |
| 최적화 주체 | 해당 없음 | AI가 성과 보고 알아서 조정 | 사용자가 골라서 축적 |
| 가격 | 프로필당 월 149에서 599달러 | 번들 월 75만원 | 충전식 |
| 브랜드 입력 | 해당 없음 | 홈페이지 크롤링 | 내부 지식 인테이크 |

**기억할 반론:** 시그마인은 매출과 정부 지원이 있고 속도에서 우리가 뒤진다. 일반 자영업 SNS 시장에서 정면으로 붙지 말고 정확성이 돈이 되는 좁은 도메인(교육·금융)부터 잡는다.

## 8. 실측으로 확정된 제작 규칙 (PRD 제약으로 반영)

- 이미지·영상 프롬프트에 텍스트를 요구하지 않는다. 모델이 한글을 못 쓴다.
- 자막·용어칩·오버레이는 로컬 렌더 후 합성한다. 비용 0, 완전 제어.
- 목소리는 고정 아이디로 박는다. 지정이 없으면 호출마다 다른 사람이 나온다.
- 속도는 후처리 배속이 아니라 생성 파라미터로 조절한다.
- Soul ID는 영구 자산이다. 한 번 학습하면 전 편에 같은 얼굴.
- 소재 공급자는 어댑터로 추상화한다. 힉스필드가 무료 플랜 소진으로 멈춘 실사례가 있다.

## 9.5 아직 안 다룬 것 (기술설계 전에 정해야 함)

논의에서 한 번도 다루지 않은 항목들이다. 전부 돈이나 사고와 직결된다.

**회장 결정 완료(2026-08-15). 아래는 확정 사항이다.**

| 항목 | 확정 |
|---|---|
| **자율 발행** | **테넌트 설정 옵션으로 둔다.** 자율 발행과 승인 후 발행 중 유저가 고른다. 채널별·유형별로 다르게 둘 수 있게 한다 |
| **실패한 생성의 과금** | **품질 게이트 반려분은 무과금.** 고객이 고른 결과물이 아니므로 받을 근거가 없다. 공급자 호출 비용은 우리 손실이며, 반려율을 운영 루프로 관리해 손실을 줄인다 |
| **무료 체험** | **연락처를 받고 경험을 주는 방식.** 시그마인이 메일 주소를 남기면 콘텐츠나 크레딧을 주는 것을 회장이 직접 확인했다. 상시 무료 등급이 아니라 **체험 크레딧 지급 + 연락처 확보**가 원가와 리드를 동시에 잡는다 |
| **테넌트가 떠날 때** | 결과물, 소재, 취향 프로파일 **전부 유저 것.** 아래 방식으로 준다 |
| **우리 벤처 데이터 분리** | **테넌트에 '내부 테스트' 표시를 둔다.** 실제 유저와 내부 테스트를 계정 단위로 구분해 운영 루프 집계에서 분리한다 |

### 데이터 소유권을 어떻게 주나 (회장 질의)

| 무엇 | 어떻게 |
|---|---|
| 결과물 | 원본 파일 일괄 내려받기 |
| 소재 | 업로드한 것과 생성한 것 모두 일괄 내려받기 |
| **편집 지시서** | 함께 준다. 이게 있어야 다른 도구에서도 재편집이 가능하다. 안 주면 결과물만 있고 고칠 수 없는 상태로 나가게 된다 |
| **취향 프로파일** | 사람이 읽을 수 있는 형태로 준다. "밝은 톤 선호, 컷 길이 짧게, 나레이션 빠르게" 같은 축과 가중치. 내부 식별자 덩어리를 주면 준 것이 아니다 |
| 성과 이력 | 어느 선택이 어떤 결과였는지 표로 |

**원칙: 옮겨 가서도 쓸 수 있는 형태로 준다.** 잡아 두는 힘은 데이터를 인질로 삼는 데서 나오면 안 된다. 노하우가 계속 쌓이기 때문에 남는 것이어야 한다.

**운영 루프 집계만 남는다.** 이건 식별 불가한 통계이고, 내부 테스트 표시와 함께 관리한다.

### 내부 테스트 표시 (회장 제안, 채택)

해줘단타와 제로원이 첫 사용자다. 우리 취향이 운영 루프에 과대 반영되면 제안 엔진이 우리 취향을 남에게 강요하게 된다.

**테넌트마다 '내부 테스트' 여부를 표시하고, 운영 루프 집계에서 분리한다.** 가중치를 낮추는 것보다 아예 구분해서 보는 편이 낫다. 나중에 실제 고객이 쌓이면 "내부 제외" 집계가 기본이 된다.

## 9.6 레드팀 회수 결정 5건 확정 (회장 2026-08-15)

레드팀 보고서(`docs/레드팀-제품구상-2026-08-15-gpt-codex.md`)가 회수 요청한 5건에 대한 회장 확정이다.

### D1. 시장 범위: 고객은 한국, 출력은 다국어

> 회장 원문: "주로 한국인을 대상으로 하지만 한국인 중에서 영어권이나 일본 태국 등을 타겟팅하는 사람들도 있잖어. 그 사람들을 위한 다국어 콘텐츠는 만들 수 있어야 할 것 같아."

레드팀은 글로벌 동시 출시를 NO-GO로 판정했으나, 회장 확정은 그 판정과 충돌하지 않는다. **두 가지가 서로 다른 층이기 때문이다.**

| 층 | 결정 | 이유 |
|---|---|---|
| 고객면(가입, 결제, 지원, 랜딩, 문서) | 한국어 하나 | 세금·시간대·지원이 1인 운영의 한계를 만든다 |
| 출력 콘텐츠 언어 | 다국어(영어, 일본어, 태국어 등) | 한국인 고객 중 해외 시장을 노리는 사람이 실재한다 |

따라서 studio는 **출력 언어를 요청 파라미터로 받는다.** 언어는 채널 규격과 같은 급의 제약이지 취향 프로파일이 아니다. 다만 취향 프로파일은 언어별로 갈라져야 한다. 한국어에서 잘 먹은 훅이 일본어에서 그대로 먹지 않기 때문이다.

**품질 보증 경계를 명시한다.** 회장이 직접 판정할 수 있는 언어는 한국어와 영어다. 그 외 언어는 "생성은 되지만 원어민 검수는 우리가 하지 않는다"를 제품 문구로 명시한다. 이걸 안 적으면 태국어 품질 클레임이 1인 지원으로 들어온다.

### D2. 첫 외부 고객: 바이브 코더 + 부업 크리에이터

> 회장 원문: "자기 컨텐츠 만들어서 방송국 만들어서 조회수 수익 얻거나 쿠팡 파트너스 부업하고 싶은 사람들"

레드팀은 "바이브 코더 하나로 좁혀라"였으나 회장이 한 층을 더했다. 둘은 서로 다른 사람이지만 **하나의 공통점으로 묶인다: 계속 뿌려야 하고, 성과가 돈으로 직결되며, 백지에서 시작하지 못한다.** 부업 크리에이터는 오히려 성과 피드백 루프의 가치를 더 크게 느낀다. 조회수와 파트너스 수익이 곧 지표이기 때문이다.

### D3. 유료 수요 검증: 자체 사용 우선

> 회장 원문: "일단 내가 해줘단타 제로원으로 계속 쓰고 이 서비스도 자동화 마케팅을 하면서 봐야지."

레드팀은 "적격 20명 예치금 3명"을 개발 선행 게이트로 걸자고 했으나, 회장 확정은 **자체 사용(도그푸딩)을 먼저 돌린다**이다. 우리 자신이 첫 사용자이고 그 콘텐츠가 증거물이 된다는 1차 목표(0.5절)와 일관된다. 추가로 이 서비스 자신의 마케팅도 이 서비스로 한다.

**단 kill-criteria는 삭제하지 않고 시점을 뒤로 옮긴다.** 자체 사용에서 나온 콘텐츠를 proof로 써서 외부 유료 수요를 검증하는 것이 순서다. 자체 사용만으로 "수요가 있다"고 말할 수는 없다. 우리는 우리 제품을 공짜로 쓰기 때문이다.

### D4. 글로벌 준비: 아키텍처는 열고 홍보는 나중에

> 회장 원문: "본격 외국 홍보 등은 나중에 하되 항상 글로벌로 나갈 수 있다는 거 생각하고 만들자."

데이터 모델에 locale, currency, timezone, tax region, policy version을 **1단계부터 넣는다.** 나중에 붙이면 마이그레이션 비용이 커지는 항목이라 지금 넣는 것이 싸다. 반대로 self-serve 다국가 결제와 24시간 지원 약속은 열지 않는다.

결제 구조는 Merchant of Record 사용을 **기술설계 단계에서 재검토**한다. 지금 정하지 않는다. 국내 결제만 하는 동안은 국내 PG로 충분하고, 해외 결제를 열 때 Paddle 같은 대행이 세무를 대신 지는 구조가 유리하다.

커뮤니티 자체 운영은 회장 언급대로 후보로 기록만 한다.

### D5. A/B/C 후보: 저해상도 먼저, 고해상도는 추가 과금

> 회장 원문: "A/B/C 같은 건 내가 퀄리티를 보고 판단해야 할 것 같고, 아니면 일단 저퀄로 주고 고퀄로 다시 보기는 추가 금액을 내게 한다든지."

레드팀 지적은 후보 3개를 모두 완성본으로 뽑으면 해당 컷 원가가 3배가 되어 33,000원 팩의 방어 여지가 사라진다는 것이었다. 회장 확정은 **저해상도 후보 3개 -> 선택 -> 선택된 하나만 고해상도**이다.

| 단계 | 산출 | 과금 |
|---|---|---|
| 후보 제시 | 저해상도 또는 짧은 프리뷰 3개 | 저해상도 원가만 |
| 선택 후 | 고해상도 완성본 1개 | 완성본 원가 |
| 선택 안 한 후보를 나중에 고해상도로 | 완성본 | 추가 과금 |

**미검증 항목:** 저해상도 프리뷰가 회장이 판단할 수 있는 수준인가는 아직 실측하지 않았다. 프리뷰가 너무 거칠면 선택이 무의미해지고, 충분히 좋으면 원가가 안 내려간다. **기술설계 전에 실제로 저해상도와 고해상도를 각각 뽑아 회장이 눈으로 판정하는 실험이 필요하다.** 이 실험 결과가 나오기 전에는 PRD에 프리뷰 해상도 수치를 확정하지 않는다.

## 9.7 요청 조립층: 이 제품의 해자 (회장 2026-08-15)

> 회장 원문: "타겟층이 한국인지 일본인지 영어권인지 등등 먼저 입력을 받아야겠네. 개인의 취향과 타겟층에서 요구사항 마케팅 공통 등 출력 프롬프트에 영향 주는 걸 진짜 잘 설계해야겠다. 이게 우리 해자일 듯."

### 왜 여기가 해자인가

일반 사용자가 영상·이미지를 못 만드는 이유는 모델 성능이 아니라 **무엇을 어떻게 요구해야 하는지를 모르기 때문**이다. 힉스필드를 열어도 무슨 말을 써야 할지, 무엇을 신경 써 달라고 해야 할지가 백지다. 우리가 파는 것은 모델 접근권이 아니라 **그 요구를 대신 조립하는 능력**이다.

모델은 계속 좋아지고 누구나 쓴다. 조립 규칙은 우리가 축적하는 것이라 복제되지 않는다.

### 출력 프롬프트에 영향을 주는 입력 층 네 가지

| 층 | 무엇 | 어디서 오나 | 저장 위치 |
|---|---|---|---|
| 타깃 시장 | 한국, 일본, 영어권, 태국 등 | 사용자가 제작 요청 시 선택 | 요청 파라미터 |
| 마케팅 공통 지식 | 그 시장에서 통하는 훅 문법, 길이 감각, 금기, 플랫폼 관습 | 우리가 축적 | 우리 자산(테넌트 무관) |
| 개인 취향 | 이 사용자가 반복해서 고른 방향 | 선택 기록에서 학습 | 취향 프로파일(언어별로 분리) |
| 브랜드 제약 | 브랜드킷, 금지선, 고정 목소리와 얼굴 | 온보딩과 누적 | 테넌트 자산 |

**네 층은 서로 다른 수명과 소유자를 가지므로 섞어서 저장하면 안 된다.** 타깃 시장은 요청마다 바뀌고, 마케팅 공통 지식은 우리가 전 고객에게 공유하며, 취향은 사용자별이고, 브랜드 제약은 사용자별이면서 거의 안 바뀐다. 이 넷을 하나의 프롬프트 문자열로 뭉쳐 저장하면 어느 것이 결과를 만들었는지 설명하지 못하고 개선도 못 한다.

### 성공 조건

회장 표현으로 "몇 번 써 봤는데 진짜 내가 원하는 대로 딱 출력물이 나오면 그날부터 충성고객 확정"이다. 즉 이 제품의 진짜 수용기준은 기능 개수가 아니라 **초기 몇 회 안에 원하는 결과에 도달하는가**다. 이것을 측정 가능한 지표로 내려야 한다. 후보: 첫 만족 결과까지 걸린 시도 횟수, 3회차 결과의 선택률 개선.

### 다국어 품질 판정 루프 (회장 2026-08-15)

회장이 이해하지 못하는 언어는 사람이 판정할 수 없다. 대신 두 경로로 닫는다.

1. **성과로 판정한다.** 태국어 결과물이 좋은지는 그 채널의 실제 반응이 말한다. 언어별 취향 프로파일이 성과 신호를 받아 갱신된다.
2. **사용자 셀프 피드백.** 그 언어를 아는 사용자 본인이 고치고 평가한다. 수정 지시와 평가가 약한 학습 신호로 들어간다.

따라서 다국어는 "우리가 검수한다"가 아니라 **"성과와 사용자 피드백이 검수한다"**로 설계한다. 이 루프가 안 돌면 다국어는 품질 보증 없는 기능으로 남는다.

## 9.8 취향 학습 노출과 작업 시작 지점 (회장 2026-08-16)

### D6. 학습된 정보는 항상 보이고 수정 가능해야 한다

> 회장 원문: "처음엔 사용자 상황 취향을 받아서 학습하고, 자기가 어떤 정보가 학습되어 있는지 항상 어딘가에 두고 수정이 가능하게 해야 할 듯함."

취향 프로파일은 숨은 상태가 아니라 **상시 열람·수정 가능한 화면**이어야 한다. 사람이 읽을 수 있는 문장으로 보이고, 틀린 항목을 직접 지울 수 있어야 한다.

이유는 두 가지다. 첫째, 학습이 잘못됐을 때 사용자가 고칠 방법이 없으면 그 뒤 결과물이 계속 어긋난다. 둘째, 우리가 파는 것이 "당신 취향을 배운다"인데 배운 내용을 못 보여주면 주장을 증명할 수 없다.

화면 요건: 온보딩에서 받은 초기 상황과 취향, 이후 선택으로 갱신된 항목, 각 항목의 근거(어느 선택에서 나왔는지), 항목별 삭제와 수정. 언어별로 분리해서 보인다(§9.6 D1).

### D7. 작업 시작 지점에서 추천을 받는다

> 회장 원문: "작업 시작할 때 성과, A/B/C, 트렌드 등을 가끔씩 받아서 새로운 영상이나 학습을 추천받아야 할 것 같고."

빈 화면에서 시작하지 않는다. 제작을 시작하는 지점에 **무엇을 만들지에 대한 추천**이 이미 놓여 있다. 근거는 세 가지다. 지난 콘텐츠의 성과, 이전 후보 선택 이력, 현재 트렌드.

"가끔씩"이라는 회장 표현이 중요하다. 매번 밀어붙이면 피로해진다. 빈도와 발동 조건은 미결정으로 둔다(후보: 성과 데이터가 유의미하게 쌓였을 때, 트렌드가 크게 바뀌었을 때, 일정 기간 제작이 없었을 때).

### D8. 작업 단위는 하나, 출력 플랫폼만 고른다

> 회장 원문: "작업은 항상 OSMU에서 진행하되 어떤 플랫폼으로 출력할지를 결정하는 것으로 할까."

**채널별로 따로 만들지 않는다.** 하나의 작업을 만들고, 그 작업에서 어느 플랫폼으로 낼지를 고른다. 이것은 기존 마스터 하나에 채널 파생 여럿 구조(§3.9)와 같은 말이며, 화면 동선도 그것을 따라야 한다.

즉 사용자는 "인스타용 만들기"가 아니라 "이 주제로 만들기"를 하고, 그다음 출력 플랫폼을 고른다. 플랫폼 선택이 제작의 입구가 아니라 출구다.
