### DESIGN.md에서 상속한 것

- **색 토큰**: `--surface`, `--surface-2`, `--border`, `--text`, `--muted`, `--subtle`, `--accent`, `--accent-soft`, `--success`, `--warning`, `--danger`와 각 soft 변형. **새로 만든 색 0개.**
- **간격 토큰**: `--space-1~6`, `--stack`, `--stack-tight`, `--stack-section`, `--pad-inset`. **새로 만든 간격 값 0개.**
- **글자 토큰**: `--fs-caption`, `--fs-body-sm`, `--fs-body`와 대응 `--lh-*`. **새 글자 크기 0개.**
- **형태 토큰**: `--radius`(패널·카드), `--control`(썸네일·자리표시). **새 radius 0개.**
- **컴포넌트**: `panel`, `notice`(중립·경고·위험), `status` 뱃지, `list`/`list-row`, `platform-tabs`, `action-group`, `field`/`label`, `OriginChip`, `StatusBadge`, `Button`, `Panel`, `Notice`, `ActionGroup`, `FormField`를 그대로 조립해 신규 블록을 만들었다.
- 신규 컴포넌트 6개는 DESIGN.md §7 인벤토리에 등록해 시스템 밖에 방치하지 않았다.

### 실제 코드 `dashboard/src`에서 확인해 반영한 구조

- `app/studio/page.tsx`(625줄)의 화면 골격: 소재 입력 → 생성 → 미리보기 → 저장·발행 순서와 우측 발행 이력 패널. 신규 블록을 이 순서 안에 끼워 넣었고 순서를 바꾸지 않았다.
- `components/studio/PlatformPreview.tsx`의 미리보기 7종 구성. 프로토타입 미리보기 수를 코드와 어긋나게 늘리지 않았다.
- `components/layout/Sidebar.tsx` 계열의 목적지 구성. 코드에 없는 화면을 그리지 않았고, 신규 라우트를 0개로 유지한 이유가 이것이다.
- `wiki/product/marketing-hub-surface-map.md`의 Studio 인벤토리(미리보기 7, 직접 발행 4, 텍스트 어댑터 8, 영상 3)를 합치거나 바꾸지 않았다.

### 새로 만든 것과 그 이유

| 새로 만든 것 | 기존에 없던 이유 |
|---|---|
| 타깃 시장·출력 언어 선택과 요약 스트립 | 출력 언어를 요청 파라미터로 받는 결정 자체가 2026-08-15 §9.6 D1에서 나왔다. v24 시점에는 다국어 출력이 제품 범위에 없었다 |
| 추천 근거 카드(질문 3개 상한) | v24는 사용자가 소재를 넣으면 바로 생성하는 흐름이라 "무엇을 만들지 정해 주는 층"이 없었다. 백지 공포 해소가 §3.7의 새 요구다 |
| 요청 조립 4층 노출 | §9.7에서 처음 정의된 개념이다. 네 층을 분리 저장한다는 결정이 v24 이후에 나왔으므로 대응 화면이 있을 수 없었다 |
| 저해상도 후보 비교 3개 | §9.6 D5의 2단 과금 모델이 v24 이후 확정됐다. v24에는 후보라는 개념 자체가 없고 결과물이 하나였다 |
| 후보 영역 상태 4종·2줄 clamp·keep-all | 위 후보 개념이 새로 생겼으니 그 데이터 상태와 넘침 규칙도 같이 정의해야 했다. 상태 토글 장치 자체는 기존 것을 썼다 |

새 화면·새 라우트·새 IA는 0개다. 위 5개는 전부 기존 `/studio` 화면 안에 들어갔고, 기존 블록은 하나도 지우지 않았다.

## 7.5 벤치마크 (실조사, 2026-08-16)

관념 벤치마킹이 아니라 실제 검색으로 확인한 경쟁 제품 동작이다. 각 항목은 확인한 사실, 차용한 것, 다르게 한 것 순이다.

### B1. AI 생성 후보 여러 개 중 하나 고르기 (Adobe Firefly)

- 출처: [Adobe 블로그 · Firefly 이미지 편집 신기능](https://blog.adobe.com/en/publish/2026/04/09/new-image-editing-features-adobe-firefly-get-you-from-almost-there-to-exactly-right), [Firefly Boards · Generate image variations](https://helpx.adobe.com/firefly/web/create-mood-boards/firefly-boards/generate-image-variations.html)
- 확인한 사실: Firefly는 프롬프트 하나에서 여러 해석을 뽑아 사용자가 고르게 한다. Precision Flow는 슬라이더로 한쪽 극단에서 반대 극단까지 훑어 하나를 고르게 하고, Boards의 Vary는 중심 아이디어는 유지한 채 스타일·구도만 바꾼 변형을 격자로 보여준다.
- 차용: 후보를 격자로 나란히 놓고 "핵심은 같고 방향만 다르다"를 유지하는 구성. 우리 후보 3개도 같은 대본에서 각도만 달리한 A·B·C다.
- 다르게 한 것: Firefly는 슬라이더로 연속 탐색을 시키지만 우리는 후보를 3개로 못 박았다. 타깃이 "판단은 되는데 정의는 못 하는 사람"이라 무한 탐색은 선택 피로를 키운다. 대신 각 후보에 방향 이름(문제 먼저·결과 먼저·사람이 말하는)을 붙여 무엇을 고르는지 말로 알 수 있게 했다.

### B2. 초안은 싸게, 확정본만 비싸게 (Runway Gen-4)

- 출처: [Runway · Creating with Gen-4 Video](https://help.runwayml.com/hc/en-us/articles/37327109429011-Creating-with-Gen-4-Video), [Runway Gen-4 Turbo 실사용 가이드](https://pamistanbul.com/en/pamlab/runway-gen-4-turbo-guide-2026)
- 확인한 사실: 권장 작업 흐름 자체가 Turbo(초안)와 표준 Gen-4(마스터)의 2단이다. 구도·모션·타이밍이 잡힐 때까지 싼 Turbo에서 반복하고, 확정된 샷 하나만 같은 프롬프트와 시드로 표준 모델에 다시 돌린다. 기본 출력은 720p이고 4K는 크레딧이 2배다.
- 차용: 저해상도 다회 탐색 후 확정본 1개만 고품질로 뽑는 2단 구조. 결정문 D5와 같은 방향이 상용 제품에서 이미 표준이라는 근거다.
- 다르게 한 것: Runway는 이 2단을 사용자가 스스로 알아서 운용해야 한다(모델 이름과 크레딧 표를 이해해야 함). 우리는 그것을 UI 기본 동선으로 박고, 후보 카드마다 고해상도 예상 비용과 소요 시간을 미리 적었다. 모델명·크레딧이 아니라 원화 금액과 분 단위로 쓴다.

### B3. 업스케일 과금을 언제 알려주나 (Leonardo AI)

- 출처: [Leonardo.AI pricing 2026 (eesel 정리)](https://www.eesel.ai/blog/leonardo-ai-pricing), [Leonardo AI Pricing 2026 가이드](https://fluxnote.io/guides/leonardo-ai-pricing-guide-2026)
- 확인한 사실: 토큰 차감제이고 업스케일은 별도 행위로 토큰을 더 쓴다(업스케일 5토큰 수준). 소모량은 작업의 GPU 부하에 비례하며, 고해상도·타일링·다중 생성이 겹치면 소모가 빠르게 불어난다. 무료 150토큰은 금방 소진된다는 후기가 반복된다.
- 차용: 업스케일을 생성과 분리된 유료 행위로 취급하는 모델.
- 다르게 한 것: Leonardo는 소모량이 사후에 드러나 "왜 이렇게 빨리 없어졌나"가 남는다. 우리는 선택 전에 후보별 금액을 붙이고, 고르지 않은 후보를 나중에 고해상도로 만들면 그때 추가 과금이라는 문장을 선택 화면에 고정 노출했다. 놀라게 하지 않는 것이 이 화면의 목적이다.

### B4. 타깃 시장과 출력 언어를 가르는 방식 (Shopify Markets)

- 출처: [Shopify Help · Localization and translation](https://help.shopify.com/en/manual/international/localization-and-translation), [Markets에 언어 배정하기 (langify)](https://support.langify-app.com/support/solutions/articles/11000119897-how-to-assign-languages-to-domains-markets)
- 확인한 사실: Shopify는 시장(Market)과 언어를 별개 축으로 두고, Settings > Markets에서 시장을 고른 뒤 그 시장에 제공할 언어를 따로 붙인다. 즉 "어디에 파는가"와 "무슨 언어로 보여주는가"가 분리된 설정이다.
- 차용: 시장과 언어를 한 덩어리로 묶지 않고 두 축으로 고르게 한 것. 결정문 §9.7이 타깃 시장을 요청 파라미터로, 취향 프로파일을 언어별로 나눈 것과 같은 분리다.
- 다르게 한 것: Shopify는 이 설정을 관리자 설정 화면 깊숙이 둔다(스토어 단위 상시 설정). 우리는 요청마다 바뀌는 값이라 제작 시작 지점에 놓고, 고른 값을 상단 요약 스트립으로 계속 보이게 했다. 그리고 Shopify에 없는 것을 하나 더 붙였다. 우리가 품질을 판정할 수 있는 언어(한국어·English)와 아닌 언어를 화면에서 구분해 말한다.

### 벤치마크가 바꾼 설계 판단

1. 후보 개수를 슬라이더식 연속 탐색이 아니라 3개 고정으로 유지했다(B1 대비 축소가 의도).
2. 비용 표시를 결과 화면이 아니라 선택 화면으로 앞당겼다(B3의 사후 소모 문제 회피).
3. 시장과 언어를 한 드롭다운으로 합치지 않았다(B4의 2축 분리 계승).
