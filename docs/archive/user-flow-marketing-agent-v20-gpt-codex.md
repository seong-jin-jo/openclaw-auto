## 0.5 v19에서 되돌린 것 두 가지

v19를 그대로 발전시키지 않고 두 곳을 되돌렸다. 둘 다 코드에 없는 것을 사실처럼 그린 자리였다.

| v19가 한 것 | 코드 사실 | v20 |
|---|---|---|
| Threads의 Growth·Popular를 Analytics 안으로 옮김 | `ChannelPage`의 탭 배열이 `queue, analytics, growth, popular, settings`다. 둘은 각자 탭이다 | 옮기지 않고 각자 탭으로 되돌렸다. Threads 7탭, 나머지 5탭 |
| 운영자 9개 항목을 모두 있는 것처럼 그림 | 실제로 있는 것은 4개다 | 9개를 지우지 않고 그대로 두되, 없는 5개에 `아직 없음`을 붙였다 |

지우지 않고 표시만 바꾼 이유는, v19가 이미 그린 목표 구조를 없애면 기술설계가 무엇을 향하는지 잃기 때문이다.
목표는 남기고 현재와 구분한다.

## 1. 한 줄 흐름

신규 고객이 Google 계정으로 한 번 들어와서, 채널을 한 번 승인하면 자격증명이 저장되고 무엇이 저장됐는지 읽을 수 있으며,
초안을 만들고 고쳐서 승인한 뒤 지금 게시하거나 예약하고, 결과를 확인하고 설정을 조정한다.
운영자는 같은 여정을 밖에서 보며 막힌 고객을 찾아 풀어주되 고객 대신 게시하지 않는다.

## 2. 회원가입에서 첫 게시까지 (회장 요구의 본줄기)

### 2.1 가입은 한 번의 승인이다

| 단계 | 고객이 하는 것 | 시스템이 하는 것 | 다음에 눌러야 하는 것 |
|---:|---|---|---|
| 1 | `Google로 계속` 한 번 | 세션 확정 뒤에만 진입시킨다. 확정 전에 완료 표시를 하지 않는다 | 성과 화면의 시작 체크리스트 |
| 2 | 업종 선택 | 그 업종의 콘텐츠 가이드를 기본값으로 넣는다 | 다음 |
| 3 | 채널 선택 | 계획으로만 저장한다. 이 선택이 권한을 주지는 않는다 | 다음 |
| 4 | 첫 채널 연결 승인 | 토큰을 교환하고 외부 신원을 되읽어 확인한 뒤 암호화 저장한다 | 저장된 내용 확인 |
| 5 | 콘텐츠 시작 | Studio 또는 그 채널의 Create로 보낸다 | 첫 초안 |

이메일·비밀번호 가입 화면은 그리지 않았다. 코드에 없고, 없는 것을 그리면 그게 발명이다.

### 2.2 가입 직후 첫 화면에서 보이는 것

성과 화면 맨 위에 시작 체크리스트를 둔다. 4항목의 이름과 이동 경로는 코드 그대로다.

`채널 1개 연결 → 브랜드 위키 작성 → 콘텐츠 1개 발행 → 성과 확인`

- 완료한 항목은 초록으로 잠기고, **다음 한 항목만** 파란 테두리로 강조한다. 강조는 언제나 정확히 하나다.
- 주 버튼 문구는 그 다음 항목을 그대로 읽는다. `콘텐츠 1개 발행 시작하기`처럼 무엇을 하는지가 버튼에 있다.
- 4항목이 다 끝나면 이 영역은 사라진다. 끝난 안내가 화면에 남아 자리를 먹지 않는다.
- 근거: Hootsuite는 신규 사용자를 첫 활성화 사건까지 최단으로 밀어붙이는 방식으로 온보딩을 다시 짰다.
  우리는 그 원리를 이미 코드에 있는 4항목에 얹었을 뿐이고 새 항목을 만들지 않았다.

### 2.3 빈 작업 공간의 empty 상태

| 화면 | 없을 때 보이는 것 | 첫 행동 | 하지 않는 것 |
|---|---|---|---|
| 성과 | 시작 체크리스트 4항목과 다음 한 항목 | 채널 1개 연결 | 0으로 채운 가짜 성과 카드 |
| Studio | 브랜드 자료가 없으면 무엇을 먼저 적어야 하는지 | 브랜드 자료 만들기 | 근거 없는 초안 자동 생성 |
| 채널 Queue | 이 채널에 아직 작업이 없다는 사실 | 이 채널에서 초안 만들기 | 남의 예시 글을 내 대기열처럼 보이기 |
| 채널 Analytics | 게시가 확인되기 전에는 숫자를 만들지 않는다는 사실 | 초안 승인하기 | 0건에서 계산한 평균 |

## 3. OAuth 연결만 하면 끝나는가 (회장 요구의 핵심)

### 3.1 기본 경로에 키 붙여넣기는 없다

코드의 콜백은 승인 코드를 받아 토큰을 교환하고, 제공자에게 다시 물어 계정 신원을 확인한 뒤,
암호화 컬럼에 저장하고 기본 계정을 정한다. 고객이 개발자 포털에서 값을 복사해 오는 단계는 기본 경로에 없다.

예외는 셋뿐이고, 화면에서 그 이유를 함께 적는다. 우리 게으름이 아니라 플랫폼 표준이라는 사실이 보여야 한다.

| 채널 | 방식 | 화면에 적는 이유 |
|---|---|---|
| Bluesky | 앱 비밀번호 직접 입력 | 플랫폼이 공식 로그인을 제공하지 않는다 |
| Telegram | 봇 토큰 직접 입력 | 봇은 계정 로그인이 아니라 봇 발급이 표준이다 |
| Discord | Webhook 직접 입력 | 전달 대상이 채널이라 계정 승인 개념이 없다 |

### 3.2 "볼 수도 있고"의 경계를 이렇게 해석했다

회장 문구 `API키 저장되고 볼 수도 있고`를 그대로 따르면 토큰 원문 노출이 되고, 그건 기존 확정 정책과 충돌한다.
그래서 **저장된 값이 아니라 무엇이 저장됐는지를 읽는 화면**으로 해석했다. 근거는 두 가지다.

1. 코드가 이미 그렇게 만들어져 있다. 화면에 값을 내려주는 경로 자체가 없고 복호화는 서버 발행 경로에서만 일어난다.
2. 업계 기준도 소유자·범위·만료·마지막 사용을 보여주는 쪽이다. 값을 보여주는 쪽이 아니다.

읽을 수 있는 것과 아직 못 읽는 것을 한 표에 같이 둔다. 빈 자리를 감추지 않는다.

| 항목 | 지금 읽을 수 있나 | 근거 |
|---|---|---|
| 연결된 계정 이름과 사용자명 | 읽을 수 있다 | `display_name`, `username` 저장 |
| 계정 식별자 끝자리 | 읽을 수 있다 | `external_account_id` 저장. 전체가 아니라 끝자리만 보여준다 |
| 기본 계정 여부 | 읽을 수 있다 | `is_default` 저장 |
| 연결 상태 | 읽을 수 있다 | `status`가 정상·만료됨·연결 해제됨 |
| 연결한 날 | 읽을 수 있다 | `created_at`과 `meta.connectedAt` |
| 연결 만료 | 읽을 수 있다 | `token_expires_at` |
| 연결 방식 | 읽을 수 있다 | 공식 로그인인지 직접 입력인지 |
| 허용한 권한 목록 | **못 읽는다** | scope 저장 컬럼이 없다 |
| 자동 갱신 성공 여부 | **못 읽는다** | 갱신 시도 기록이 없다 |
| 마지막 확인 시각 | **못 읽는다** | 확인 시각 컬럼이 없다 |

못 읽는 세 항목은 빈칸으로 지우지 않고 사유를 적은 채로 남긴다. 값 없음을 정상으로 칠하지 않는 것이 이 표의 목적이다.

### 3.3 "연결됨"이라고 쓸 수 있는 조건

과거 관찰된 결함은 콜백이 신원·권한·만료를 되읽지 않고 성공을 표시한 것이었다. v20의 계약은 이렇다.

| 화면 문구 | 쓸 수 있는 조건 | 못 쓰는 경우 |
|---|---|---|
| 연결됨 | 토큰 교환 성공 **그리고** 외부 신원 되읽기 성공 **그리고** 저장 행 존재 | 교환만 성공하고 신원 확인이 실패했을 때 |
| 게시 가능 | 그 채널의 발행 경로가 실제로 있고 준비 8단계가 6단계 이상 | 코드만 있고 실증이 없을 때 |
| 게시 확인 | 외부 결과와 확인 시각이 둘 다 있을 때 | 요청만 보냈을 때 |
| 자동화 사용 중 | 고객이 계정과 범위를 지목해 동의했을 때 | 연결만 됐을 때 |

준비 8단계는 v19에서 그대로 가져왔다. 오늘 기준 Threads 8/8, Instagram 2/8, 나머지는 표시한 그대로다.

### 3.4 연결이 끊어졌을 때

플랫폼 토큰은 비밀번호 변경·정책·기한으로 끊긴다. Buffer는 끊긴 채널을 목록 맨 위로 올리고 강조해서
고객이 찾아 헤매지 않게 한다. v20도 같게 한다. 이미 `status` 컬럼이 있으므로 새 데이터가 필요하지 않다.

| 상태 | 목록 위치 | 문구 | 안전한 출구 |
|---|---|---|---|
| 만료됨 | 맨 위, 강조 배경 | 다시 연결하면 초안과 예약은 그대로 이어집니다 | 다시 연결 |
| 연결 해제됨 | 맨 위, 강조 배경 | 이 계정으로 예약된 발행은 실패로 처리됩니다 | 다시 연결 또는 다른 계정 |
| 서버 자격증명 미설정 | 원래 자리, 버튼 잠김 | 서버에 이 채널 개발자 앱 값이 아직 없습니다 | 운영자에게 문의 |
| 정상 | 원래 자리 | 무엇이 확인됐는지 한 줄 | 연결 확인 |

## 4. 콘텐츠 생성에서 게시까지

### 4.1 두 곳에서 시작하고 한 기록으로 남는다

v19의 원칙을 유지한다. Studio에서 시작하든 채널 화면에서 시작하든 기록은 하나이고
`OSMU에서 생성` 또는 `이 플랫폼에서 생성`은 출처 표시일 뿐이다.

### 4.2 채널 화면의 탭 (코드 순서 보존 + 2개 신설)

| 채널 | 탭 | 신설 표시 |
|---|---|---|
| Threads | Create · Queue · Calendar · Analytics · Growth · Popular · Settings | Create와 Calendar에만 |
| X · Instagram · Facebook · Bluesky · YouTube · TikTok | Create · Queue · Calendar · Analytics · Settings | Create와 Calendar에만 |

- 기존 Queue·Analytics·(Growth·Popular)·Settings의 **상대 순서를 바꾸지 않았다.** 앞에 Create를, Queue 뒤에 Calendar를 끼웠다.
- Create와 Calendar는 화면에서 `이번에 더함`으로 표시하고, 현재 제품이 그 일을 어디서 하는지 한 줄로 적는다.
  Create 옆에는 `현재 제품의 대기열에는 작성 칸이 없습니다`, Calendar 옆에는 `현재 일정은 전체 캘린더 한 곳입니다`.
- Threads의 Growth·Popular는 실제 내용을 담았다. Growth는 팔로워 추이와 가장 많이 늘어난 날,
  Popular는 이 계정이 올린 글의 반응 순이다. 외부에서 모은 남의 인기 글은 섞지 않는다.

### 4.3 생성 → 수정 → 승인 → 게시 흐름

| 단계 | 화면 | 이 화면에서 다음에 눌러야 하는 것 | 막힐 수 있는 지점과 출구 |
|---:|---|---|---|
| 1 | Create | 초안 저장 또는 검토 요청 | 브랜드 자료 미확인 → 자료 열기 |
| 2 | Create 또는 Studio | 문구 수정 후 다시 저장 | 채널 글자 제한 초과 → 그 채널 문구만 수정 |
| 3 | 승인 인박스 | 항목별 의견 남기고 승인 | 승인자 권한 없음 → 승인자에게 요청 |
| 4 | Create의 검토와 게시 | 지금 게시 또는 예약 | 준비 미달 → 그 채널 Settings |
| 5 | Queue와 Calendar | 상태 확인 | 예약 취소됨 → 초안으로 보존 |

승인 뒤 내용·계정·시간이 바뀌면 승인은 무효가 되고 다시 받는다. 승인 스냅샷과 현재 수정본이 어긋난 채로 게시되지 않는다.

## 5. 성과

- 성과는 별도 화면이 아니라 홈이다. 코드가 그렇게 합쳐져 있고 `/performance`는 홈으로 보내는 리다이렉트다.
- 채널 고유 지표는 그 채널 Analytics에, 전체 집계는 홈에 둔다. 서로 다른 단위를 하나로 더하지 않는다.
- **표본 부족 보류**: 게시 4건 이하 채널은 평균을 계산하지 않고 보류로 표시한다.
  화면에 그 이유를 적는다. 표본이 적을 때 나온 평균은 다음 판단을 잘못된 방향으로 끌고 간다.
- 값이 없는 항목은 0으로 세지 않는다. `처리 중 2 · 측정 가능 14/18`처럼 분모를 밝힌다.

## 10. 레드팀과 셀프심문

**까다로운 고객의 공격**: "탭에 `이번에 더함`이라고 써 있으면, 나는 그게 되는 기능인지 아닌지 헷갈린다.
파는 화면에 공사중 표지를 붙인 셈이다."
받아들인 수정: 표시를 지우지 않되 문구를 상태가 아니라 위치로 바꿨다. `아직 없음`이 아니라
`현재 제품의 대기열에는 작성 칸이 없습니다`처럼 지금 그 일을 어디서 하는지 알려준다. 고객은 막히지 않고 옮겨간다.
설계 승인 뒤 실제로 구현되면 이 표시는 제거 대상이고, 그 제거가 구현 완료의 증거가 된다.

**운영자의 공격**: "없는 화면 5개를 목록에 남겨두면 매번 눌러보고 실망한다. 그냥 지워라."
받아들이지 않은 이유: 지우면 기술설계가 무엇을 향하는지 잃는다. 대신 좌측 목록에서 눌러보기 전에
`아직 없음`이 보이므로 헛클릭이 한 번으로 끝난다.

**SOCRATIC_MARKER, 이 설계가 틀렸다면 가장 그럴듯한 이유**:
`무엇이 저장됐는지 읽기`가 고객이 진짜 원한 것이 아닐 수 있다는 점이다.
회장이 `볼 수도 있고`라고 말한 의도가 "내 키가 잘 들어갔는지 눈으로 확인하고 싶다"라면 이 카드로 충분하다.
그러나 "다른 도구에 그 키를 옮겨 쓰고 싶다"라면 이 설계는 요구를 못 채운다.
후자라면 필요한 것은 화면 노출이 아니라 별도 발급 경로이고, 그건 보안 결정이라 회장 합의 사항이다.
그래서 §3.2에 해석과 근거를 적어두고 회수 항목으로 올린다.

두 번째 흔들기: Threads Growth·Popular를 되돌린 판단이 틀렸을 수 있다.
코드가 그렇다는 것이 그 배치가 옳다는 뜻은 아니다. 다만 이번 지시는 발명 금지였으므로
현재 배치를 보존하는 쪽이 계약에 맞다. 배치 개선은 별도 안건으로 올려야 한다.

⛔ 회수 필요: `볼 수도 있고`의 의도가 화면 확인인지 다른 도구로의 반출인지. 후자면 발급 경로와 보안 경계를 회장이 정해야 한다.

⛔ 회수 필요: 한 콘텐츠 식별·쓰기 소유·게시 멱등은 API와 DB 계약을 건드리므로 기술설계 티키타카에서 회장과 합의해야 한다.

⛔ 회수 필요: Create·Calendar 신설을 이번 범위에 넣을지, 아니면 표시만 남기고 다음 스프린트로 미룰지.
