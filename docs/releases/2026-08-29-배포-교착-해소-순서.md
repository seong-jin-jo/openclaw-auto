# 배포 교착 해소와 회장이 누를 순서

## 한 줄

배포가 막힌 진짜 이유는 스키마가 위험해서가 아니라, 배포 검사가 앱이 멀쩡히 지원하는 상태를 거절했기 때문이다. 그 거절 한 줄을 걷어내고 대신 진짜 위험을 보는 검사를 늘렸다. 회장이 누를 순서는 네 번이다.

## 무엇이 왜 막혀 있었는지

세 번의 배포 실패는 서로 다른 사고가 아니라 하나의 순환이었다.

1. 배포 워크플로의 스키마 검사가 운영 DB 상태를 보고 멈춘다. 운영 DB는 두 장부가 서로 다른 단계에 있다. 생성 멱등 장부는 작업공간 기준 제약만 있고, 무료 몫 장부는 회원 기준 제약까지 있다. 이것을 검사가 "짝이 안 맞으니 사람이 손대야 한다"고 판정했다.
2. 그 짝을 맞추는 것은 승인형 DB 워크플로의 `expand-member` 단계다.
3. 그런데 `expand-member` 는 지금 떠 있는 앱 컨테이너에서 어떤 코드로 빌드됐는지를 나타내는 표식을 읽는다. 그 표식은 새 배포가 붙인다. 지금 떠 있는 것은 08-28 배포본이라 표식이 없다.

배포는 마이그레이션을 기다리고, 마이그레이션은 배포를 기다렸다. 첫 바퀴를 돌 방법이 없었다.

파고 보니 순환의 고리는 하나 더 있었다. 표식을 요구하지 않는 `expand-guard` 단계로 우회할 수 있어야 하는데, 위 1번의 "짝이 안 맞음" 판정이 그 단계까지 똑같이 막고 있었다. 로컬 재현에서 확인했다.

```
ERROR: mixed generation/quota schema fingerprint requires an explicit recovery: S1|S2
expand-guard exit=3
```

즉 뿌리는 하나다. 코드 리뷰가 `run-migrations.sh:123` 으로 이미 짚은 그 줄이다.

## 무엇을 고쳤는지

### 1. 배포 검사가 앱이 실제로 지원하는 상태를 말하게 했다

앱은 이 두 장부에 쓸 때 제약 이름을 지정하지 않는다. 충돌하면 그냥 넘어가고 다시 읽는다(`dashboard/src/lib/studio/generation/repository.ts`). 그래서 강제하는 물건이 작업공간 기준 제약이든, 둘 다든, 회원 기준 제약이든 동작이 같다. 두 장부가 서로 다른 단계에 있는 것은 이 절차가 장부별로 나눠 진행하기 때문에 생기는 정상 중간 상태이지, 앱이 못 버티는 상태가 아니다.

그래서 "짝이 안 맞으면 거절"을 "장부마다 지원 목록 안에 있으면 통과"로 바꿨다. 정의가 어긋난 상태는 계속 거절한다.

### 2. 대신 진짜 위험을 보는 검사를 늘렸다

원래 목적인 "준비 안 된 스키마에 앱이 붙어 데이터가 깨지는 것"은 그대로 막아야 한다. 그 목적을 지키는 것은 아래 세 가지이고 전부 그대로 두거나 새로 넣었다.

- 회원 전역 멱등과 무료 몫이 제약이나 방어 장치로 실제 강제되는가. 기존 검사, 유지.
- 회원 범위 중복이 실제로 0인가. 기존 검사, 유지.
- 앱이 읽고 쓰는 필수 표 21개가 존재하고, 작업공간 격리가 켜져 있고 강제돼 있고 정책이 붙어 있고, 앱 접속 역할이 격리를 우회하지 않는가. **새로 추가.** 코드 리뷰 `:433` 이 지적한 구멍이다.

바꾼 결과 배포 게이트는 느슨해진 것이 아니라 더 촘촘해졌다. 없어진 것은 데이터 안전과 무관한 대칭성 요구 하나뿐이다.

### 3. 상태를 볼 수 있는 읽기 전용 경로를 만들었다

운영 DB에 접속하지 않으면 다음 단계를 정할 수 없었다. 아무것도 바꾸지 않고 상태만 찍는 `audit` 단계를 승인형 워크플로에 넣었다. 이제 첫 단추는 관측이다.

### 4. 함께 고친 것

- 구형 DB에서 표가 없으면 검사가 그대로 죽던 문제. 이제 죽지 않고 없다고 보고한다. 리뷰 `:55`.
- `expand-member` 가 **항상** 실패하던 잠복 결함. 색인 정합 검사가 내부 자료형의 배열 시작 번호 차이 때문에 항상 어긋난 것으로 판정했다. 로컬에서 실측했다.
  ```
  ERROR:  member unique index definition drift requires manual recovery
  ```
  이것은 표식 문제와 별개다. 표식만 붙었어도 `expand-member` 는 실패했을 것이다. 같은 파일의 다른 검사와 같은 방식으로 통일해 고쳤다.
- 실패로 남은 장부 기록이 고쳐진 마이그레이션의 재시도를 영구히 막던 문제. 리뷰 `:415` 의 재진입 경로.

## 회장이 누를 순서

전부 GitHub Actions 화면에서 `Run workflow` 로 실행한다. 브랜치는 이 수정이 들어간 브랜치다.

**먼저 이 브랜치를 운영 브랜치에 병합해야 한다.** 병합 전에는 워크플로가 옛 코드를 체크아웃해 같은 자리에서 또 막힌다.

### 1단계. 상태 확인

- 워크플로: **OSMU approved DB migration**
- `phase`: **audit**
- 나머지 입력은 비운다.

이 단계는 DB를 바꾸지 않는다. 읽기만 한다.

성공하면 로그에 이런 모양이 보인다.

```
schema_fingerprint=S1|S2
duplicate_groups=0|0|0
compatibility_readiness=false|true
--- runtime schema ---
drafts ok
engagement_items ok
...
osmu_service ok
--- migration ledger ---
20260829_010_studio_generation_expand_contract applied expand
```

**여기서 확인할 것 세 가지.**

- `duplicate_groups` 가 `0|0|0` 인가. 아니면 멈추고 알려주십시오. 데이터에 손댈 일이 생긴 것이라 여기서 판단이 필요하다.
- `runtime schema` 줄이 전부 `ok` 인가. `missing-relation` 이나 `rls-` 로 끝나는 줄이 있으면 2단계 전에 알려주십시오.
- 장부에 `20260829_010_studio_generation_expand_contract` 가 `applied` 로 있는가. **없으면 2단계 전에 `phase: expand-fk` 를 먼저 한 번 돌려야 한다.** 그것도 실패하면 `phase: apply-legacy` 를 먼저 돌린다. 둘 다 표식을 요구하지 않는다.

### 2단계. 생성 장부에 회원 범위 방어 장치를 건다

- 워크플로: **OSMU approved DB migration**
- `phase`: **expand-guard**

이 단계는 표식을 요구하지 않는다. 그래서 배포보다 먼저 돌 수 있다. 여기가 교착을 푸는 지점이다.

성공 신호는 마지막 줄의 `schema_fingerprint=S1|S2` 와 오류 없는 종료다. 확실히 하려면 `phase: audit` 을 한 번 더 돌려 `compatibility_readiness` 가 **`true|true`** 로 바뀌었는지 본다. 이것이 3단계의 통과 조건이다.

### 3단계. 배포

- 워크플로: **Deploy openclaw (marketing VM)**
- `services`: 비운다.

성공 신호는 두 줄이다.

```
schema_fingerprint=S1|S2
compatibility_ready=true|true
runtime_schema=ok (22 checks)
OSMU DB fingerprint preflight 완료
```

그리고 맨 끝의 스모크 통과 줄. 이 배포가 새 컨테이너에 표식을 붙인다.

### 4단계. 스키마 확장 마무리

- 워크플로: **OSMU approved DB migration**
- `phase`: **expand-member**

3단계가 끝난 뒤에만 돌린다. 이제 표식이 있어 관측 단계가 통과한다.

성공 신호는 마지막 줄이 **`schema_fingerprint=S2|S2`** 로 바뀌는 것이다. 두 장부가 같은 단계로 맞춰졌다는 뜻이다.

여기까지가 이번 판이다. 그다음 단계인 `prepare-rollback` 과 `contract-generation` 은 이번에 누르지 않는다. 되돌림 장부가 걸린 별도 승인 절차다.

## 잘못되면 되돌리는 방법

각 단계가 무엇을 바꾸는지에 따라 되돌리는 값이 다르다.

- **1단계 audit**: 아무것도 바꾸지 않는다. 되돌릴 것이 없다.
- **2단계 expand-guard**: 표를 바꾸지 않고 방어 장치만 얹는다. 되돌리려면 **OSMU approved DB migration** 의 `phase: cleanup` 이 아니라, 그 방어 장치를 제거하는 별도 판단이 필요하다. 다만 이 장치는 중복 입력을 막기만 하고 기존 행을 건드리지 않으므로, 되돌릴 실익이 거의 없다. 문제가 보이면 되돌리기 전에 알려주십시오.
- **3단계 배포**: 배포 워크플로가 스스로 되돌린다. 새 기동이 실패하면 직전 컨테이너를 원래 이름으로 되살린다. 자료 저장소는 건드리지 않는다.
- **4단계 expand-member**: 이 단계는 제약을 **추가**만 한다. 기존 데이터를 지우거나 바꾸지 않는다. 만약 중복 때문에 실패하면 아무것도 적용되지 않은 채 멈춘다. 되돌리려면 `phase: rollback-generation` 이 있으나, 그것은 되돌림 장부를 만든 `contract-generation` 이후에 쓰는 것이다. 이번 판 범위에서 4단계가 실패하면 실패한 자리에서 멈춘 것이므로, 로그를 그대로 두고 알려주십시오.

어느 단계든 실패하면 **다음 단계로 넘어가지 마십시오.** 각 단계는 앞 단계의 성공을 전제로 한다.

## 셀프심문: 이 완화가 데이터를 위험하게 만드는 경우가 있는가

질문을 정확히 놓고 답한다. 없앤 것은 "두 장부가 같은 단계에 있어야 한다"는 요구다. 이것이 데이터를 지키고 있었을 경우가 있는가.

**있을 뻔한 경우 하나.** 두 장부가 어긋난 상태가 실은 앞선 마이그레이션이 중간에 죽어서 생긴 사고의 흔적이고, 그 사고가 데이터도 함께 망가뜨렸을 수 있다. 그렇다면 어긋남을 거절하는 것이 사고 탐지 역할을 한 셈이다.

**그러나 그 역할은 다른 검사가 더 정확하게 한다.** 어긋남 자체는 사고의 증거가 아니다. 이 절차는 장부별로 나눠 진행하도록 설계돼 있어서 어긋남이 정상 중간 상태로 반드시 발생한다. 사고의 실제 증거는 회원 범위 중복이 남아 있는가인데, 그것은 중복 감사가 직접 센다. 그 검사는 그대로 두었고 여전히 fail-closed 다.

**실측으로 확인했다.** 마이그레이션 검증 스크립트가 어긋난 상태(`S3|S2`)에서 서로 다른 작업공간의 동시 요청을 실제로 던져 회원 기준으로 한 건만 남는지 센다. 이번 수정 뒤에도 통과한다.

```
PASS 축이 어긋난 승인 상태에서도 배포 preflight 통과
PASS S3-generation-S2-quota generation cross-tenant race count=1
PASS S3-generation-S2-quota quota cross-tenant race count=1
```

**반대로 진짜 위험한 상태는 계속 막힌다.** 회원 범위 강제를 일부러 없앤 DB와, 작업공간 격리를 꺼 놓은 DB를 만들어 배포 검사에 넣어 보았다.

```
PASS 회원 범위 강제 없는 상태는 여전히 fail-closed
PASS RLS 미강제 상태는 배포 preflight 에서 차단
```

두 번째는 이번에 새로 생긴 방어다. 예전 검사는 격리가 꺼진 DB에 앱을 붙이는 것을 통과시켰다. 그쪽이 훨씬 위험했다.

결론. 이 완화로 데이터가 위험해지는 경우는 확인하지 못했고, 오히려 막지 못하던 위험 하나를 새로 막게 됐다.

## 검증 증거

로컬에서 운영과 같은 상태를 재현해 확인했다. 운영 DB에는 접속하지 않았고, 운영 워크플로도 실행하지 않았다.

| 확인한 것 | 결과 |
|---|---|
| 운영과 같은 `S1|S2` 상태 재현 뒤 옛 코드 실행 | `preflight` 와 `expand-guard` 둘 다 종료 코드 3. 교착 재현 |
| 새 코드로 `audit` | 종료 코드 0. 상태와 장부 출력 |
| 새 코드로 `expand-guard` 이후 `preflight` | `compatibility_ready=true|true`, `runtime_schema=ok (22 checks)`, 종료 코드 0 |
| 이어서 `expand-member` | `schema_fingerprint=S2|S2`, 종료 코드 0 |
| 필수 표 제거 뒤 `preflight` | `engagement_items missing-relation` 으로 차단 |
| 격리 강제 해제 뒤 `preflight` | `drafts rls-not-forced` 로 차단 |
| `dashboard/scripts/verify-generation-migration-matrix.sh` 전량 | 17개 사례 전부 PASS, 종료 코드 0 |
| `npx tsc --noEmit` | 종료 코드 0 |
| 워크플로 두 개 YAML 구문 | 통과 |

**미검증으로 남긴 것.**

- 운영 DB의 실제 상태는 직접 보지 못했다. 위 순서의 1단계 `audit` 이 그것을 보기 위한 단계다. 운영 장부에 `20260829_010` 이 없거나 필수 표가 비어 있으면 순서가 한 단계 늘어난다.
- 자체 호스팅 러너에서 도커 실행 경로가 도는 것은 확인하지 못했다. 기존 배포가 같은 경로를 쓰고 있으므로 새로 생긴 위험은 아니다.
- 운영 앱 컨테이너에 표식이 실제로 붙는지는 3단계 이후에만 확인 가능하다. 4단계가 그 확인을 겸한다.
