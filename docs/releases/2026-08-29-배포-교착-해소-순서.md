# 배포 교착 해소와 회장이 누를 순서

STAMP | line: osmu | 생성: 2026-08-29 KST | 개정: 2026-08-30 06:15 KST | model: claude-opus-5[1m] | agent: code-builder | 기반: 2026-08-29 운영 워크플로 실행 33273870691 / 33274470699 / 33274554394 / 33274615508 / 33274730816 의 실측 로그 | 고민: 게이트를 끄지 않고 교착만 푸는 지점이 어디인가.

## 개정 이유 (먼저 읽으십시오)

이 문서의 08-29 판은 **틀린 순서를 담고 있었다.** 그대로 누르면 두 번째 단추에서 막힌다. 운영에서 다섯 번 실행해 확인한 사실 두 가지 때문이다.

1. **2단계로 안내했던 `expand-guard` 는 운영에서 영구히 불가능하다.** 우리 Supabase 계정에는 그 단계가 만드는 전용 역할을 만들 권한이 없다.
   ```
   ERROR: permission denied to alter role
   DETAIL: Only roles with the SUPERUSER attribute may alter roles with the SUPERUSER attribute.
   ```
   이것은 재시도로 풀리는 종류가 아니다. 이 길은 순서에서 완전히 뺐다.
2. **`apply-legacy` 가 반드시 필요한데 08-29 판에는 조건부로만 적혀 있었다.** 운영 DB에 필수 표 하나가 없었고(`studio_generation_candidate_rejections missing-relation`), 그 상태로는 배포 검사가 통과하지 못한다. 08-29 판은 이것을 "없으면 돌려라" 정도로 적어 회장이 그냥 넘어가기 쉬웠다.

그리고 뿌리 원인 하나가 아직 살아 있었다. 08-29 판이 고쳤다고 적은 완화는 `main` 과 병합하는 과정에서 사라졌다. 이번 판에서 다시, 그리고 더 정확한 자리에 넣었다.

## 한 줄

배포가 막힌 진짜 이유는 스키마가 위험해서가 아니라, 배포 검사가 **자기가 만들어 낸 정상 중간 상태를 자기가 거절**했기 때문이다. 그 검사를 배포의 사전 조건에서 확장 단계의 사후 조건으로 옮겼다. 회장이 누를 순서는 네 번이다.

## 무엇이 왜 막혀 있었는지

세 번의 실패는 서로 다른 사고가 아니라 하나의 순환이었다.

1. 배포 preflight 가 `compatibility_ready` 를 `true|true` 로 요구했다. 운영은 `false|true` 다.
   ```
   ERROR: compatibility app requires member UNIQUE or enabled E1 guard for generation and quota; readiness=false|true
   ```
2. `true` 로 만드는 길은 둘뿐이다. `expand-guard` 는 위에 적은 권한 문제로 영구히 막혀 있다.
3. 남은 길 `expand-member` 는 지금 떠 있는 앱 컨테이너에서 어떤 코드로 빌드됐는지를 나타내는 표식을 읽는다. 그 표식은 새 배포가 붙인다. 지금 떠 있는 것은 08-28 22:15 배포본이라 표식이 없다.
   ```
   ##[error]running app commit label is not observable
   ```
4. 그 새 배포는 1번에 막힌다.

배포는 마이그레이션을 기다리고, 마이그레이션은 배포를 기다렸다. 첫 바퀴를 돌 방법이 없었다.

**그런데 그 `false|true` 상태 위에서 운영은 이틀 동안 멀쩡히 돌고 있다.** 즉 검사가 거절한 것은 "앱이 못 쓰는 상태"가 아니었다. 여기가 뿌리다.

## 무엇을 고쳤는지

### 배포가 요구할 것과 확장이 요구할 것을 갈라놓았다

`compatibility_ready = true|true` 는 **회원 전역 멱등이 이미 강제된 상태**를 요구한다. 그것은 `expand-member` 를 끝낸 뒤의 **목표 상태**이지, 배포의 전제가 아니다. 둘을 같은 자리에 묶어 둔 것이 교착의 설계 결함이었다.

배포가 실제로 요구하는 안전 불변식은 이것 하나다.

> 두 장부가 최소한 `(tenant_id, member_id, ...)` 범위에서 **유효한 UNIQUE 로 강제**되고 있고, 실제 중복이 **0** 이다.

앱의 읽기 경로가 정확히 그 범위이기 때문이다. `dashboard/src/lib/studio/generation/repository.ts` 의 조회는

```sql
WHERE tenant_id = :workspace AND member_id = :member AND operation = ... AND idempotency_key = ...
```

이다. 그래서 생성 장부가 S1(작업공간+회원 UNIQUE)일 때 앱은 자기 읽기 범위와 **완전히 일치**한다. 다른 회원이나 다른 작업공간의 응답이 새어 나오는 경로는 없다.

그래서 `assert_compatibility_ready` 를 배포 preflight 에서 떼어 `expand-member` 의 **사후 조건**으로 옮겼다. 배포 preflight 에는 위 불변식을 보는 `assert_deploy_compatible` 을 넣었다.

### 게이트를 끈 것이 아니라 옮긴 것이다

배포 preflight 에 남아 있는 fail-closed 검사는 그대로다. 하나도 빼지 않았다.

- 두 장부의 제약이 지원 목록(S1/S2/S3) 안에 있는가. 정의가 어긋난 상태(X)와 표 자체가 없는 상태(MISSING)는 계속 거절한다.
- 회원 범위 중복이 실제로 0인가.
- 앱이 읽고 쓰는 필수 표 21개가 존재하고, 작업공간 격리가 켜져 있고 강제돼 있고 `tenant_iso` 정책이 붙어 있는가.
- 앱 접속 역할 `osmu_service` 가 격리를 우회하지 않는가.

이 넷이 전부 살아 있음을 로컬에서 실제로 깨뜨려 보며 확인했다. 아래 검증 증거 표에 있다.

### 우회로는 만들지 않았다

`expand-member` 가 요구하는 앱 표식 검사는 **손대지 않았다.** 표식 없는 컨테이너로 그 단계를 돌리려 하면 지금도 막힌다. 배포가 먼저 돌면 표식이 붙고, 그때 자연히 통과한다. 상시 우회로를 두면 이 검사가 존재할 이유가 없어진다.

## 회장이 누를 순서

전부 GitHub Actions 화면에서 `Run workflow` 로 실행한다.

**먼저 이 수정이 `main` 에 병합돼 있어야 한다.** 병합 전에는 워크플로가 옛 코드를 체크아웃해 같은 자리에서 또 막힌다.

**08-29 판에 있던 `expand-guard` 단계는 누르지 마십시오.** 운영 권한으로 불가능하고, 실패해도 DB를 바꾸지 않지만 시간만 버린다.

### 1단계. 상태 확인

- 워크플로: **OSMU approved DB migration**
- `phase`: **audit**
- 나머지 입력은 비운다.

DB를 바꾸지 않는다. 읽기만 한다. 08-29 실행 33273870691 에서 나온 모양이 이것이다.

```
schema_fingerprint=S1|S2
duplicate_groups=0|0|0
compatibility_readiness=false|true
--- runtime schema ---
studio_generation_candidate_rejections missing-relation
... 나머지 ok
osmu_service ok
--- migration ledger ---
20260829_010_studio_generation_expand_contract applied expand
```

**여기서 확인할 것 두 가지.**

- `duplicate_groups` 가 `0|0|0` 인가. 아니면 멈추고 알려주십시오. 데이터에 손댈 일이 생긴 것이라 판단이 필요하다.
- `runtime schema` 에 `missing-relation` 이나 `rls-` 로 끝나는 줄이 있는가. 있으면 2단계가 그것을 채운다.

`compatibility_readiness` 가 `false|true` 인 것은 **정상이다.** 이제 배포를 막지 않는다.

### 2단계. 빠진 표를 채운다

- 워크플로: **OSMU approved DB migration**
- `phase`: **apply-legacy**

08-29 실행 33274470699 에서 이 단계가 성공했다. 앱 표식을 요구하지 않으므로 배포보다 먼저 돌 수 있다.

이 단계 뒤 **`phase: audit` 을 한 번 더 돌려** `runtime schema` 가 전부 `ok` 인지 확인한다. 하나라도 `ok` 가 아니면 3단계는 막힌다.

### 3단계. 배포

- 워크플로: **Deploy openclaw (marketing VM)**
- `services`: 비운다.

성공 신호는 이 네 줄이다.

```
schema_fingerprint=S1|S2
duplicate_groups=0|0|0
deploy_compatible=S1|S2 member_global_readiness=false|true
runtime_schema=ok (22 checks)
OSMU DB fingerprint preflight 완료
```

`member_global_readiness=false|true` 아래에 이런 안내 한 줄이 함께 찍힌다. 오류가 아니다.

```
note: member-global enforcement is still expanding (readiness=false|true). ...
```

그리고 맨 끝의 스모크 통과 줄. **이 배포가 새 컨테이너에 표식을 붙인다.** 4단계가 열리는 지점이다.

### 4단계. 스키마 확장 마무리

- 워크플로: **OSMU approved DB migration**
- `phase`: **expand-member**

3단계가 끝난 뒤에만 돌린다. 성공 신호는 마지막 두 줄이다.

```
compatibility_ready=true|true
schema_fingerprint=S2|S2
```

두 장부가 같은 단계로 맞춰졌고, 회원 전역 강제가 닫혔다는 뜻이다.

여기까지가 이번 판이다. 그다음 `prepare-rollback` 과 `contract-generation` 은 이번에 누르지 않는다. 되돌림 장부가 걸린 별도 승인 절차다.

### 회장이 내일 아침 콘텐츠를 만들려면 어디까지 필요한가

**3단계까지다.** 4단계는 데이터 안전을 한 칸 더 조이는 것이지 기능을 여는 것이 아니다. 3단계가 끝나면 새 코드가 운영에 올라가 있다. 4단계는 그날 중 아무 때나 눌러도 된다.

## 잘못되면 되돌리는 방법

- **1단계 audit**: 아무것도 바꾸지 않는다. 되돌릴 것이 없다.
- **2단계 apply-legacy**: 없는 표를 만들고 없는 칼럼을 더한다. 기존 데이터를 지우거나 바꾸지 않는다. 각 마이그레이션은 스키마 변경과 장부 기록을 한 거래로 묶어 돌므로, 중간에 실패하면 그 마이그레이션은 통째로 되돌아간 채 멈춘다.
- **3단계 배포**: 배포 워크플로가 스스로 되돌린다. 새 기동이 실패하면 직전 컨테이너를 원래 이름으로 되살린다. 자료 저장소는 건드리지 않는다.
- **4단계 expand-member**: 제약을 **추가**만 한다. 중복 때문에 실패하면 아무것도 적용되지 않은 채 멈춘다. 실패하면 로그를 그대로 두고 알려주십시오.

어느 단계든 실패하면 **다음 단계로 넘어가지 마십시오.** 각 단계는 앞 단계의 성공을 전제로 한다.

## 셀프심문 1. 이 완화로 데이터가 깨질 수 있는 경우가 실제로 있는가

질문을 정확히 놓는다. 없앤 것은 "배포 전에 회원 전역 강제가 이미 걸려 있어야 한다"는 요구다.

**S1 에서 아직 닫히지 않은 것은 정확히 무엇인가.** 한 회원이 **서로 다른 두 작업공간**에 걸쳐 같은 멱등 키를 쓰거나 무료 몫을 두 번 쓸 수 있다. 작업공간 안에서는 S1 의 UNIQUE 가 그대로 막는다.

**그것이 데이터 파손인가.** 아니다. 사업 규칙의 빈틈이다. 어떤 행도 덮어써지지 않고, 어떤 회원도 남의 응답을 보지 않는다. 앱의 조회가 작업공간+회원 범위이므로 S1 의 강제 범위와 정확히 같기 때문이다.

**오히려 짚어야 할 것은 반대 방향이다.** S3(회원 전역 UNIQUE)에서는 다른 작업공간의 행과 충돌할 수 있고, 그때 작업공간 범위 재조회가 빈손으로 돌아와 요청이 조용히 아무것도 하지 않는 경로가 있다(`repository.ts` 의 `created:false, requestHash:""`). 즉 **S1 이 지금 앱에게 더 정합적인 상태**다. 목표 상태로 가는 것이 옳지만, 그것을 배포의 전제로 삼을 이유는 없었다.

**이 빈틈은 이번에 생긴 것이 아니다.** 운영은 처음부터 그 상태였고 지금도 그 상태로 돌고 있다. 배포를 막는다고 닫히지 않는다. 닫는 것은 4단계다.

**진짜 위험은 계속 막힌다.** 필수 표 누락, 격리 강제 해제, 앱 역할의 격리 우회, 제약 정의 드리프트, 회원 범위 중복. 다섯 가지를 로컬에서 일부러 만들어 넣어 보았고 전부 배포가 차단됐다. 아래 표에 출력이 있다.

결론. 이 완화로 데이터가 깨지는 경우는 확인하지 못했다.

## 셀프심문 2. 회장이 새 순서대로 눌렀을 때 정말 끝까지 가는가

단계마다 "무엇에 막힐 수 있는가"를 하나씩 답한다.

- **1단계 audit** 은 읽기 전용이고 08-29 에 실제로 성공했다(33273870691). 막힐 이유가 없다.
- **2단계 apply-legacy** 도 08-29 에 실제로 성공했다(33274470699). 앱 표식을 요구하지 않는다.
- **3단계 배포**의 preflight 가 볼 것은 네 가지다. `S1|S2` 는 이제 통과한다(로컬 실측). `duplicate_groups` 는 운영 audit 이 `0|0|0` 으로 관측했다. `runtime_schema` 는 2단계가 채운다. `osmu_service` 는 운영 audit 이 `ok` 로 관측했다. 넷 다 근거가 있다.
- **4단계 expand-member** 가 요구하는 표식은 3단계가 붙인다. `dashboard/Dockerfile:21` 이 `org.opencontainers.image.revision` 라벨을 박고, `.github/workflows/deploy-marketing.yml:41` 이 그 값에 `GITHUB_SHA` 를 넣는다. 코드로 확인했다.

**남은 불확실 하나.** 4단계는 실행 중 컨테이너의 표식 커밋이 호환 기준 커밋 `9b72c05b` 의 후손인지도 본다. 3단계가 `main` 에서 배포되고 이 수정이 `main` 에 병합돼 있으면 성립한다. 병합 없이 이 브랜치로만 배포하면 이 검사에서 막힐 수 있다. 그래서 순서 맨 앞에 병합을 적었다.

**정직하게 남기는 것.** 운영 DB에는 접속하지 않았고 운영 워크플로도 실행하지 않았다. 3단계와 4단계의 실제 통과는 회장이 누른 뒤에만 확인된다.

## 검증 증거
