## 0. v22는 v21의 수선이다

v21의 화면·어휘·상태 3분류·정책 사실을 갈아엎지 않았다. 부모가 브라우저에서 직접 클릭해 재현한
결함 3건과, 그 3건을 쫓다가 발견한 같은 계열 결함 55건을 닫았다.

### 0.1 결함 3건과 그 하나의 뿌리

부모의 관찰은 셋이었지만 원인은 하나였다.

| 부모가 본 것 | v21 코드에서 실측한 원인 |
|---|---|
| 홈 체크리스트 `채널 1개 연결`이 아무 데도 가지 않는다 | 1단계가 Settings까지 데려다 놓지만, 거기 있는 `연결` 버튼에 전용 처리기가 없다 |
| 미연결 채널 화면에 연결 진입점이 없다 | 사유는 `statusReasonBlock`이 그리는데 그 블록에 행동이 없다 |
| 미연결인데 승인·지금 게시·예약이 활성이다 | `platformCreate`의 게시 패널이 채널 상태를 전혀 보지 않는다 |

세 줄의 공통 뿌리는 **`connect` 동작에 처리기가 없었다는 것**이다. v21의 모든 `연결` 버튼은
등록된 계약 목록의 마지막 갈래로 떨어져 `채널 연결 관리 · 동작을 기록했습니다`라는 접수증만
남기고 아무 화면도 열지 않았다. 연결이라는 제품의 첫 관문 자체가 없었다.

**부모의 관찰과 한 군데 다른 점을 정직하게 적는다.** 헤드리스 브라우저에서 `채널 1개 연결`을 누르면
화면은 Settings로 바뀌었다. 즉 "DOM이 전혀 안 바뀐다"는 아니었다. 다만 거기서 `연결`을 눌러도
아무 일이 없었으므로, 유저가 겪는 일은 부모가 말한 그대로 막다른 길이다. 원인 진단은 부모의 관찰이 옳았다.

### 0.2 왜 v21의 QA가 이걸 못 잡았나

v21은 `미등록 핸들러 0`을 검증했다. 그것은 "누르면 예외가 나지 않는가"였지 "누르면 무슨 일이
일어나는가"가 아니었다. v22는 검사를 바꿨다. **실제로 누르고, 누른 뒤 화면이 바뀌었는지를 본다.**

## 1. 결함 1 수선: 첫 행동이 도착지가 아니라 문으로 간다

### 1.1 시작 체크리스트 4단계가 각각 도달하는 곳

| 단계 | v21 | v22 | 왜 |
|---|---|---|---|
| 1 채널 1개 연결 | `/settings` 이동 (거기서 막힘) | **연결 화면을 바로 연다.** 지금 연결 가능한 첫 채널이 대상 | 신규 가입자의 첫 행동에 한 번의 추가 탐색도 물리지 않는다 |
| 2 브랜드 위키 작성 | `/studio` 이동 (편집기는 그 화면에 없음) | 브랜드 자료 단계를 직접 연다 | Studio에 내려놓아도 자료 편집기가 없으면 같은 막다른 길이다 |
| 3 콘텐츠 1개 발행 | `/channels/threads` 고정 | **연결된 채널 중 첫 하나**의 Create 탭 | Threads를 안 쓰는 사람은 못 쓰는 채널로 끌려간다 |
| 4 성과 확인 | `/` 이동 | `/` 이동 + 성과를 봤다는 사실을 기록 | 4단계 완료 조건이 이 행동이기 때문이다 |

### 1.2 완료 표시는 방문이 아니라 사건으로만 켜진다

v21의 완료 여부는 고정값이었다. 화면을 한 번도 안 쓴 사람에게도 2/4가 켜져 있었다.
v22는 실제 사건에만 반응한다.

| 단계 | 켜지는 조건 |
|---|---|
| 1 | 연결된 채널이 1개 이상 |
| 2 | 브랜드 자료의 검토 요청이 통과된 버전이 있음 |
| 3 | 게시가 제공자 응답으로 확인됨 |
| 4 | 성과 화면을 실제로 열어봄 |

연결을 끝내고 홈으로 돌아오면 그 자리에서 1/4이 된다. 화면이 유저의 행동을 따라간다.
이것은 근거 있는 규칙이다. 진행 표시를 방문만으로 채우면 그 표시는 거짓말이 된다
(원요구 감사 H02 "endowed progress must never mark setup steps complete from mere route visit").

### 1.3 다 끝낸 사람에게는 체크리스트를 치운다

4/4가 되면 같은 체크리스트를 계속 보여주지 않는다. 끝난 일을 다시 시키는 화면이 되기 때문이다.
대신 `첫 흐름을 끝까지 돌렸습니다`와 다음 행동 하나(아직 연결 안 한 채널 1개)를 준다.

## 2. 결함 2 수선: 연결 통로 전체

### 2.1 연결이 시작되는 자리 (v22에서 신설·수선한 진입점)

| 자리 | v21 | v22 |
|---|---|---|
| 홈 시작 체크리스트 1단계 | 이동만 | 연결 화면을 연다 |
| Settings 채널 목록의 각 미연결 행 | 접수증만 | `연결 시작` |
| Settings 계정 목록의 만료·미연결 행 | 접수증만 | `다시 연결` / `연결 시작` |
| 채널 상세 `지금 이 채널 상태` 블록 | 없음 | `지금 하실 일` 카드 + `연결 시작` |
| 채널 상세 게시 패널 | 없음 | 같은 버튼을 짧게 반복 |
| 채널 Settings 탭 하단 | 접수증만 | `연결 시작` / `계정 바꾸기` |
| Settings 계정 저장 내용 빈 상태 | 남의 계정이 보였음 | 빈 상태 + `연결 시작` |

### 2.2 연결 화면의 3단계

```
시작  →  제공자 승인(또는 값 입력)  →  연결 완료
                    ↓ 실패
              실패 사유 + 보존 안내 + 재시도
```

**시작.** 무엇을 허용하게 되는지를 먼저 보여준다. 채널마다 4줄로 고정했다.
예: Instagram은 `이 계정으로 글과 사진을 올립니다 / 올린 글의 반응 숫자를 읽습니다 /
프로페셔널 계정 정보를 읽습니다 / 비밀번호는 받지 않습니다`. 필요한 계정 종류가 따로 있으면
그 사실도 여기서 미리 말한다. 승인 화면까지 갔다가 계정 종류 때문에 돌아오는 일을 줄인다.

이것은 의도된 마찰이다. 권한을 넘기는 지점에서 과정을 건너뛰면 신뢰를 만들 기회를 잃는다.

**제공자 승인.** 우리가 그릴 수 없는 화면이므로 대체 표현임을 화면 안에서 밝힌다.
회색 바에 `Threads 승인 화면 · 우리 제품이 아니라 Threads가 보여주는 화면입니다`를 두고,
그 아래 안내에 `이 프로토타입은 실제 화면을 대신 그린 것입니다. 실제 연결은 개발 단계에서 확인합니다`를
붙였다. 없는 것을 있는 것처럼 그리지 않는다.

**값 직접 입력(Bluesky·Telegram·Discord).** 이 세 채널은 공식 로그인 화면이 없다.
그래서 이 채널만 값을 직접 받고, 그 사실과 이유를 화면에 적는다.
Bluesky는 `로그인 비밀번호가 아닙니다`를 입력 칸 옆에 둔다. 근거는
`wiki/reference/channel-status.md`의 수동 입력 유지 채널 목록이다.

**연결 완료.** 무엇이 저장됐는지를 5줄로 읽어준다. 연결된 계정, 계정 식별자 끝자리, 연결 방식,
다시 확인이 필요한 시점, 저장 형태. 값 자체는 어느 화면에도 표시하지 않는다는 문장을 함께 둔다.
그리고 다음 행동을 준다. `이 채널에서 초안 만들기` / `다른 채널도 연결` / `닫기`.

### 2.3 연결 실패 5종 (만들지 않고 코드가 실제로 분류하는 것만)

`lib/oauth-errors.ts`가 실제로 분류하는 범주만 화면에 올렸다.
그 파일의 마지막 갈래는 분류되지 않은 제공자 원문을 그대로 노출하지 않고
일반 문구로 바꾼다. 화면도 같은 규칙을 따른다.

| 사유 | 화면 문구 | 다음 행동 | 사유의 주인 |
|---|---|---|---|
| 승인 화면에서 취소함 | 저장된 것은 없고 만들던 초안도 그대로 있습니다 | 다시 시도 | 고객 |
| 계정 종류가 맞지 않음 | 이 계정으로는 연결할 수 없습니다 | 계정 바꾸는 방법을 함께 표시 후 다시 시도 | 고객 |
| 앱 권한 부족 | 이 계정이 개발자·테스터·관리자로 등록돼 있어야 합니다 | 운영자에게 등록 요청 | 우리 |
| 서버에 앱 값이 없음 | 고객이 하실 일이 아닙니다 | 운영자에게 알리기 | 우리 |
| 일시적 오류 | 다시 시도해 주세요. 계속되면 관리자에게 | 문의번호 `req_8f31c2`와 함께 재시도 | 우리 |

모든 실패 화면에 같은 문장을 고정으로 둔다.
**`만들던 초안과 예약은 그대로 있습니다. 연결 실패로 잃은 것은 없습니다.`**
손실회피는 이 지점에서 가장 강하게 작동한다. 무엇을 잃었는지 모르면 다시 시도하지 않는다.

## 3. 결함 3 수선: 반드시 실패할 버튼을 지우고 그 자리에 지금 가능한 것을 놓는다

### 3.1 두 가지 방법 중 무엇을 골랐나

막는 방법은 둘이었다.

1. 버튼을 그 이름 그대로 두고 비활성으로 막는다.
2. 그 자리에 지금 실제로 가능한 행동을 놓는다.

v21이 `준비 상황 보기` 비활성 버튼을 스스로 걷어내며 1번은 나쁘다고 판정했다.
하고 싶은 일을 이름으로 걸어놓고 막는 것은 신뢰를 깎는다. 그래서 v22는 2번을 골랐다.

### 3.2 미연결 채널의 게시 패널

패널 제목이 `검토와 게시`에서 `게시는 아직 열려 있지 않습니다`로 바뀐다.
그 안에 네 개의 행이 남는다. 검토 요청 / 승인 / 지금 게시 / 예약. 각 행에는
`연결 후`라는 표시와 `연결이 끝나면 이 자리에 버튼으로 나타납니다`가 붙는다.
버튼이 아니라 예고다. 무엇이 생길지는 알려주되 지금 누를 수는 없다.

그 아래 `지금 하실 일: 연결` 버튼이 놓인다.

### 3.3 초안 만들기는 계속 열어 둔다

연결 없이도 초안은 만들 수 있어야 한다. 잃는 것이 없어야 기다릴 수 있기 때문이다.
그래서 `이 플랫폼에서 만들기`와 `연결 없이 초안만 저장`은 미연결에서도 활성이다.
오픈 준비중 채널에서는 `먼저 초안만 만들어 두기`가 주 버튼이 되고,
`열리는 즉시 그대로 게시됩니다`를 함께 적는다.

### 3.4 게시 성공 판정을 경로 문자열에서 연결 상태로 바꿨다

v21은 주소가 `/channels/threads`인지만 보고 성공을 그렸다. 연결을 끊어도 성공했다.
v22는 지금 그 채널이 실제로 연결돼 있는지를 본다. 이것도 false-success 계열이었다.

## 4. 여정 A · 신규 회원 (15단계, 실브라우저 통과)

각 단계 끝의 괄호는 증거 스크린샷 파일명이다.

| # | 단계 | 화면에서 다음에 누를 것 | 증거 |
|---:|---|---|---|
| 1 | 가입 직후 빈 상태. 연결 0개, 체크리스트 0/4 | `Threads 연결 시작` | `01-A01` |
| 2 | 1단계 클릭 → 연결 화면 시작 | `Threads 승인 화면 열기` / `나중에 하기` | `02-A02` |
| 3 | 제공자 승인 화면(대체 표현) | `승인하고 돌아오기` / `취소` | `03-A03` |
| 4 | 연결 실패와 보존 안내 | `다시 시도` / `다른 실패 사유 보기` | `04-A04` |
| 5 | 재시도 후 연결 완료, 저장 내용 5줄 | `Threads에서 초안 만들기` / `다른 채널도 연결` | `05-A05` |
| 6 | 홈 복귀. 체크리스트가 1/4로 바뀜 | `브랜드 위키 작성 시작하기` | `06-A06` |
| 7 | 브랜드 자료 작성 | `초안 저장` / `검토 요청` | `07-A07` |
| 8 | 검토 통과. 체크리스트 2/4 | `콘텐츠 1개 발행 시작하기` | `08-A08` |
| 9 | 연결한 채널에서 초안 생성 | `승인` / `지금 게시` / `예약` | `09-A09` |
| 10 | 채널별 다시 쓰기 | `이 문구 저장` / `되돌리기` | `10-A10` |
| 11 | 승인 | `지금 게시` | `11-A11` |
| 12 | 게시. 제공자 응답으로 결과 확인 | `게시 결과 열기` / `이 채널 성과 보기` | `12-A12` |
| 13 | 게시된 글 주소 열기 | `외부 결과 원문` / `닫기` | `13-A13` |
| 14 | 성과 확인 | `전체 성과 보기` | `14-A14` |
| 15 | 4/4 완료. 다음 행동 제안 | `Instagram 연결 시작` / `성과 다시 보기` | `15-A15` |

**15단계 전부에서 다음에 누를 것이 화면에 있었다.** 이것을 자동으로 검사한다.
어떤 단계든 눌러야 할 버튼이 0개면 그 단계는 실패로 처리된다.

### 4.1 12단계의 정직성 경계

게시 결과에는 주소를 보여주지만, 반응 숫자는 그 자리에서 만들지 않는다.
`반응 숫자는 제공자가 집계하는 데 시간이 걸립니다. 지금은 게시된 것만 확인되고,
성과는 확인되는 대로 채워집니다.` 게시 확인과 성과 확인은 다른 사건이다.

## 5. 여정 B · 관리자 (10단계, 실브라우저 통과)

| # | 단계 | 무엇을 보고 무엇을 하나 | 증거 |
|---:|---|---|---|
| 1 | 운영자 화면 진입 | 운영 요약 6개 숫자. 실패 7건의 주인을 찾으러 가는 버튼 | `16-B01` |
| 2 | 고객 목록 | 고객 4곳. 확인 필요 2곳이 위로 | `17-B02` |
| 3 | 문제 고객 상세 | 요금제·가입·최근 사용·연결 계정·발행/실패. 조치 버튼 | `18-B03` |
| 4 | 앱 자격증명 등록 | X의 Client ID·Secret 입력 폼 | `19-B04` |
| 5 | 저장 → 채널 오픈 | X가 `준비 완료`로. 고객 화면 영향이 그 행에 적힘 | `20-B05` |
| 6 | 한도와 정책 | 앱 전체 공유 채널과 계정별 채널 | `21-B06` |
| 7 | 사용량 | 수집값과 설계 목표를 섞지 않음 | `22-B07` |
| 8 | 문제 고객 일시 정지 | 예약과 자동화가 멈춤 | `23-B08` |
| 9 | 재개 | 고객 작업 가능 상태로 | `24-B09` |
| 10 | 고객 화면 확인 | X가 `오픈 준비중`에서 `연결 시작`으로 바뀜 | `25-B10` |

### 5.1 이 여정의 핵심은 10단계다

운영자가 값을 넣으면 고객 화면이 바뀐다. 이 연결이 v21에는 없었다.
`오픈 준비중`이 무엇 때문에 걸려 있고 누가 무엇을 하면 풀리는지가
두 화면 사이에서 실제로 이어져야 그 상태 이름이 의미를 갖는다.

### 5.2 오픈 준비중의 원인은 둘이고 조치가 다르다

| 원인 | 채널 | 운영자가 값을 넣으면 |
|---|---|---|
| 서버에 앱 값이 없음 | X | 그 자리에서 열린다 |
| 플랫폼 심사를 못 넘음 | YouTube, TikTok | **열리지 않는다.** 심사 신청이 따로 필요하다 |

이 차이를 화면에 명시했다. 섞어 두면 운영자가 값을 넣고 열렸다고 착각한다.
`심사가 원인인 채널은 값을 넣어도 열리지 않습니다. YouTube와 TikTok이 그렇습니다.`

### 5.3 운영자가 할 수 없는 일도 적는다

바른치과의 실패 5건은 고객의 연결 만료가 원인이다. 운영자는 대신 연결할 수 없다.
그래서 조치는 `고객에게 안내 보내기` 하나뿐이고, 그 사실을 사유 문장에 적었다.
지원 모드에서도 운영자는 고객 대신 게시할 수 없다는 문장을 상세 하단에 고정으로 둔다.

### 9.3 이 여정에서 새로 드러난 결함과 그 처리

8단계에서 `일시 정지`가 한 화면에 두 개 있어 자동 조작이 대상을 특정하지 못했다.
사람이 눌러도 같은 문제였다. 고객 상세의 정지와 아래 작업 공간 패널의 정지가 같은 상태를 건드리는데
화면은 어느 고객이 멈추는지 말하지 않았다. 게다가 아래 패널은 어떤 고객을 골라도
모노스튜디오 값을 그대로 보여줘서, 바른치과를 고른 상태에서 모노스튜디오 숫자를 읽게 했다.

수선 2건.
- 조치는 상세 한 곳으로 모으고 버튼에 대상 이름을 넣었다. `바른치과 일시 정지`. 조치 위에 "아래 조치는 모두 바른치과에게만 적용됩니다" 한 줄을 둔다.
- 작업 공간 패널은 모노스튜디오를 고른 경우에만 펴고, 그때도 읽기 전용으로 둔다. 다른 고객에서는 "선택한 고객의 상세 카드는 아직 옮기지 않았습니다"로 적는다. 숫자를 돌려쓰지 않는다.

### 9.4 연결 흐름 갱신: 실패하기 전에 막는 두 문장

경쟁 3사 조사에서 연결 실패의 실제 1·2순위가 나왔다.
브라우저에 로그인돼 있던 다른 계정이 연결되는 것, 승인 화면에서 권한을 일부만 켜는 것이다.
세 곳 다 이 경고를 도움말 문서에만 두고 흐름 안에 두지 않아서, 사용자는 실패한 뒤에야 알게 된다.
우리도 같았다. 연결 시작(1단계) 화면에 확인 2건을 한 블록으로 넣었다.
공식 로그인 방식에만 붙이고, 값을 직접 받는 채널(Bluesky·Telegram·Discord)에는 해당이 없어 붙이지 않는다.

### 9.5 연결 실패 5종에서 6종으로

`dashboard/src/lib/oauth-errors.ts`와 다시 대조했다.
코드는 "테스터 초대 미수락"과 "개발자 역할 없음"을 다른 분기로 잡는데 프로토타입은 하나로 묶고 있었다.
초대 수락은 고객이 직접 눌러야 하고 역할 추가는 운영자가 한다. 묶으면 고객에게 틀린 다음 행동을 준다.

| 사유 | 고치는 사람 | 화면이 주는 다음 행동 |
|---|---|---|
| 승인 화면에서 취소함 | 고객 | 다시 시도 (있던 자리에서 이어짐) |
| 계정 종류가 맞지 않음 | 고객 | 계정 종류 바꾸는 방법 표시 후 다시 시도 |
| 앱 권한 부족 | 운영자 | 운영자에게 등록 요청 |
| **테스터 초대를 아직 수락하지 않음 (신설)** | **고객** | **초대 메일에서 수락 후 다시 시도. 운영자가 대신 못 누름을 명시** |
| 서버에 앱 값이 없음 | 운영자 | 운영자에게 알리기 |
| 일시적 오류 | 제품 | 문의번호와 함께 다시 시도 |

`redirect_uri` 불일치는 코드에 있지만 운영자 사유라 고객 화면 분류로 올리지 않았다.
실브라우저에서 6종이 순환 확인됐다: account_type → role → invite → credential → temporary → cancelled.

### 9.6 막다른 길 재점검

역할 전환 추가로 이전에 없던 경로가 하나 닫혔다.
v22까지 운영자 콘솔은 들어가는 문도 나오는 문도 없었다(검수 바를 켠 경우 제외).
지금은 양쪽 상단 같은 자리에 문이 있고, 운영자 상단바는 sticky라 표가 길어도 사라지지 않는다.
역할을 바꿀 때 상대 역할의 오버레이 8종을 모두 닫아 고객 모달이 운영자 화면 위에 남는 경로도 없앴다.

**현재 dead-end 0.**
