## 1. 한 줄 결론

기존 v24의 셸, Studio 7채널 미리보기, 다계정 데이터 구조, 채널별 capability 탭과 현재 운영자 콘솔을 보존하면서, 선택 피로를 줄이는 제작 흐름과 1인 운영자가 장애·과금·고객 막힘·지원 요청을 먼저 발견해 복구하는 운영 흐름을 하나의 막힘 없는 체계로 연결한다. v9.3은 여기에 테넌트별 발행 모드, 품질 게이트 반려 무과금, 연락처 기반 가입 전 체험, 사용자 소유 데이터 내보내기, 내부 테스트 테넌트 구분을 추가한다.

v9.3의 34장은 제품구조 결정서 §9.5의 회장 확정 5건을 최종값으로 사용한다. 앞선 장의 `결정 대기`, `후보`, `목표 UX` 문구가 34장과 충돌하면 34장이 우선한다. API 계약, DB 스키마, 보관 기간, 체험 크레딧 수량과 만료값은 이 문서에서 확정하지 않는다.

## 3. 설계 범위와 정본

### 3.1 이번 문서가 정하는 것

- 사용자가 어떤 화면을 어떤 순서로 만나는지
- 각 화면에서 보는 정보, 선택, 추천, 근거, 다음 행동
- happy, edge, empty, error, loading 상태와 복구 경로
- 390과 1024 뷰포트에서의 주축, 열수, 정보 우선순위
- 데이터량 0, 정상, 과다에서의 표시 규칙
- 기존 기능을 유지하면서 v9에서 추가할 UX 차이

### 3.2 이번 문서가 정하지 않는 것

- OAuth API 파라미터와 콜백 저장 방식
- 크레딧 원장 및 환불 트랜잭션
- 채널 정책 판정 API
- 성과 데이터의 통계적 인과 모델
- 실제 숫자 견적을 만드는 Studio 계약
- 프로토타입 픽셀과 최종 카피

위 항목은 이 흐름을 승인한 뒤 기술설계에서 확정한다. 이 문서에 표시된 데이터 필드는 사용자에게 필요한 정보 계약이며 API나 DB를 미리 확정하는 선언이 아니다.

## 6. 흐름 원칙과 관심사 경계

### 6.1 선택 피로 감소 규칙

모든 질문 화면은 다음 순서를 지킨다.

1. 질문의 답 후보를 먼저 보여준다.
2. 추천 후보에 `추천` 배지와 짧은 이유를 붙인다.
3. 근거는 `우리 실험 로그`, `공개 사례`, `가설` 중 하나로 표시한다.
4. 추천과 사용자의 기존 선택이 충돌하면 조용히 덮지 않고 충돌 이유를 말한다.
5. 자유 입력은 `직접 입력` 보조 행동으로만 둔다.
6. 선택하지 않으면 다음으로 갈 수 없는 단계는 이유와 선택 수를 표시한다.
7. 선택 뒤에는 언제든 이전 단계로 돌아갈 수 있고, 바뀌는 견적과 파생물을 미리 경고한다.

근거: Hick의 법칙에 따라 한 화면의 주요 선택 수를 제한하고, Nielsen의 인지보다 재인을 우선하며, Fogg 모델에 따라 능력이 낮은 첫 사용자는 한 번에 하나의 명확한 행동만 요구한다.

### 6.2 생성과 편집의 두 모드

| 구분 | 생성 모드 | 편집 모드 |
|---|---|---|
| 입력 | 업계, 목적, 사례, 스타일, 제작 방식, A/B/C | 현재 결과물과 수정 지시 |
| 핵심 신호 | A/B/C 중 강제 선택 | 자연어 수정 지시와 수정 범위 확인 |
| 결과 | 새 마스터 v1 | 원본을 보존한 새 revision |
| 크레딧 | 생성 전 범위 표시 | 자막, 컷, 오버레이 등 허용 범위는 `추가 크레딧 0` 표시 |
| 되돌리기 | 이전 선택으로 돌아가 재견적 | 이전 revision으로 언제든 복원 |

`추가 크레딧 0`은 서버 렌더 비용이 없다는 뜻이 아니다. 사용자 과금만 추가하지 않는다는 뜻으로 제한한다.

### 6.3 관심사 분리 3기준

| 질문 | 소유 화면과 서비스 |
|---|---|
| 채널 자격증명이 필요한가 | OpenClaw의 연결, 계정, 예약, 발행 화면 |
| 창작 정보를 읽거나 쓰는가 | Studio의 질문, 생성, 편집, 캡션, 해시태그 화면 |
| 미디어 바이트를 만지는가 | Studio의 생성, 변환, 편집, 파생물 화면 |

OpenClaw는 채널 제한과 계정, 시각, 발행 상태를 Studio 요청에 제약으로 전달한다. Studio는 플랫폼 계정과 토큰을 알지 않는다. Studio가 만든 마스터와 창작 텍스트를 OpenClaw가 받아 정확한 계정으로 발행한다.

### 6.4 마스터와 채널 파생 원칙

- 결과물 하나를 `마스터`로 고정한다.
- 비율, 길이, 안전영역, 캡션, 해시태그는 채널 파생으로 저장한다.
- 파생물 편집은 마스터를 덮어쓰지 않는다.
- 마스터를 바꾸면 영향받는 파생물 수를 먼저 보여주고 재생성 여부를 묻는다.
- 기존 소재 재사용 범위의 파생은 추가 크레딧 0 후보지만, 소재 재생성은 별도 견적이다.
- 캡션과 해시태그는 Studio가 만들고, OpenClaw는 채널 한도와 발행 가능 여부를 전달한다.

## 8. 공통 화면 계약

### 8.1 선택형 질문 화면

모든 C-01부터 C-05 화면은 다음 슬롯을 같은 순서로 쓴다.

1. 현재 단계와 전체 8단계 중 위치
2. 답을 먼저 제시하는 한 문장
3. 3개에서 5개의 선택 카드
4. 추천 카드의 이유와 근거 유형
5. 선택 충돌 안내
6. `직접 입력` 보조 행동
7. 이전, 다음 CTA

선택 카드에는 라벨, 한 줄 결과, 추천 여부, 근거, 비용 영향, 시간 영향 중 해당 값을 담는다. 값이 아직 계산되지 않았으면 임의 숫자를 쓰지 않고 `견적 계산 중`으로 표시하며 선택과 다음 CTA를 잠시 비활성화한다.

### 10.1 Happy 경로

### 10.2 추가 크레딧 표시 규칙

- 자막 크기, 폰트, 색, 위치, 자막 문구 수정은 내레이션을 바꾸지 않으면 `추가 크레딧 0`.
- 전환과 효과, 컷 순서, 컷 길이, 컷 삭제, 오버레이, 비율과 크롭은 기존 소재 재사용 범위에서 `추가 크레딧 0`.
- 내레이션 내용 변경이나 새 소재 생성이 필요하면 E-02에서 새 비용 범위를 먼저 보여주고 확인을 받는다.
- `추가 크레딧 0` 옆 보조 설명은 `기존 결과물을 다시 편집합니다. 원본은 유지됩니다.`로 통일한다.

## 11. 채널 연결과 계정 전환 흐름

### 11.1 해결해야 하는 실측 결함

브라우저에 다른 소셜 계정 세션이 있으면 그 계정으로 인증이 진행되고, 서비스 안에서 로그아웃하거나 계정을 바꾸지 못했다. 다계정 운영자에게 `연결 성공`은 충분하지 않다. `어느 계정이 돌아왔는지 확인했고 의도한 계정인지 승인했다`까지가 성공이다.

서비스는 외부 제공자의 쿠키와 로그인 세션을 강제로 지울 수 없다. 따라서 제공자가 공식 계정 선택기를 지원하면 사용하고, 지원하지 않으면 연결 전 세션 점검과 연결 뒤 실제 계정 확인을 결합한다.

### 11.2 Happy 경로

`A-01 채널 상태 센터` -> `A-02 다른 계정 추가` -> `A-03 외부 세션 확인` -> `A-04 OAuth` -> `A-05 돌아온 계정 확인` -> `A-07 연결 계정 관리`

| 화면 | 사용자가 보는 것 | 선택과 추천 | 안전장치 |
|---|---|---|---|
| A-01 | 플랫폼별 연결 계정 수, 기본 계정, 만료, 권한, 마지막 확인 | 복수 계정 운영자는 `다른 계정 추가` 추천 | 계정명과 외부 식별자 끝자리로 구분. 토큰 표시 금지 |
| A-02 | `기존 계정 사용`, `다른 계정 추가`, `만료 계정 재연결` | 새 브랜드 계정이면 `다른 계정 추가` 추천. 이유 표시 | 추가와 교체를 같은 버튼으로 표현하지 않음 |
| A-03 | 브라우저에서 현재 로그인된 제공자 세션을 서비스가 확정할 수 없다는 설명 | 제공자 계정 센터 확인, 비공개 창 사용, Google 공식 선택기 중 가능한 옵션 | `서비스에서 로그아웃`처럼 통제할 수 없는 약속 금지 |
| A-04 | 제공자 공식 화면 | 필요한 최소 권한 승인 | 돌아올 위치와 취소 시 보존 항목을 출발 전에 안내 |
| A-05 | 돌아온 실제 계정의 프로필명, 사용자명, 외부 식별자 일부, 권한 | `이 계정을 추가` 또는 `다른 계정으로 다시 연결` | 사용자 확인 전 기본 계정 변경 금지 |
| A-07 | 플랫폼별 모든 계정, 기본 배지, 상태, 예약 영향 | 향후 기본 계정 변경과 특정 작업 계정 선택을 분리 | 기존 예약은 지정된 계정을 유지. 계정 삭제는 영향 건수 확인 뒤 별도 승인 |

### 11.3 제공자별 계정 전환 규칙

| 제공자 능력 | 연결 방식 | 화면 규칙 |
|---|---|---|
| 공식 계정 선택 지원 | 계정 선택 요청을 사용 | A-03에서 `계정 선택 창이 열립니다` 표시. 현재 확인된 공식 근거는 Google 계열 |
| 선택기 없이 현재 세션을 재사용할 수 있음 | 제공자 계정 센터 또는 비공개 창 안내 | A-03에 현재 계정 점검 체크리스트. 복귀 뒤 A-05 확인 필수 |
| 여러 자산을 한 사용자 계정이 관리 | OAuth 뒤 실제 페이지나 비즈니스 자산 선택 | 사용자 계정과 발행 자산을 두 단계로 구분 |
| 제공자 상태 불명 | 자동 전환을 시도하지 않음 | A-03에 불명 상태와 수동 확인 경로 표시 |

### 11.4 잘못된 계정이 돌아온 경우

`A-04` -> `A-05 의도한 계정 아님` -> `A-06 후보 연결 보류` -> `A-03 세션 변경 안내` -> `A-04 재인증`

A-06 규칙:

- 새 후보는 활성 또는 기본 계정으로 확정하지 않는다.
- 기존 기본 계정과 예약, 초안은 그대로 둔다.
- `후보 폐기`, `제공자 계정 바꾸기`, `비공개 창에서 다시 연결`, `지금은 그만두기`를 제공한다.
- 사용자가 그만두면 A-01로 돌아가며 미완료 연결은 `확인 필요`로 남기지 않고 폐기한다.
- 후보 토큰을 언제 저장하고 폐기할지는 기술설계에서 보안 검토가 필요하다.

## 12. 탭 일관 규칙

### 12.1 공통 기본 탭과 순서

콘텐츠 채널은 다음 기본 순서를 유지한다.

1. Queue
2. Analytics
3. Growth
4. Popular
5. Settings

Editor가 구조적으로 필요한 채널은 Queue 다음에 삽입한다. 따라서 Instagram은 `Queue, Editor, Analytics, Growth, Popular, Settings` 순서다. 기존 v24와 `channel-capabilities.ts`의 순서를 계승하며 새 정보구조를 만들지 않는다.

### 12.2 숨김과 비활성 규칙

| capability 상태 | 표현 | 예 |
|---|---|---|
| 구조적으로 불가능 | 탭 숨김 | 메시징 채널에서 공개 인기 콘텐츠나 성장 분석이 성립하지 않는 경우 |
| 개념상 가능하지만 미구현 | 위치를 유지하고 비활성, `연동 예정` 이유 표시 | 표준 텍스트 채널의 Growth와 Popular |
| 사용 가능하지만 데이터 0 | 탭 활성, 내부 empty state | Analytics에 아직 발행 데이터가 없음 |
| 일시 오류 | 탭 활성, 내부 repair state | 토큰 만료나 분석 조회 실패 |
| 권한에 따라 사용 불가 | 탭 활성, 권한 해결 CTA | Analytics 권한 미승인 |

숨김은 capability 자체가 성립하지 않을 때만 허용한다. 구현되지 않았다는 이유로 숨기면 사용자가 플랫폼마다 정보구조가 다르다고 느끼므로 비활성과 이유 표시를 쓴다.

### 12.3 현재 채널군에 적용한 예시

| 채널군 | 탭 구성 |
|---|---|
| Threads | Queue, Analytics, Growth, Popular, Settings |
| Instagram | Queue, Editor, Analytics, Growth 비활성, Popular 비활성, Settings |
| 표준 텍스트 채널 | Queue, Analytics, Growth 비활성, Popular 비활성, Settings |
| 비디오 채널 | Queue, Analytics, Growth 비활성, Popular 비활성, Settings |
| 메시징 채널 | Settings만 표시. 나머지는 구조적으로 성립하지 않는 경우에 한함 |

### 12.4 반응형 탭

- 1024에서는 한 줄 탭을 유지하고 콘텐츠 본문과 시작 정렬선을 맞춘다.
- 390에서는 탭 순서를 유지한 가로 내부 스크롤을 사용한다.
- 선택된 탭이 진입 시 보이도록 스크롤 위치를 맞춘다.
- 페이지 전체의 가로 overflow는 금지한다.
- 비활성 탭을 눌렀을 때 같은 위치에서 이유와 열리는 조건을 보여준다.

## 15. SNS 계정 연결 없이 제작만 해 보는 흐름

### 15.1 Happy 경로

OpenClaw 로그인과 작업공간은 기존 제품 진입을 따른다. 새 익명 인증 방식을 이 문서에서 만들지 않는다. 단, 어떤 SNS 계정도 연결하지 않은 상태로 제작, 결과 확인, 원본 보존 편집까지 갈 수 있어야 한다.

|---|---|---|---|
| G-00 | `연결 없이 제작부터`, `채널 연결하고 시작` | 기본 추천은 제작부터 | 연결이 제작의 선행 조건처럼 보이지 않음 |
| T-01 | 가능한 것과 나중에 필요한 것 | 계속 제작, 연결하기 | 한 문장 안내 후 C-01로 이동 |

| T-03 | 연결하면 열리는 기능과 현재 결과 보존 안내 | 연결 시작, 계속 미룸 | 연결 취소 시 T-02로 복귀 |

### 15.2 Edge 경로

## 16. 반응형, 밀도, overflow 계약

### 16.1 공통 토큰

- spacing은 `4, 8, 12, 16, 24, 32, 48`만 사용한다.
- 페이지 섹션 간격은 24 또는 32, 카드 내부는 16 또는 24, 밀접한 라벨과 값은 4 또는 8을 쓴다.
- 임의 spacing 값은 금지한다.
- 색, 타이포, radius는 DESIGN.md v24 토큰을 그대로 사용한다.
- 질문 카드, 견적 범위, 계정 확인, repair card, revision compare와 v9.1 운영자 패턴은 DESIGN.md v24.2까지 반영했다.

### 16.2 1024 레이아웃

| 화면군 | 주축 | 열수 | 배치 |
|---|---|---|---|

### 16.5 Overflow 점검 기준

- 한글 40자 계정명, URL, 다국어 해시태그, 2,200자 캡션을 넣어도 페이지 가로 넘침 0.
- 비용과 시간 범위는 한 줄을 우선하되 390에서 라벨과 값을 두 줄로 분리할 수 있다.
- A/B/C 카드의 근거가 길면 3줄 요약과 `근거 보기`를 쓴다.
- 오류 항목이 20개여도 상단 요약과 오류 필터를 유지한다.
- 이미지 비율이 달라도 고정된 미디어 프레임 안에서 contain 또는 crop 기준을 명시한다.

## 17. 상태와 복구 계약

### 17.1 전역 복구 원칙

1. 실패 화면마다 `무엇이 보존됐는지`를 먼저 말한다.
2. 재시도는 실패한 단위만 대상으로 한다.
3. 성공한 채널이나 revision을 중복 처리하지 않는다.
4. 복구 뒤 사용자가 떠난 화면과 필드 위치로 돌아온다.
5. 외부 상태를 모르면 성공으로 낙관하지 않고 `확인 중` 또는 `확인 필요`로 둔다.
6. 초안, 마스터, 파생, 예약은 삭제 행동이 아니면 유지한다.

## 19. 회장 결정 필요

### D-08. 토큰 만료와 채널 실패를 어디에 노출할지

무엇을 정할지: 영향받은 화면의 repair card와 전체 채널 상태 센터를 함께 쓸지 결정해야 한다.

추천안: 둘 다 사용한다. 작업 중에는 해당 화면에서 바로 복구하고, A-01에서는 계정 전체 상태를 관리한다.

선택 시 결과: 사용자가 발행 맥락을 잃지 않으면서도 다계정 전체를 점검할 수 있다.

미선택 시 리스크: 상태 센터만 쓰면 작업 복귀 비용이 크고, inline만 쓰면 다른 만료 계정을 놓친다.

이 문서에서는 후보 화면 A-08과 영향 화면 repair card를 모두 그렸지만 제품 계약으로 확정하지 않았다.

### D-09. 생성 성공 뒤 발행 실패의 크레딧 처리

무엇을 정할지: 생성 비용 유지, 발행 재시도 비용, 우리 결함일 때 복구 범위를 정해야 한다.

추천안: 생성 결과가 사용 가능하면 생성 비용은 유지한다. 같은 산출물의 발행 재시도에는 추가 크레딧을 받지 않는다. 우리 결함으로 결과 자체가 사용할 수 없을 때만 복구 또는 환급한다.

선택 시 결과: 제작 가치와 발행 전송 실패를 분리해 사용자에게 설명할 수 있다.

미선택 시 리스크: P-06이 정확한 비용 약속을 할 수 없어 분쟁과 중복 과금 불안을 만든다.

이 문서에서는 P-06에 `크레딧 처리 확인 중` 상태를 허용하며 숫자나 환급을 확정하지 않았다.

### D-10. 다채널 캡션과 해시태그의 기본 구조

무엇을 정할지: 공통 기본값에서 채널별 override를 만들지, 처음부터 채널별 독립본을 만들지 결정해야 한다.

추천안: Studio가 공통 마스터 텍스트를 만들고, 채널 제약을 받아 채널별 파생본을 만든다. 사용자는 공통 변경과 채널 한정 변경을 명시적으로 선택한다.

선택 시 결과: 반복 입력을 줄이면서 플랫폼별 길이와 화법을 지킬 수 있다.

미선택 시 리스크: 공통 편집이 파생본을 덮거나, 채널별 편집이 서로 다른 원본으로 갈라질 수 있다.

이 문서의 P-02는 두 구조를 수용하는 검수 화면만 정의하며 저장 계약은 확정하지 않았다.

## 20. 레드팀

### 20.1 까다로운 다계정 운영자의 공격

공격: `다른 계정 연결`을 눌러도 Meta가 이미 로그인된 개인 계정으로 다시 들어가면 화면만 늘고 해결되지 않는다.

수정: A-03에서 서비스가 외부 쿠키를 통제하지 못한다는 사실을 먼저 밝힌다. 제공자 계정 센터와 비공개 창 경로를 연결 전에 제공하고, A-05에서 실제 돌아온 계정을 승인하기 전 활성화하지 않는다. 잘못 돌아오면 A-06에서 후보만 폐기하고 기존 기본 계정과 예약을 보존한다.

### 20.2 회의적 투자자의 공격

공격: 8단계는 선택 피로를 줄이는 것이 아니라 전환을 떨어뜨리는 긴 설문일 수 있다.

수정: 각 단계는 빈 입력이 아니라 최대 3개에서 5개의 답을 먼저 보여주고, 이전 선택을 임시 저장한다. G-00에서 SNS 연결을 빼고 제작부터 시작하게 한다. 단계 이탈률, 추천 수락률, A/B/C 재생성률을 계측해야 하며, 실제 데이터 없이 8단계가 최적이라고 단정하지 않는다.

### 20.3 경쟁자의 공격

공격: 비용과 시간 범위를 붙여도 실제 견적이 없으면 신뢰를 더 잃는다.

수정: C-03의 모든 선택 카드에 실제 Studio 견적 범위를 필수화한다. 값이 없으면 `계산 중` 또는 실패 상태로 두며 가짜 숫자를 채우지 않는다. 범위의 산정 시각과 포함 범위를 표시한다.

### 20.4 정책 담당자의 공격

공격: 정책 거부를 자동 수정하면 사용자가 의도하지 않은 표현으로 발행할 수 있다.

수정: P-03과 P-06은 위반 위치, 정책 출처, 수정 후보만 제공한다. 수정본은 다시 미리보고 사용자가 승인해야 하며 자동 발행하지 않는다.

## 21. 셀프심문

질문: 이 결론이 틀렸다면 가장 그럴듯한 이유는 무엇인가?

답: 가장 load-bearing한 가정은 제공자 인증에서 돌아온 계정을 서비스가 안전하게 식별하고, 사용자 확인 전 연결을 보류할 수 있다는 것이다. 현재 구현은 복수 계정을 저장할 수 있지만 첫 연결의 기본값 처리와 후보 보류 상태가 이 UX를 그대로 지원한다는 증거는 없다. 또한 제공자마다 계정 선택과 자산 선택의 의미가 다르다.

수정: 문서에서 `후보 연결 보류`를 사용자 안전 요구로 정의하되 API나 저장 방식을 확정하지 않았다. A-05와 A-06을 구현하기 전 제공자별 샌드박스 검증과 보안 기술설계를 필수 gap으로 올렸다. 공식 선택기는 Google 계열에만 확인된 사실로 제한했다.

두 번째 질문: 성과 화면이 선택의 효과를 과장할 위험은 없는가?

답: 있다. 같은 기간의 캠페인, 계절, 계정 규모가 성과를 바꿀 수 있다.

수정: R-02의 문구를 `이 선택이 만든 결과`가 아니라 `이 선택 뒤 관찰된 결과`로 고정하고, 표본, 기간, 외부 변수, revision을 함께 표시한다. 다음 추천은 검증된 결론이 아니라 실험 후보로만 제시한다.

| O-05 | 크레딧·결제·환불 | 잔액, 충전, 차감, 환불, 결제 상태, 최근 원장 조회 | 목표 | O-06 또는 O-04 |
| O-06 | 잔액 조정 확인 | 조정 전후, 사유, 증거, 고객 통지 여부를 확인 후 실행 | 목표 | O-05 |
| O-07 | 사용량·원가 | 테넌트·제작방식·공급자별 사용량과 원가, 마진 위험 조회 | 목표 | O-04, O-09 |
| O-08 | 유저 막힘 퍼널 | 질문·연결·생성·편집·발행 단계별 이탈과 실패 조회 | 목표 | O-04, O-02, O-09 |
| O-09 | 운영 루프 집계 | 제작 방식별 성과, 실패 프롬프트, 재시도율, 선택 결과 조회 | 목표 | C-04 근거 후보 또는 O-07 |
| O-10 | 지원 요청함 | 신규, 대기, 고객 답변 대기, 해결 요청을 기한순 처리 | 목표 | O-11 |
| O-11 | 지원 요청 상세 | 고객 맥락과 실패 이력을 보며 답변·복구·환불 분기 | 목표 | O-02, O-04, O-05, O-10 |
| O-12 | 알람 규칙·수신 | 임계값, 수신 경로, 조용한 시간, 테스트 알림 관리 | 목표 | O-01 |

### 26.1 O-00 운영 홈

첫 접힘선은 다음 네 블록으로 제한한다.

1. 미확인 치명·높음 알람과 가장 오래된 발생 시각
2. 오늘 기한이 지난 지원 요청
3. 오늘 금전 조치 대기와 원가 이상
4. 시스템 건강 요약과 마지막 계산 시각

정상 지표는 두 번째 블록부터 배치한다. 기존 6개 요약 카드는 `정상 운영 요약`으로 유지하되 치명 알람이 있으면 접힌다. 알람 0개일 때는 `현재 미확인 장애 0개, 마지막 확인 시각`을 보여주고 빈 빨간 영역을 남기지 않는다.

### 26.2 O-01 통합 알람함

- 기본 필터는 `미확인 + 처리 중`이다.
- 정렬은 심각도, 영향 고객 수, 오래된 순서다.
- 같은 근본 원인의 반복 이벤트는 한 사건으로 묶고 횟수와 최초·최근 시각을 표시한다.
- 목록 행은 알람 종류, 심각도, 영향 범위, 발생 시각, 마지막 변화, 현재 주인, 다음 행동을 한눈에 보여준다.
- 1인 운영 전제라 사람 배정 UI를 만들지 않는다. 소유자는 `운영자` 또는 `시스템 대기` 둘뿐이다.
- `모두 읽음`은 제공하지 않는다. 치명·높음 알람은 개별 확인이 필요하다.

### 26.3 O-02 장애 상세·조치

상단 질문은 하나다. `지금 고객 작업을 보호하려면 무엇을 해야 하는가?`

| 영역 | 내용 |
|---|---|
| 사실 | 감지 시각, 마지막 정상, 영향 고객·채널·요청, 현재 상태 |
| 근거 | 오류 묶음, 기준 대비 편차, 공식 정책 확인 여부, 데이터 신선도 |
| 보존 | 초안, 예약, 성공 채널, 크레딧, 외부 게시 결과 중 유지된 것 |
| 다음 행동 | 안전한 상태 조회, 재연결 안내, 실패 단위 재시도, 고객 알림, 지원 요청 연결 |
| 타임라인 | 감지, 확인, 조치, 관찰, 해결 확인. 역순 최신 기록이 위 |

재시도 버튼은 중복 실행 위험을 검사한 뒤에만 활성화한다. 외부 게시 여부가 불명인 `unknown` 상태는 재발행을 금지하고 reconcile만 허용한다.

### 26.4 O-03과 O-04 회원·테넌트

O-03 기본 열은 고객명, 상태, 연결 계정, 최근 사용, 미확인 장애, 지원 요청, 잔액이다. 이메일과 내부 ID는 검색 가능하지만 한 행에 모두 노출해 밀도를 높이지 않는다.

O-04는 기존 정보와 조치를 보존하고 아래 탭을 추가한다.

1. 개요
2. 연결·발행
3. 제작·사용량
4. 크레딧·결제
5. 막힘·지원
6. 감사 이력

탭 위치는 고정한다. 데이터가 없으면 탭을 숨기지 않고 empty state와 필요한 첫 행동을 보여준다. 정지·재개와 공유 AI 승인·회수는 `개요`의 위험 조치 영역에 유지한다.

### 26.5 O-05와 O-06 크레딧·결제·환불

O-05의 상단은 `사용 가능 잔액`, `보류`, `최근 차감`, `환불 대기`, `마지막 원장 반영`을 분리한다. 잔액과 사용량 데이터의 갱신 시각이 다르면 각각 표시한다.

원장 행은 발생시각, 유형, 증감, 이전 잔액, 이후 잔액, 관련 작업, 사유, 처리 주체를 보여준다. 생성 비용, 발행 재시도, 환불, 수동 보정은 같은 유형으로 합치지 않는다.

O-06은 의도된 마찰을 둔다.

1. 조정 유형 선택
2. 금액 또는 크레딧 입력
3. 관련 작업·결제·지원 요청 연결
4. 고객에게 보일 사유와 내부 사유 분리
5. 조정 전후 잔액 미리보기
6. 실행 확인
7. 성공 뒤 원장 행과 감사 ID 표시

조정 실패 시 중복 제출을 막고 상태 재조회만 허용한다. 환불 가능 범위와 승인 권한, 결제 제공자 계약은 제품·기술 합의 전 확정하지 않는다.

### 26.6 O-07 사용량과 원가

- 고객 크레딧과 공급자 원가를 같은 숫자로 표현하지 않는다.
- 기간, 테넌트, 제작 방식, 공급자, 성공·실패를 필터로 제공한다.
- 핵심 지표는 사용 크레딧, 공급자 원가, 성공 건당 원가, 재시도 원가, 실패 원가다.
- 집계 수치마다 계산 기간, 포함 범위, 마지막 집계 시각을 표시한다.
- 원가 급증은 총액만으로 판단하지 않고 성공 건당 원가와 재시도율을 함께 본다.
- 과다 데이터는 상위 위험 8개를 먼저 보여주고 전체는 검색·필터·내보내기로 연다.

### 26.7 O-08 유저가 막힌 지점

질문, 연결, 생성, 편집, 발행을 같은 퍼널로 합치지 않는다. 각 흐름별로 진입, 완료, 반복, 이탈, 오류를 분리한다.

| 흐름 | 먼저 보는 지표 | 상세 진입 |
|---|---|---|
| 질문 엔진 | 단계별 이탈, 추천 거절, 자유입력 전환, A/B/C 재생성 | 해당 세션의 선택·근거 이력 |
| 계정 연결 | 제공자 이동, 콜백, 실제 계정 확인, 오계정 보류, 재연결 | A-02부터 A-08 이벤트 타임라인 |
| 생성 | 단계 실패, 재시도, 크레딧 판정, 보존 결과 | C-07과 공급자 오류 |
| 편집 | 모호 지시, 유과금 전환, revision 미채택 | E-01부터 E-03 |
| 발행 | 사전 차단, 전송 중, 확인 중, 실패, 복구 | P-03부터 P-06 |

이탈은 실패로 단정하지 않는다. 사용자가 저장 후 정상 종료했는지, 브라우저를 닫았는지, 오류 뒤 멈췄는지를 분리한다.

### 26.8 O-09 운영 루프

운영 루프는 개인 취향 프로필과 분리된 집계만 사용한다.

- 제작 방식별 성과와 표본
- 프롬프트 유형별 실패율
- 재시도 횟수와 이유
- 추천 채택·거절·반박 수용
- 비용 범위 예측과 실제 차이
- 결과 수정 종류와 미채택 이유

개별 고객을 식별할 수 있는 원문을 기본 집계 화면에 노출하지 않는다. 추천 엔진에 돌려보낼 후보는 `우리 실험 로그`, 표본, 기간, 불확실성을 갖춘 경우만 승인 후보가 된다.

### 26.9 O-10과 O-11 유저 지원

지원 요청은 고객이 `지원` 메뉴에서 새로 만들거나 C-07, A-08, P-06의 오류 화면에서 현재 맥락을 붙여 보낸다. 오류 화면에서 보낼 때 아래 정보를 자동 포함한다.

- 테넌트와 사용자 식별자
- 화면 ID와 요청 ID
- 발생 시각과 마지막 정상 행동
- 오류 분류와 보존된 항목
- 이미 시도한 복구 행동
- 비밀값을 제거한 환경·provider 정보

O-10 정렬은 미확인, 응답 기한 초과, 결제·발행 중단, 오래된 순서다. O-11은 고객 메시지와 시스템 사실을 시각적으로 분리한다. 운영자는 답변, 복구 조치, 환불 검토, 고객 답변 대기, 해결 확인 중 하나를 선택한다. 답변만 보냈다고 해결로 닫지 않는다.

### 26.10 O-12 알람 규칙·수신

각 알람은 활성 여부, 임계값, 계산 기간, 지연 허용, 수신 경로, 테스트 시각을 가진다. 치명 알람은 대시보드 밖 수신 경로가 최소 하나 필요하다. 이메일, Slack, 문자 중 어느 제공자를 쓸지는 기술설계와 비용 합의로 회수한다.

조용한 시간에도 치명 알람은 차단하지 않는다. 테스트 알림은 실제 사건과 명확히 구분하고 마지막 성공·실패 시각을 남긴다.

## 27. v9.1 운영자 핵심 흐름과 상태

### 27.1 장애 발견과 복구 Happy 경로

`시스템 감지` -> `O-00 위험 레일` -> `O-01 알람함` -> `O-02 장애 상세` -> `영향 고객 O-04 또는 고객 복구 A-08/P-06` -> `관찰 중` -> `정상 신호 확인` -> `해결 확인`

| 단계 | 운영자가 보는 것 | 행동 | 보존·안전장치 |
|---|---|---|---|
| 감지 | 알람 종류, 심각도, 영향, 최초 시각 | 알람 열기 | 중복 사건 묶기 |
| 확인 | 사실, 근거, 보존된 것, 다음 행동 | `확인하고 처리 시작` | 확인을 해결로 표시하지 않음 |
| 조치 | 안전한 복구 후보 | 하나 선택 또는 지원 연결 | 외부 상태 unknown이면 재발행 금지 |
| 관찰 | 상태 변화, 실패율, 큐 감소 | 계속 관찰 또는 추가 조치 | 계산 시각 표시 |
| 종료 | 정상 신호와 확인 시각 | 해결 확인 | 수동 종료는 사유 필수 |

### 27.2 과금 조정 Happy 경로

`O-04 고객 상세` -> `O-05 원장` -> `O-06 조정 유형` -> `관련 증거 연결` -> `전후 잔액 확인` -> `실행` -> `원장·감사 ID 확인` -> `필요 시 O-11 고객 안내`

### 27.3 지원 요청 Happy 경로

`고객 오류 화면 또는 지원 메뉴` -> `O-10 신규 요청` -> `O-11 사실·메시지 대조` -> `O-02/O-04/O-05 복구` -> `고객 답변` -> `고객 또는 운영자 해결 확인` -> `O-10 종료`

### 27.4 공통 Edge 경로

| 조건 | 처리 | 탈출구 |
|---|---|---|
| 같은 장애가 여러 테넌트에서 반복 | 하나의 사건과 영향 테넌트 목록으로 묶기 | 개별 고객 상세와 전체 사건 사이 왕복 |
| 알람이 회복됐다가 재발 | 새 사건으로 숨기지 않고 이전 사건에 재발 표시 | 재개 또는 별도 근본원인 사건 분리 |
| 운영자가 이미 외부에서 조치 | 수동 조치 시각·사유 기록, 상태 재조회 | 정상 확인 또는 관찰 중 |
| 원장 반영 응답이 시간 초과 | 성공·실패 단정 금지 | 최신 잔액과 idempotency 상태 재조회 |
| 고객 메시지와 시스템 기록이 충돌 | 양쪽 사실을 병렬 표시 | 추가 증거 요청, 사건 연결 |
| 한 고객이 요청을 여러 개 보냄 | 자동 병합하지 않고 연관 요청 후보 표시 | 운영자가 병합 또는 분리 |

### 27.5 공통 Empty 경로

|---|---|---|
| O-00/O-01 | `미확인 장애가 없습니다`와 마지막 점검 시각 | 정상 지표 보기, 알람 테스트 |

| O-08 | 계측 데이터 없음 | 계측 범위와 첫 수집 시각 확인 |
| O-09 | 집계할 표본 부족 | 최소 표본 전까지 가설로 유지 |

|---|---|---|

| 고객 상세 일부 실패 | 정상 블록 유지, 실패 블록만 error | 해당 블록 재조회 |
| 원장 조회 실패 | 잔액 조정 버튼 비활성 | 원장 복구 후 재조회 |
| 잔액 조정 실패 | 입력과 사유 보존, 처리 여부 미확정 표시 | 상태 재조회, 중복 실행 금지 |
| 원가 집계 실패 | 마지막 정상 집계와 실패 시각 | 재집계 요청, 원시 사용량 확인 |
| 지원 답변 전송 실패 | 답변 초안 보존 | 다시 전송, 복사, 내부 메모 전환 |

### 27.7 공통 Loading 경로

- O-00은 전체 페이지를 비우지 않고 마지막 정상 스냅샷과 갱신 중 배지를 함께 보여준다.
- O-01은 행별 상태 갱신을 허용하고 목록 필터를 막지 않는다.
- O-04는 탭별 skeleton을 사용하며 고객명과 상태는 유지한다.
- O-06은 실행 중 같은 조정의 재제출을 비활성화한다.
- O-07과 O-09는 집계 중 기간·필터와 이전 결과를 유지한다.
- O-11은 답변 전송 중 시스템 이력 탐색을 허용한다.

### 27.8 운영자 dead-end 방지

모든 운영자 화면은 다음 중 하나를 제공한다.

- 이전 목록으로 돌아가기
- 고객 상세로 이동
- 장애 상세로 이동
- 지원 요청으로 연결
- 안전하게 보류하고 관찰 상태로 전환
- 변경 없이 종료

오류가 계속돼도 원본 고객 콘텐츠, 성공 채널, 기존 잔액, 이전 감사 이력을 삭제하지 않는다.

## 28. v9.1 질문 엔진 화법 준수 감사

### 28.1 적용 규칙

질문 엔진에 해당하는 화면은 네 슬롯을 모두 갖는다.

1. 선택지
2. 추천
3. 추천 근거
4. 자유입력 보조

질문이 아니라 상태 확인, 실행 확인, 보안·과금 승인인 화면은 자유입력을 기본 경로로 강제하지 않는다. 단, 사유 입력이 필요한 고위험 조치는 별도 의도된 마찰로 둔다.

### 28.3 반박 화법 점검

추천과 사용자 선택이 목적, 비용 상한, 채널 정책, 권리 범위와 충돌하면 화면은 다음 순서로 말한다.

1. 사용자가 고른 것을 정확히 재진술한다.
2. 충돌하는 목적이나 제약을 한 문장으로 말한다.
3. 대안 두 개에서 세 개를 제시한다.
4. 추천안과 근거를 붙인다.
5. 그래도 원안을 유지하거나 다른 생각을 적을 길을 연다.

예시: `TikTok용 90초 영상을 고르셨습니다. 현재 선택한 목표는 첫 방문 도달이라 첫 장면 이탈 위험이 큽니다. 30초 압축안을 추천합니다. 같은 목적의 공개 사례에서 짧은 시작 구조가 반복됐기 때문입니다. 90초를 유지하거나 원하는 길이를 직접 적을 수도 있습니다.`

### 28.4 질문 화면 금지 패턴

- 빈 textarea 하나와 `다음`
- 추천 하나를 사실처럼 강제
- `AI 추천`만 있고 근거·표본·시점 없음
- 자유입력만 크게 두고 선택지를 접음
- 사용자 선택과 충돌해도 조용히 덮어씀
- 질문 한 화면에 주요 선택 7개 이상을 동등 위계로 노출
- 추천 근거와 광고성 카피를 구분하지 않음

3. 복구 뒤 자동 재시도하지 않고 영향 작업을 다시 확인한다.
4. 크레딧 잔액은 최근 사용, 보류, 데이터 시각과 함께 본다.
5. 질문은 자유입력보다 예시 선택을 먼저 보여주되 모바일에서 한 화면 선택 수를 제한한다.

## 32. v9.1 레드팀·셀프심문·품질 판정

### 32.1 레드팀 1: 1인 운영자의 공격

공격: 메뉴를 여덟 개 늘리면 운영자가 더 많은 화면을 돌아다녀야 한다. 알람 메뉴가 있어도 바쁠 때 안 열면 소용없다.

수정: O-00 첫 접힘선과 사이드바 전역 배지에서 미확인 위험을 먼저 드러낸다. 치명 알람은 대시보드 밖 수신 경로를 최소 하나 요구한다. 각 알람 상세에서 고객, 발행 복구, 지원, 과금으로 바로 이동한다.

### 32.2 레드팀 2: 까다로운 고객의 공격

공격: 운영자가 잔액을 마음대로 조정하거나 실패 게시물을 자동 재발행하면 돈과 브랜드 신뢰를 동시에 잃는다.

수정: O-06은 관련 증거, 고객용 사유, 전후 잔액, 실행 확인, 감사 ID를 요구한다. 연결 복구 뒤 실패 게시물은 자동 재시도하지 않는다. 외부 결과가 unknown이면 재발행을 막고 상태 조회만 허용한다.

### 32.3 레드팀 3: 경쟁자의 공격

공격: 알람 5종과 사용량 대시보드는 일반적인 운영 도구다. 제품 차별점이 아니다.

수정: 차별점은 알람 자체가 아니라 고객 질문 선택, 제작 방식, 수정, 채널 파생, 발행 결과, 성과를 한 사건과 운영 루프로 연결하는 데 둔다. O-08과 O-09는 단순 오류 수가 아니라 어디서 어떤 선택 뒤 막혔고 무엇이 성과·원가에 연결됐는지 보여준다.

### 32.4 셀프심문

질문: 이 결론이 틀렸다면 가장 그럴듯한 이유는 무엇인가?

답: 가장 load-bearing한 가정은 다섯 장애를 신뢰할 수 있게 감지하고 고객·요청·크레딧에 연결할 데이터가 존재한다는 것이다. 현재 구현에는 고객·발행·사용 이벤트 일부만 있고 임계값, 사건 묶음, 생성 원가, 질문 단계 이탈, 지원 요청 원장이 확인되지 않았다. 화면만 먼저 만들면 정확해 보이는 빈 운영 콘솔이 된다.

수정: 모든 신규 화면을 목표로 표시하고, 값마다 데이터 소스·계산 기간·마지막 계산 시각을 요구한다. 임계값이 없으면 `기준 미설정`, 집계가 실패하면 마지막 정상 스냅샷과 실패 상태를 분리한다. 기술설계 전에 이벤트·원장·사건 연결 가능성을 검증하도록 회수 항목을 추가한다.

두 번째 질문: 모든 질문 화면에 자유입력을 열면 다시 백지공포가 커지지 않는가?

답: 자유입력이 시각적으로 주 입력과 동등하면 그렇다.

수정: 자유입력은 선택 카드 아래의 보조 행동으로만 둔다. 먼저 3개에서 5개의 선택과 추천을 보여주고, 선택지에 없을 때만 연다. 직접 입력 뒤에도 해석 후보와 추천을 다시 제시해 백지 상태로 방치하지 않는다.

## 33. v9.2 공식 벤치마크 근거 보강

### 33.1 개정 범위와 회귀 방지

v9.2는 v9.1의 화면 ID, 흐름 순서, 상태, 운영자 화면, 질문 화법, 반응형 계약을 변경하지 않는다. 이번 개정은 다음 네 근거 축을 공식 제품 자료로 다시 조사해 설계 이유와 적용 경계를 보강한다.

1. 여러 소셜 계정을 다루는 제품의 계정 전환과 계정 맥락 유지
2. 사용자가 답하기 쉬우면서 이후 행동으로 계속 학습하는 온보딩 질문
3. 크레딧 잔액, 최근 사용, 소진 경고, 자동 충전 설정
4. 발행 실패, 연결 만료, 권한 부족의 알림과 복구

신규 화면 ID, 신규 컴포넌트, 신규 토큰은 0개다. v9.1의 A-01부터 A-08, C-01부터 C-06, P-03부터 P-06, O-00부터 O-06, O-12에 근거를 추가했다. 따라서 `DESIGN.md`는 v24.2와 정합하며 이번 리테이크에서 추가 개정하지 않는다.

### 33.9 벤치마크가 강화한 기존 우선순위

1. 계정 전환은 연결 버튼보다 `현재 어떤 계정으로 들어가 있는가` 확인이 먼저다.
2. OAuth callback 성공보다 `돌아온 실제 계정을 사용자가 승인했는가`가 연결 완료의 마지막 조건이다.
3. 온보딩 질문 수를 줄이는 것만이 답은 아니다. 비교 가능한 선택지를 보여주고, 첫 결과 뒤 행동으로 계속 학습해야 한다.
4. 크레딧은 잔액 숫자가 아니라 사용 가능·보류·최근 사용·갱신 시각·소진 방지 설정의 묶음이다.
5. 연결 복구와 실패 발행 재시도는 다른 행동이다. 복구 성공 뒤 자동 재발행하지 않는다.
6. 알림은 사건 종류와 심각도로 나눈다. 발행 실패, 연결 해제, 결제·보안 알림을 하나의 전역 토글로 뭉치지 않는다.

### 33.10 레드팀

#### 까다로운 다계정 운영자의 공격

공격: Buffer·Later·Hootsuite도 결국 사용자가 provider에서 로그아웃해야 한다. OpenClaw가 안내를 화면 안에 넣어도 잘못된 계정 연결 문제를 해결하지 못한다.

수정: 안내를 해결로 과장하지 않는다. A-03은 위험 감소 단계이고, 진짜 안전장치는 A-05의 실제 계정 readback과 A-06의 후보 보류다. readback을 신뢰할 데이터가 없으면 연결을 완료하지 않고 `확인 불가`로 남긴다.

#### 회의적 투자자의 공격

공격: Stitch Fix와 Spotify는 패션·음악 소비 제품이다. 마케팅 제작의 8단계 질문에 그대로 적용할 근거가 아니다.

수정: 숫자와 레이아웃을 복제하지 않는다. 두 사례에서 차용하는 것은 자유입력보다 선택을 먼저 보여주는 원리와 초기 입력 뒤 행동으로 계속 학습하는 구조뿐이다. C-02 2열은 별도 prototype 실험 후보이며 전체 질문 흐름 규칙으로 확정하지 않는다.

#### 까다로운 고객의 공격

공격: 잔액 경고와 자동 충전은 더 쓰게 만드는 다크패턴이 될 수 있다.

수정: 자동 충전은 기본 활성으로 확정하지 않는다. 최소선, 목표선, 월 상한, 즉시 발생 가능성, 끄기, 최근 충전 이력을 한 화면에서 보여준다. 충전하지 않아도 현재 작업을 저장하고 저비용 범위로 축소할 수 있다.

#### 장애 대응자의 공격

공격: 모든 만료와 실패를 위로 올리면 운영 홈이 경고로 가득 차고 실제 치명 장애를 못 찾는다.

수정: 같은 원인·provider·시간대의 실패는 사건으로 묶고 영향 고객 수, 예약 기한, 최근 정상 시각으로 정렬한다. 해결 확인과 오탐에는 근거를 요구하고, 단순 `확인함`을 해결로 표시하지 않는다.

34장은 위 확정값을 v9.2의 관련 분기보다 우선한다. 이 문서는 사용자에게 필요한 정보, 선택, 상태, 복구, 종료점을 확정한다. 체험 크레딧 수량·만료, 연락처 보관 기간, 콘텐츠 유형 분류, 발행 정책의 서버 적용 시점, 내보내기 보관 기간, 품질 반려 사유 코드는 제품·법무·기술설계에서 정한다.

### 34.4 테넌트 발행 방식 설정과 두 모드

#### 34.4.1 적용 우선순위

사용자가 보는 우선순위는 `콘텐츠 유형별 override > 채널별 override > 테넌트 기본값`이다. 이 순서는 화면 해석 계약이며 저장 스키마를 확정하지 않는다.

M-01의 각 행은 범위, 현재 모드, 상속 출처, 다음 발행부터 적용 여부, 영향받는 대기 건수를 보여준다. 한 행의 예시는 `Instagram · 영상 · 자율 발행 · 테넌트 기본에서 상속`이다. 모드 두 가지는 다음처럼 설명한다.

| 모드 | 화면 설명 | 품질 통과 뒤 | 실패·unknown |
|---|---|---|---|
| 자율 발행 | `품질 기준을 통과한 결과를 선택한 시각과 계정으로 자동 발행합니다.` | P-03 사전 점검 후 예약 또는 발행 | 자동 재발행 금지. P-06과 A-08에서 명시적 복구 |
| 승인 후 발행 | `품질 기준을 통과한 결과를 승인 대기함에 보냅니다. 확인 전에는 발행하지 않습니다.` | V-01·V-02 승인 뒤 P-04 또는 P-05 | 승인 대기로 보존. 자동 전환·자동 승인 금지 |

신규 테넌트의 화면 추천은 `승인 후 발행`이다. 첫 채널·첫 유형의 결과를 확인한 뒤 사용자가 자율 발행으로 바꿀 수 있다. 추천은 제품 기본값을 확정하는 기술 계약이 아니라, 위험이 큰 첫 사용에서 브랜드 손실을 줄이는 UX 제안이다.

#### 34.4.2 M-01 Happy 경로

`Settings` -> `M-01 테넌트 기본 선택` -> `채널별 예외 선택` -> `유형별 예외 선택` -> `M-02 적용 결과 미리보기` -> `변경 확인` -> `원래 작업으로 복귀`

자율 발행으로 바꿀 때 M-02는 다음을 한 화면에 보여준다.

1. 자동 발행되는 채널과 콘텐츠 유형
2. 사용되는 계정과 예약 시각 결정 위치
3. 품질 게이트 반려 시 무과금·미발행
4. 토큰 만료, 정책 거부, 결과 unknown 시 자동 재발행 금지
5. 현재 승인 대기·예약 건 중 새 정책이 적용되는 범위

`자율 발행 켜기`는 영향 목록을 읽은 뒤에만 활성화한다. 채널별·유형별 예외가 하나도 없으면 빈 표를 보여주지 않고 `현재 모든 범위가 테넌트 기본값을 따릅니다`와 `예외 추가`를 제공한다.

#### 34.4.3 자율 발행 Happy 경로

`C-07 생성` -> `품질 게이트 통과` -> `P-01·P-02 파생·텍스트 준비` -> `P-03 계정·정책·현재 모드 확인` -> `예약이면 P-04` -> `P-05 자동 실행` -> `P-06 결과`

- C-07과 P-03에 `자율 발행 · Instagram 영상 override`처럼 실제 적용 모드와 출처를 표시한다.
- 사용자는 플랫폼 요청 전까지 작업 단위 `이번만 승인 후 발행으로 전환` 또는 `이번 발행 중지`를 선택할 수 있다.
- 품질 통과는 발행 성공이 아니다. 계정·토큰·정책·시간·중복 검사를 P-03에서 다시 통과해야 한다.
- 일부 채널만 차단되면 정상 채널은 설정에 따라 계속하고 차단 채널은 P-06에 보존한다. 사용자가 `모두 성공해야 발행`을 별도 선택하지 않았다면 조용히 전체를 취소하지 않는다.
- 외부 결과가 unknown이면 해당 채널은 상태 조회만 허용한다. 자율 발행 모드라는 이유로 재전송하지 않는다.

#### 34.4.4 승인 후 발행 Happy 경로

`C-07 생성` -> `품질 게이트 통과` -> `P-01·P-02 준비` -> `V-01 승인 대기` -> `V-02 상세 검수` -> `승인하고 예약 P-04` 또는 `승인하고 지금 발행 P-05` -> `P-06 결과`

V-01 기본 정렬은 발행 예정이 가까운 순서, 품질 통과 시각이 오래된 순서다. 행은 결과 썸네일, 채널·계정, 유형, 예정 시각, 품질 통과, 비용, 변경된 revision, 필요한 행동을 표시한다.

V-02의 주요 행동은 한 번에 하나다.

- `승인하고 예약`: 예약 시각이 있거나 시각 확인이 필요한 경우
- `승인하고 지금 발행`: 지금 발행이 선택된 경우
- `수정 요청`: E-01로 이동하고 현재 승인안 보존
- `이번 결과 사용 안 함`: 사유를 선택하고 결과를 미채택으로 보존. 품질 게이트 반려와 다른 사건이므로 자동 무과금으로 표현하지 않는다.

승인 대기 기한이 지나도 자율 발행으로 바뀌지 않는다. 예약 시각이 지나면 `승인 필요 · 예약 시각 지남`으로 남고 새 시각 선택 또는 지금 발행을 요구한다.

#### 34.4.5 발행 모드 Edge·Empty·Error·Loading

| 상태 | 화면 | 복구·종료 |
|---|---|---|
| 범위 충돌 | M-02에 테넌트·채널·유형 규칙과 최종 적용값 표시 | 예외 제거, 범위 수정, 최종값 유지 |
| 정책 변경 중 대기 건 존재 | 영향 건수를 모드별로 분리 | 기존 정책 유지 또는 다음 작업부터 적용. 일괄 소급은 별도 확인 |
| 승인자 부재 | V-01에 `승인 가능한 사람이 없습니다` | 권한 해결, 초안 보존, 자율 발행으로 몰래 전환 금지 |
| 승인 대기 0건 | V-01 empty에 마지막 확인 시각과 새 제작 CTA | C-01 또는 종료 |
| 설정 조회 실패 | M-01 마지막 확인값과 갱신 실패 표시 | 재조회. 확인 불가 상태에서 자율 발행 활성화 금지 |
| 설정 저장 timeout | M-02 `적용 여부 확인 중` | 현재값 재조회. 중복 저장 금지 |
| 승인 저장 실패 | V-02 입력·검수 위치 보존 | 다시 승인, 초안 저장, 지원 요청 |
| 대기 건 과다 | V-01 상위 위험 20건, 필터·페이지 | 채널·유형·기한·계정 필터, 선택 일괄 승인 전 영향 확인 |
| 모드 로딩 | 현재 적용 모드를 지우지 않고 `갱신 중` 표시 | 읽기는 허용, 저장만 잠금 |

### 34.5 품질 게이트 반려는 무과금

#### 34.5.1 Q-01 정보 위계와 확정 카피

Q-01의 첫 문장은 결과 실패보다 금전 사실과 보존을 먼저 말한다.

**제목:** `품질 기준을 통과하지 못해 결과를 전달하지 않았어요`

**핵심 안내:** `이번 시도는 품질 게이트에서 반려되어 크레딧을 사용하지 않았습니다.`

**보존 안내:** `선택한 방향, 자료, 스타일, 채널 설정은 그대로 보존했습니다.`

**이유 영역:**

- 통과하지 못한 기준의 사용자 언어 이름
- 발견된 위치 또는 구간
- 왜 전달할 수 없는지
- 자동으로 바꿀 수 있는 것과 다시 선택해야 하는 것
- 검수 시각과 기준 버전

내부 모델 오류명, 점수 원문, 공급자 프롬프트는 고객에게 그대로 노출하지 않는다. 이유가 권리·안전과 관련돼 제한 미리보기도 위험하면 결과 이미지를 보여주지 않고 안전한 설명만 제공한다.

#### 34.5.2 잔액과 원장 표시

| 원장 상태 | 고객 문구 | 행동 |
|---|---|---|
| 차감 없음 확인 | `차감 0크레딧 · 현재 사용 가능 잔액은 원장 확인값을 표시` | 같은 방향 재시도, 선택 수정 |
| 잔액 동기화 중 | `이번 시도는 차감되지 않았습니다. 현재 잔액을 확인하고 있어요.` | 잔액 새로고침, 제작 선택 수정 |
| 원장 조회 실패 | `차감 없음은 확인했습니다. 잔액 표시는 잠시 불러오지 못했습니다.` | 원장 재조회, 지원 요청 |
| 판정과 원장 충돌 | `차감 상태를 확인 중입니다. 같은 작업을 다시 실행하지 마세요.` | O-11 지원 사건 자동 연결, 상태 조회만 |

무과금은 사용자 선택으로 버린 결과, 발행 실패, 연결 실패의 비용 정책을 자동으로 바꾸지 않는다. Q-01은 시스템 품질 게이트가 사용자에게 전달하기 전에 반려한 사건에만 사용한다.

#### 34.5.3 Q-01 Happy·Edge·Empty·Error·Loading

`C-07 품질 검사` -> `Q-01 반려 이유·차감 0 확인` -> `같은 방향 자동 보정`, `C-05 선택 변경`, `E-01 지시 수정`, `저장 후 종료`, `지원 요청` 중 하나

| 이유 여러 개 | 전달을 막은 상위 3개, 나머지 접기 | 한 번에 고칠 묶음 제안, 전체 이유 보기 |

### 34.6 가입 전 연락처 기반 체험

#### 34.6.1 체험 원칙

- 상시 무료 등급이 아니라 확인된 연락처에 체험 크레딧을 지급한다.
- 기본 연락처는 시그마인 사례와 결과 전달 목적에 맞춘 이메일이다. 전화번호·메신저를 추가 수단으로 만들려면 별도 제품 결정이 필요하다.
- 결과 전달과 체험 운영에 필요한 필수 동의와 광고성 정보 수신 선택 동의를 분리한다.
- 가입 전에도 연락처 수집 목적, 보관 기간, 삭제·문의 경로를 입력 전에 보여준다.
- SNS 연결은 체험의 선행 조건이 아니다. TR-03은 기존 T-01 무연결 제작을 재사용한다.
- 체험 크레딧 수량, 만료, 1인당 지급 횟수는 실제 정책값을 읽는다. 화면에 임의 숫자를 쓰지 않는다.

#### 34.6.2 Happy 경로

`TR-00 연락처 남기고 체험 크레딧 받기` -> `TR-01 이메일·필수 동의` -> `TR-02 확인 링크 또는 코드` -> `지급 완료` -> `TR-03 C-01부터 제작` -> `Q-01 또는 T-02 결과` -> `TR-04 결과 보존 가입` -> `기존 Home`

| 화면 | 핵심 정보 | 주요 행동 | 신뢰 장치 |
|---|---|---|---|
| TR-00 | 체험으로 가능한 것, 불가능한 것, 지급 조건 | 연락처 남기기 | 카드 등록 요구 여부, SNS 무연결, 결과 보존 조건 명시 |
| TR-01 | 이메일, 필수 동의, 선택 마케팅 동의 | 확인 메일 받기 | 선택 동의 미체크여도 체험 가능 |
| TR-02 | 마스킹 연락처, 확인 상태, 지급 상태 | 링크 열기 또는 코드 확인 | 재전송 간격과 연락처 수정 |
| TR-03 | 사용 가능 체험 잔액, 이번 예상, 남은 범위 | C-01부터 제작 | 가입 모달 자동 노출 금지, 품질 반려 무과금 |
| TR-04 | 결과, 남은 크레딧, 이어지는 데이터 | 계정 만들고 그대로 이어가기 또는 결과 받기 | 가입을 미뤄도 안내된 범위의 결과 전달 보장 |

가입 완료 뒤 결과물, 선택 이력, 남은 유효 체험 크레딧은 같은 작업공간에 이어진다. 가입을 취소하면 TR-03으로 돌아가며 이미 만든 결과를 즉시 삭제하지 않는다. 보존 기간이 끝나기 전 남은 기간과 내보내기 또는 가입 행동을 보여준다.

### 34.8 운영자 화면의 내부 테스트 구분

#### 34.8.1 표시와 집계 원칙

- `내부 테스트`는 운영자 전용 라벨이다. 고객 셸과 고객용 다운로드에는 노출하지 않는다.
- O-03 테넌트 행은 고객명 옆에 텍스트 배지 `내부 테스트`를 표시한다. 색만으로 구분하지 않는다.
- O-04 개요는 현재 분류, 변경 시각, 변경 주체, 사유를 보여준다.
- O-09 운영 루프의 기본 필터는 `실사용자만`이다. `내부 테스트만`, `모두 비교`를 선택할 수 있다.
- O-07 원가와 O-08 막힘은 내부 테스트를 숨기지 않고 기본값과 필터 상태를 명시한다. 실제 비용은 내부 테스트도 발생하므로 원가 총계에서 조용히 제외하지 않는다.
- 벤치마크·추천 근거로 승격되는 집계는 내부 테스트 제외값을 기본으로 한다. 비교 화면에는 두 집단 표본을 병렬로 표시할 수 있다.

#### 34.8.2 Happy 경로

`O-03 테넌트 선택` -> `O-04 개요` -> `분류 변경` -> `현재 영향 확인` -> `사유 입력` -> `변경 확인` -> `O-09 집계 재계산 상태 확인`

분류 변경 전 영향 목록은 운영 루프 추천 근거, 고객 지표, 내부 proof 보고, 원가 집계 중 바뀌는 것과 바뀌지 않는 것을 구분한다. 과거 원시 사건을 삭제하거나 이동했다고 말하지 않는다. 집계 관점만 분리한다.

### 34.12 레드팀과 셀프심문

#### 레드팀 1: 까다로운 고객

공격: 자율 발행을 켰다가 브랜드에 맞지 않는 게시물이 나가면 품질 게이트가 있다는 설명은 변명이 되지 않는다.

수정: 신규 테넌트 화면 추천은 승인 후 발행으로 두고, 자율 발행 전 M-02에서 채널·유형·계정·시각·실패 안전장치를 확인한다. 작업 단위 중지와 이번만 승인 전환을 열고, 품질 통과와 provider 발행 성공을 분리한다. unknown과 기존 실패 건은 자율 모드에서도 자동 재발행하지 않는다.

#### 레드팀 2: 개인정보에 민감한 체험 사용자

공격: 무료 크레딧을 미끼로 연락처와 광고 동의를 묶으면 리드 수집 다크패턴이다.

수정: 결과 전달·체험 운영 필수 동의와 마케팅 수신 선택 동의를 분리한다. 선택 동의를 하지 않아도 같은 체험을 제공하고, 입력 전에 목적·보관·삭제 경로를 보여준다.

#### 레드팀 3: 이탈하려는 고객

공격: ZIP 파일 하나를 주면서 취향 프로파일과 편집 지시서는 내부 식별자 덩어리라 다른 도구에서 쓸 수 없다.

수정: X-01은 Markdown·CSV·미리보기 인덱스를 필수로 정의한다. 취향은 축·가중치·근거·불확실성을 사람 문장으로, 편집 지시서는 결과별 컷·자막·효과·순서 표로 제공한다. JSON은 보조일 뿐 사람용 문서를 대체하지 않는다.

#### 레드팀 4: 회의적 데이터 담당자

공격: 내부 테스트 배지를 운영자가 임의로 바꾸면 성과가 좋은 표본만 실제 유저로 남기는 데이터 세탁이 가능하다.

수정: O-04에서 변경 주체·시각·사유와 전후값을 감사 이력으로 남기고, O-09는 현재 분류뿐 아니라 기간 내 분류 변경을 표시한다. 원시 사건은 삭제하지 않고 집계 관점만 바꾼다.

#### 셀프심문

질문: 이 결론이 틀렸다면 가장 그럴듯한 이유는 무엇인가?

답: 가장 load-bearing한 가정은 사용자가 테넌트·채널·콘텐츠 유형의 세 층 정책을 이해하고 실제 적용 모드를 예측할 수 있다는 것이다. override가 늘어나면 자율 발행을 껐다고 생각한 영상이 특정 채널에서 계속 나갈 수 있다.

수정: M-01의 규칙 편집보다 M-02의 최종 적용 결과를 승인 대상으로 둔다. 모든 제작·검수·발행 화면에서 `현재 모드 + 적용 출처`를 반복하고, 정책 변경 시 영향받는 대기 건을 먼저 보여준다. 설정 저장 성공 토스트만으로 종료하지 않는다.

두 번째 질문: 품질 반려 무과금이 공급자 원가를 무한히 떠안는 악용 경로가 되지 않는가?

답: 가능하다. 무과금은 고객 신뢰 원칙이지만 반복 자동 보정이 무한하면 우리 원가가 폭증한다.

수정: Q-01은 반복 횟수와 바뀐 점을 보여주고 같은 이유의 자동 반복을 중단한다. 반복 상한과 속도 제한 값은 화면에서 임의 확정하지 않고 운영 루프·기술설계 회수 항목으로 올렸다. 사용자에게는 무과금 원칙을 유지하되 다음 선택 변경이나 지원 경로로 전환한다.
