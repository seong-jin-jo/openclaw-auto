# 와이어프레임: 읽히는 본문과 상시 담당 v47

한 줄 결론: 1024는 왼쪽 탐색 56px과 본문:담당 70:30을 기본으로 하고, 390은 담당을 본문 아래에 두어 글자 단위 줄바꿈과 딱지 잘림을 없앤다.

## 1. 기존 구현 확인과 보존

| 확인 대상 | 실제 상태 | v47 판단 |
|---|---|---|
| `openclaw-auto-4room-v46.html` | 화면 131개, 오른쪽 담당 304px, 왼쪽 224px 기본, 가운데 흐름 3열 | 화면과 기능은 전량 유지. 1024 폭 규칙만 덧붙임 |
| `dashboard/src/components/layout/Sidebar.tsx` | 실제 항목과 그룹이 구현되어 있음 | 항목 삭제 없음. 1024에서 표현만 56px 레일로 축소 |
| `DESIGN.md` v24 | 1024와 1440 담당을 모두 304px로 규정 | v25에서 1024만 30% 이하, 최소 240px로 수정 |
| v46 검수 셸 | 카드 여백 A/B, 화면 선택, 저장, 미리보기, 복사 | 전부 유지 |

유지한 기존 기능: 두 층 헤더, 왼쪽 탐색 접기, 오른쪽 상시 담당, 화면 131개, 정상·내용 없음·불러오는 중·오류·내용 많음, 라이트·다크, 390·768·1024·1440, 선택·자동 저장·실제 미리보기·복사, 카드 여백 A/B.

## 2. 1024 구조

주축은 `row`다. 순서는 왼쪽 탐색 → 본문 → 상시 담당이다.

```text
┌──────────────────────────── 헤더 두 층 ────────────────────────────┐
├──────┬───────────────────────────────────────┬─────────────────────┤
│ 탐색 │ 본문 70%                              │ 상시 담당 30%       │
│ 56px │ 최소폭이 있는 세 카드                 │ 최소 240px          │
│      │                                       │                     │
│ [›]  │ 결과 152 | 정보 208 | 인계 152       │ 대화                │
│ 아이콘│ 딱지는 어절 단위로 여러 줄 허용       │ 선택지와 44px 입력   │
└──────┴───────────────────────────────────────┴─────────────────────┘
```

- Android canonical supporting pane의 840dp 이상 70:30을 본문 우선 비율의 출발점으로 차용한다.
- 왼쪽 탐색은 Apple HIG의 제한 폭 compact control 원칙대로 56px로 자동 축소한다.
- 사용자가 탐색을 펼치면 224px이 56px 레일 위로 임시 겹친다. 본문과 담당 폭은 움직이지 않는다.
- 상시 담당은 항상 보인다. 닫기, 임시 호출, 전체 화면 전환을 추가하지 않는다.
- 가운데 상세의 주축은 `row` 3열이다. 순서는 `지금 보는 결과 / 읽고 쌓는 정보 / 다음으로 넘김`이다.

## 3. 1440 구조

주축은 `row`다. v46 구조를 보존한다.

```text
┌────────────┬──────────────────────────────────────────┬───────────┐
│ 탐색       │ 본문                                     │ 담당      │
│ 224 또는 56│ 결과 / 읽고 쌓는 정보 / 다음으로 넘김    │ 304px     │
└────────────┴──────────────────────────────────────────┴───────────┘
```

본문 폭이 충분하므로 오른쪽 담당 304px과 사용자가 저장한 왼쪽 탐색 상태를 유지한다. v47의 70:30 강제는 1024에만 적용한다.

## 4. 390 구조

주축은 `column`이다. 순서는 헤더 → 본문 → 상시 담당이다.

```text
┌──────────── 헤더 두 층 ────────────┐
├────────────────────────────────────┤
│ 본문                               │
│ 받아온 묶음 › 다음 묶음            │
│ 읽는 정보 | 이번에 쌓임             │
│ 성과와 제작 정보 | 규칙 후보 | 승낙 │
├────────────────────────────────────┤
│ 상시 담당                          │
│ 내부 대화 스크롤, 44px 입력         │
└────────────────────────────────────┘
```

- Android compact 규칙대로 보조 패널을 본문 아래에 둔다.
- 결과 그림과 상세 인계 카드는 v46처럼 접지만, 받아온 묶음과 다음 묶음, 읽는 정보, 쌓이는 정보, 학습 고리 세 단계는 보존한다.
- 딱지는 11/16 이상이며 한 줄 말줄임을 쓰지 않는다. 어절을 먼저 지키고 필요한 만큼 카드 높이를 늘린다.

## 5. 긴 내용과 딱지 계약

| 대상 | 정상 | 내용 많음 | 금지 |
|---|---|---|---|
| 작업물 제목 | 어절 단위 1~2줄 | 카드 폭 안에서 3줄까지 | 한두 글자짜리 세로 열 |
| 정보 딱지 | 한 줄 또는 자연스러운 2줄 | 나머지 수를 별도 딱지로 표시 | `text-overflow:ellipsis`, 오른쪽 잘림 |
| 다음 묶음 | 어절 단위 1~2줄 | 카드 높이를 늘림 | 단어마다 강제 줄바꿈 |
| 학습 고리 | 세 단계 모두 표시 | 연결선을 먼저 줄임 | 단계 이름 삭제 또는 글자 단위 분절 |

적용 규칙: `white-space: normal`, `word-break: keep-all`, `overflow-wrap: break-word`. 모든 격자 칸은 `min-width:0`이며 카드와 딱지는 overflow로 내용을 숨기지 않는다.

## 6. 상태와 인터랙션

| 상태 | 본문 | 상시 담당 | 다음 행동 |
|---|---|---|---|
| 정상 | 현재 결과와 세 열 | 현재 단계 문맥 | 다음 단계로 또는 대화 |
| 내용 없음 | 첫 글 또는 영상 갈래 | 무엇부터 고를지 질문 | 글로 만들기, 영상으로 만들기 |
| 불러오는 중 | 자리와 열 폭 고정 | 같은 열에서 진행 설명 | 자동 복구 뒤 현재 장면 유지 |
| 오류 | 보존된 원본과 늦은 성과 구분 | 복구 선택 안내 | 성과 다시 받기, 원본 보기 |
| 내용 많음 | 상위 항목과 접힌 수 표시 | 패널 내부만 스크롤 | 현재 판단 계속 |

1024 탐색 펼치기는 화면, 단계, 대화, 카드 여백 A/B를 바꾸지 않는다. 뷰포트를 바꾸면 1024 임시 펼침만 닫고 저장된 데스크톱 탐색 상태는 보존한다.

## 7. 공식 벤치마크와 판단

| 제품 | 공식 문서에서 확인한 규칙 | 차용 | 기각 |
|---|---|---|---|
| Android canonical layouts | 600dp 미만 아래 또는 bottom sheet, 600dp 이상 50:50, 840dp 이상 70:30 | 1024의 70:30, 390의 아래 배치 | 1024의 50:50은 본문 우선순위와 불일치 |
| Apple HIG Sidebars | 제한 폭 compact control, 창 크기에 따른 자동 숨김 | 1024 왼쪽 56px | 오른쪽 담당까지 숨기는 안 |
| Figma UI3 | hover-only 패널의 불안정성을 수정, 접기와 크기 조절. 공개 숫자 없음 | 안정된 위치와 폭 | hover 때만 나타나는 담당 |
| Notion side peek | 오른쪽에서 열어 왼쪽 목록 문맥 유지. 공개 숫자 없음 | 본문 문맥 보존 | 전체 화면 전환 |
| Intercom Messenger | 데스크톱 최소 20px 여백, 크기 사용자 지정 불가 | 가장자리 여백 원칙 | 고정 overlay로 본문 폭 경쟁 |
| Linear Peek | Space 임시 열기, Esc 닫기. 공개 숫자 없음 | 상세를 임시 층에 두는 아이디어만 참고 | R101과 충돌하는 임시 담당 |

## 8. 레드팀, 셀프심문, 회수

레드팀: 까다로운 고객은 1024에서 세 카드와 오른쪽 담당을 모두 지키려다 숫자만 바꾼 절충안이 됐다고 공격한다. 대응: 왼쪽 탐색에서 168px을 먼저 회수하고, 담당은 30% 상한, 카드에는 역할별 최소폭을 부여했다. 폭이 더 줄면 390 구조로 전환해 수평 경쟁을 없앤다.

셀프심문: 이 결론이 틀렸다면 가장 그럴듯한 이유는 Android의 dp 규칙을 CSS px에 기계적으로 옮긴 것이다. 대응: 70:30은 비율 근거로만 사용하고, 최종 합격은 Chrome에서 1440·1024·390 실렌더의 담당 비율, 글자 줄, 딱지 overflow를 직접 측정하고 그림을 확인해 판정한다.

회수 필요: 없음. API, DB, 아키텍처, 비용, 배포 결정을 만들지 않았다.
