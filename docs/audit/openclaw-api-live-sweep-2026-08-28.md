# openclaw API 실사 점검 2026-08-28

한 줄 결론: 도는 앱에 붙어 읽기 경로 84개를 전부 두드린 결과 79개가 정상이고, 고장 2개를 찾아 그 자리에서 고쳤으며, 나머지 3개는 고장이 아니라 필요한 값을 주지 않은 내 호출 탓이었다.

## 점검 방법

`dashboard/src/app/api/**/route.ts` 중 읽기(GET)를 내보내는 경로 84개에 실제 HTTP 요청을 보냈다. 서버는 `localhost:3456` 에서 실제로 돌고 있었고, 데이터베이스도 붙어 있었다. 테스트 통과가 아니라 관찰이다.

| 결과 | 건수 |

| 정상 | 79 |
| 고장이었고 이번에 고침 | 2 |
| 인증 경계 밖(의도된 거절) | 2 |
| 값을 주면 정상 | 3 |

## 고친 것

### 하나. Google 로그인 준비 안 됨을 서버 고장으로 답하던 것

`/api/auth/google` 이 Supabase 주소가 없을 때 500 으로 답했다. 설정이 아직 없는 것은 고장이 아니다. 500 으로 답하면 감시 도구가 이것을 영원히 장애로 읽는다. 준비되지 않음을 뜻하는 503 으로 바꾸고 회귀 테스트를 붙였다.

### 둘. 회원 장부 하나가 없으면 운영자 화면 전체가 죽던 것

`/api/operator/customers` 는 작업 공간 목록과 회원 장부를 함께 읽는다. 회원 장부는 Supabase 가 있는 배포에만 있는데, 그 조회가 실패하면 이미 잘 읽어 온 작업 공간 목록까지 버리고 빈 응답에 500 을 얹었다.

한쪽이 없으면 없다고 밝히고 나머지를 주도록 바꿨다. 이제 작업 공간은 정상으로 오고, 회원 장부를 못 읽었다는 사실이 응답에 함께 담긴다.

관찰: 고치기 전 500 과 빈 목록, 고친 뒤 200 과 작업 공간 1건 그리고 못 읽은 사유.

## 고장이 아니었던 것

- `/api/isolation-proof`, `/api/publish`: 고객 토큰만으로는 닿을 수 없는 경로다. 거절이 정상이다.
- `/api/connect/readiness`, `/api/studio/brand-setup`, `/api/brand/sync-repo`: 작업 공간을 지정하지 않아 거절당했다. 지정하니 전부 정상이다.
- `/api/tiktok/creator-info`, `/api/tiktok/publish-status`: 작업 공간을 지정해도 거절한다. 이 경로는 주소값이 아니라 토큰으로 작업 공간을 가리기 때문이다. 계약이 그렇게 되어 있다.

## 남은 것

studio 생성 장부가 프로세스 메모리에 있다. 이것은 이 점검의 대상이 아니었고 별도로 회장 결정을 기다린다.
