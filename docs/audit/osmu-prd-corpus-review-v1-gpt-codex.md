## PRD 리뷰: Studio와 OpenClaw PRD 코퍼스 v1

한 줄 판정: **반려, 15/25.** 현재 파이프라인이 승인 산출물로 가리키는 두 PRD는 사업계획 v1.3과 R71·R85~R89에 정면으로 어긋나며, 최신 v3 두 문서도 `99/99 반영`을 입증하지 못한다.

### 30초 다이제스트: 이 문서가 무엇을 약속하는가

1. Studio는 생성·편집·채널별 창작 문구를 맡고, OpenClaw는 계정·예약·발행·성과를 맡는 두 서비스 구조다.
2. 사업계획 v1.3은 `S0·S1·U2·U3·X4·L5·R6` 일곱 층, 브랜드 층 금지, 작업 공간 복제, Studio 단독 판매를 정본으로 확정했다.
3. 현재 승인 핀인 Studio v1.2.1과 OpenClaw v8.2.1은 Studio 단독 판매를 비범위로 잠갔고, 새 일곱 층과 R79~R99를 반영하지 않았다.
4. 최신 `생성 v3.0`과 `운영 v3.0`은 새 정본을 가져왔지만, 옛 `열두 조건`, 채널 문구 상충, 알림·모델 상호작용 누락을 둔 채 `99/99`, `25/25`를 선언했다.
5. 현 상태에서 design·eng-design을 계속하면 서로 다른 제품을 구현하게 된다. plan을 재개방하고 라인별 현행 PRD를 하나씩 다시 핀해야 한다.

### 3. 같은 폴더의 현행형 PRD 여섯 개가 폐기된 층 구조를 계속 노출한다

| 잔재 | 파일 | 대표 위치 | 판정 |
|---|---|---|---|
| 옛 `L0~L6` | `studio/docs/prd-studio-v2.0.md`, `prd-studio-v3.0.md`, `docs/prd-openclaw-v2.0.md`, `prd-openclaw-v3.0.md` | Studio v2 `§6.1`, Studio v3 `§6.2`, OpenClaw v2 `§7`, OpenClaw v3 `§6~§7` | R69·R84~R86와 사업계획 v1.3에 어긋남 |
| `U3 브랜드`, `U4 작업 공간` | `studio/docs/prd-studio-생성-v2.0.md`, `docs/prd-openclaw-운영-v2.0.md` | Studio v2 `§4.2·§13`, OpenClaw v2 `§4.2·§13` | R85가 폐기한 브랜드 층을 그대로 둠 |
| 현행 파일 선택 규칙 부재 | 18개 PRD 전체 | `studio/docs/`, `docs/` | 이름만으로는 승인본·최신 후보·폐기본을 구분하지 못함 |

이 문제는 문장 정리 수준이 아니다. 이미 `pipeline-state.studio.md`의 기술설계 산출물이 R85·R86 이전 전제로 재작업 필요라고 기록돼 있다. 잘못된 PRD 선택이 실제 하류 회귀로 이어졌다는 증거다.

수정은 다음 두 단계가 필요하다.

1. 라인별 현행 PRD 한 개와 승인 SHA를 manifest에 고정한다.
2. 나머지는 `archive/`로 옮기고 문서 첫머리에 `superseded_by`를 남긴다.

### 4. 최신 v3의 `99/99 반영`은 요구 의미가 아니라 행 개수를 센 결과다

| 파일:절 | 주장 | 반증 |
|---|---|---|
| Studio 최신 `§13`, line 801, `§17` | 99건 전량 대조, 누락 0, 99/99 반영 | R60은 `§8·§9에 연결`이라고만 쓰지만 최초 진입·며칠 주기·추천 알림을 정의한 FR·AC가 없다 |
| OpenClaw 최신 `§13`, line 858, `§17` | 99건 전량 대조, 누락 0, 99/99 반영 | R63은 여러 FR 번호를 나열하지만 OpenClaw와 모델의 상호작용 도식이 없다 |
| 두 최신 문서의 수용기준 | FR마다 Given/When/Then이 있다 | 다수 Given이 `관련 회원·작업 공간과 필요한 외부 상태가 준비됨`, Then이 `실패 상태를 성공으로 위장하지 않음`으로 반복된다. 요구별 초기상태와 관찰 결과가 아니다 |

[Cucumber 공식 문서](https://cucumber.io/docs/gherkin/reference/)는 Given을 잘 정의된 초기상태, When을 사건, Then을 사용자나 외부 시스템이 관찰할 결과로 설명한다. 또한 한 예시를 3~5단계로 유지하고 모호한 중복 표현을 피하라고 권한다. 현재의 반복 문장은 형식만 Gherkin이고 요구의 검증 계약으로 기능하지 않는다.

### 5. 최신 Studio PRD 안에 폐기된 조건 구조가 한 줄 살아 있다

`studio/docs/prd-studio-생성-v3.0.md:468`은 `학습 규칙은 열두 조건을 갖고`라고 요구한다. 그러나 사업계획 v1.3 §3.4는 일곱 층과 작업 공간 복제만 정본으로 두고, 미승인 조건표 추가를 금지한다. 같은 PRD가 `다른 이름이나 번호를 추가하지 않는다`고 쓴 뒤 열두 조건을 추가했으므로 내부 모순이다.

고치는 법은 열두 조건을 삭제하는 데서 끝나지 않는다. 적용 범위는 `현재 작업 공간`, `승낙된 L5`, `이번 R6`, `선택한 X4`, `S0·U3 금지선`으로 다시 써야 하고, 어떤 값이 달라질 때 자동 적용을 막는지 사업계획의 층 의미로 정의해야 한다.

### 6. 채널별 문구 계약이 같은 문서 안에서 충돌한다

| 위치 | 문장 | 판정 |
|---|---|---|
| Studio 최신 `§13 R38` | 단독 사용자는 원본과 선택한 채널 문구를 함께 내려받는다 | R88과 사업계획 §3.2에 부합 |
| Studio 최신 `R38 검증 카드` | 원본만 받는 Studio 단독 경로에는 채널 문구가 없다 | 위 문장과 충돌 |
| OpenClaw 최신 `FR-OP-006` | 단독 사용자도 선택 채널 문구를 원본과 함께 내려받는다 | R88에 부합 |
| OpenClaw 최신 `R38 검증 카드` | 원본만 받는 Studio 단독 경로에는 채널 문구가 없다 | 위 수용기준과 충돌 |

원본만 받는 선택과 원본에 채널 문구를 추가로 받는 선택은 동시에 존재할 수 있다. 문서는 이를 `채널 중립 원본 필수 + 선택 채널 사본 선택`으로 한 계약에 묶어야 한다.

### 7. 같은 파일에서 v3.0과 v3.0-r1을 함께 선언해 버전 핀이 무효다

두 최신 파일은 파일명과 제목이 v3.0인데 개정 이력에는 v3.0-r1을 별도 버전으로 기록한다. SHA를 별도로 고정하지 않으면 어느 v3.0을 검토·승인했는지 복원할 수 없다. 수정본은 새 파일명과 semver로 내고 기존 파일은 변경하지 않아야 한다.

### 요구 대조 결론

최신 v3 두 문서에서 최소한 R24, R50, R54~R56, R60, R62, R63은 제품 요구 또는 관찰 가능한 수용기준이 누락됐다. R38·R88은 같은 문서 안에서 이탈했고, R26·R32·R37·R65는 후속 요구와 충돌하지만 대장에 명시적인 superseded 관계가 없다. 따라서 `99/99 반영`은 철회해야 한다.

## 리스크·빈틈 Top 3

1. **잘못된 정본으로 하류가 계속 움직인다.** Studio는 eng-design, OpenClaw는 design인데 두 승인 핀이 새 사업계획 이전 제품을 정의한다. 이미 기술설계 재작업 필요가 상태 파일에 기록됐다.
2. **단독 Studio의 운영 원가가 상품 정의보다 늦다.** 회원·인증·workspace·L5·결제·환불·지원이 독립 상품에 필요하지만 최신 Studio v3는 `화면·인증·과금·지원 어댑터만 붙인다`고 축약한다. 이 네 영역은 어댑터가 아니라 고객 계약이다.
3. **요구 추적표가 결함을 숨긴다.** 모든 요구에 같은 출처와 같은 종료 문장을 붙여 누락과 충돌을 `경계 반영`으로 포장한다. 이 상태로는 독립 QA가 무엇을 관찰해야 하는지 알 수 없다.

## 회장이 지금 결정할 것

### 1. 어느 PRD 계열을 현행으로 삼을지

- 추천: `생성 v3.0`과 `운영 v3.0`을 리테이크 입력으로 삼되 현재 파일을 승인하지 않는다. 본 리뷰의 결함을 고친 새 MAJOR 버전을 만든 뒤 라인별 한 개만 승인 핀으로 고정한다.
- 하면: 사업계획 v1.3과 R01~R99를 기준으로 두 라인이 같은 제품을 구현한다.
- 안 하면: v1.2.1·v8.2.1의 단독 판매 금지와 최신 v3의 단독 판매 필수가 동시에 하류에 남는다.
- 복사 답변: `두 라인의 plan을 재개방하고 최신 v3를 리테이크 입력으로 사용하되, 결함을 고친 새 MAJOR PRD만 승인 핀으로 올린다.`

### 2. Studio 단독 상품의 제품 준비와 판매 시점을 분리할지

- 추천: 제품 구조와 수용기준에는 독립 가입·작업 공간·학습·다운로드·과금·지원을 지금 포함하고, 실제 공개 판매는 결합 상품 proof 뒤로 둔다.
- 하면: R71의 독립성은 지키면서 사업계획 §4.6의 출시 순서도 지킨다.
- 안 하면: `첫날부터 계약 가능`으로 가면 결제·환불·지원 범위가 즉시 커지고, 비범위로 두면 R71을 다시 위반한다.
- 복사 답변: `Studio는 지금부터 독립 상품으로 설계하되 공개 판매는 결합 상품 proof 뒤에 연다.`

### 3. 충돌한 옛 요구의 효력을 대장에 명시할지

- 추천: R26은 R89, R31은 R88, R32는 R71·R85, R37은 R43, R65는 R71·R89가 대체한다고 대장에 명시한다.
- 하면: 리뷰어와 구현자가 불가능한 동시 충족을 시도하지 않는다.
- 안 하면: PRD는 어느 쪽을 골라도 다른 요구를 위반하고도 `99/99`라고 쓸 수 있다.
- 복사 답변: `R26·R31·R32·R37·R65의 superseded_by 관계를 요구사항 대장에 명시한다.`

## 반박: 가장 강한 전제에 대한 steelman 공격

가장 강한 전제는 **Studio와 OpenClaw를 분리해도 사용자는 하나의 학습형 제품으로 느끼고, Studio는 동시에 독립 상품이 될 수 있다**는 것이다.

가장 강한 반대는 이렇다. 독립 Studio가 자기 회원·작업 공간·L5·과금·지원을 가지면서 결합 상품에서는 OpenClaw도 회원·작업 공간·성과·발행 정책을 가진다. 그러면 같은 사람과 같은 작업 공간이 두 서비스에서 다른 상태를 가질 수 있다. `현재 범위 투영`과 `밀기형 사본`은 이중 진실을 없애지 않고 동기화 문제로 바꿀 뿐이다. 단독 판매가 성장할수록 어느 서비스가 회원 삭제, workspace 복제, 금지선 변경, L5 승낙, 환불을 최종 확정하는지에 대한 고객 분쟁이 커진다.

이 공격을 견디려면 PRD가 서비스별 저장소를 먼저 정할 것이 아니라 사용자 사건별 단일 결정권을 정해야 한다. 최소한 `가입`, `workspace 생성·복제`, `U3 금지선 변경`, `L5 승낙·철회`, `단독 결제·환불`, `결합 상품 해지` 여섯 사건에 대해 누가 최종 사용자 응답을 하고 다른 서비스 장애 때 무엇을 보장하는지 수용기준이 필요하다. 현재 문서에는 이 계약이 없다.

## 전달 가능성 + 더 나은 방법

- 전달: **불가.** 18개 현행형 PRD, 승인 상태 모순, 내부 코드명·층 약어, 중복 99개 카드 때문에 클라이언트나 다른 팀이 어떤 문서를 따라야 하는지 알 수 없다.
- 인간 이해가능성: **어려움.** 최신 두 문서만 약 3,300줄이며, 핵심 누락이 반복 카드 사이에 묻힌다.
- 더 나은 방법 1: 라인별 30쪽 안팎의 본문과 별도 기계 판독 RTM으로 분리한다. 본문은 제품 약속·범위·흐름·BM·리스크를 설명하고, RTM은 `요구 ID → FR → 고유 AC → 검증 단계 → 상태`만 가진다.
- 더 나은 방법 2: 단독 Studio와 결합 상품을 별도 제품으로 쪼개지 말고 같은 Studio capability에 `standalone customer shell`과 `OpenClaw orchestration shell` 두 배치를 정의한다. 공통 capability는 한 번만 요구하고 회원·과금·지원 차이만 배치별 AC로 둔다.

### 벤치마크에서 확인된 추가 빈틈

1. **상품 정의가 두 겹이다.** 경쟁 제품은 한 문장 약속과 과금 단위가 같은 표에 있다. Studio 최신 PRD는 `생성·편집·학습`, OpenClaw 최신 PRD는 `발행·성과`를 말하지만 결합 상품과 단독 상품 중 구매자가 실제로 무엇을 결제하는지 한 개의 offer로 닫지 못했다.
2. **요금 계약이 사업계획에서 PRD로 내려오지 않았다.** 사업계획 v1.3 §4.3은 무료 0원, 스타터 19,900원, 프로 99,000원, 기업 390,000원부터와 편수·작업 공간을 적었다. Studio PRD `§10`은 이를 `가격 가설`로 물리고 절대 가격을 쓰지 않아 사업계획의 표시가와 PRD의 제품 계약이 분리됐다.
3. **온보딩 성공지표가 없다.** Predis는 `2분 설정`, Copy.ai는 `15일차 운영`, Jasper와 Ocoya는 `7일 체험`을 판매 약속으로 드러낸다. 우리 PRD는 질문을 한 번에 하나씩 받고 채널 연결을 미루는 흐름은 있지만 `가입 후 N분 안에 실제 결과 한 편`, `필수 입력 N개 이하`, `무료 결과 확인 전 결제 없음` 같은 time-to-value 수용기준이 없다.
4. **차별화가 검증 가능한 문장으로 내려오지 않았다.** 우리 강점 후보는 `채널 연결 전 제작`, `성과가 승낙형 L5 후보로 환류`, `Studio 단독과 결합 상품의 동일 제작 능력`이다. 이 셋을 경쟁 제품보다 낫다고 주장하려면 첫 결과 시간, 수정 횟수 감소, 승낙률, 다음 콘텐츠 반영률을 파일럿 KPI로 고정해야 한다.

이번 조사에서 차용할 것은 세 가지다. 상품 한 문장과 과금 단위를 붙여 쓰기, 첫 가치까지의 입력·시간·결과를 수치로 약속하기, workspace·브랜드·credits 중 무엇이 확장 요금의 기준인지 공개하기다. 차용하지 않을 것은 경쟁사의 즉시 자동 발행 기본값이다. 우리 R89는 제작을 채널 연결보다 먼저 두어 계정 연결 실패가 첫 가치 경험을 막지 않게 하므로 유지할 근거가 있다.
