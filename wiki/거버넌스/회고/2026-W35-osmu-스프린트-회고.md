# OSMU 2026-W35 스프린트 회고 (2026-08-28 ~ 2026-08-31)

## 한 줄 판정

**제품이 동작하지 않는 상태에서 그 위에 UI 를 4일간 쌓았다.**
회장이 실사용으로 그것을 두 번 드러냈고, 두 번 다 컨트롤러가 사전조건을 확인하지 않은 것이 원인이었다.

## 숫자로 본 결과

| 지표 | 값 |
|---|---|
| 회장 요청 대조 (확정요구 + 1·2차 피드백) | 266건 중 충족 128 · 부분 60 · 미충족 48 · 확인불가 30 |
| 2차 실사용 피드백 | 31건 중 충족 1건 |
| 회장 평가 | neg 1점 (2026-08-31 적립) |
| 배포 | 성공 4회, 실패 5회 |
| 병합 | PR 36·37·38·39 |
| 전체 시험 | 205 파일 1,542건 통과 |
| VM 컨테이너 | 12개 → 2개, 디스크 81% → 36% |

## 잘 된 것

1. **로깅을 고치자 몇 시간 만에 원인이 나왔다.**
   long-lived token 교환 실패 시 provider 응답을 버리던 것을 고쳤더니
   회장이 재연결한 직후 Meta 가 준 문장이 그대로 찍혔다
   (`threads_basic permission ... list of Threads testers`).
   ⇒ **관측 가능성에 투자한 것이 가장 빨리 회수됐다.**
2. **배포 교착을 게이트를 끄지 않고 풀었다.**
   검사를 제자리로 옮기고 장부 단조성 검사를 추가했다.
   컨트롤러가 "올라갔다 내려간 상태와 아직 안 올라간 상태는 다르다"를 지적해
   워커의 과잉 완화를 잡았다.
3. **워커 주장을 그대로 릴레이하지 않은 사례가 여럿 있었다.**
   "운영 빌드가 죽는다"는 경보가 실은 다른 조의 작업중 파일이었던 것,
   "간격 유틸리티가 전역으로 죽는다"는 전제가 틀렸던 것을 컨트롤러가 잡았다.
4. **성과실 무한 렌더를 시험 건너뛰기로 덮지 않고 뿌리를 고쳤다.**
   회장이 첫 방문에서 화면이 멎을 수 있던 자리였다.

## 못 한 것 (뿌리 순서)

1. **ADR-004 를 안 읽고 그 위에 개발했다.**
   "고객은 API 발급 없이 OAuth 연결, 전제는 App Review 1회" 가 이미 적혀 있었다.
   위임 프롬프트에 넣지 않아 워커도 몰랐다.
2. **배포 환경에서 로그인부터 발행까지 한 번도 밟지 않고 "쓰실 수 있습니다"라고 보고했다.**
   HTTP 200 을 기능 동작의 증거로 취급했다.
3. **생성이 LLM 을 부르지 않고 문자열 템플릿이라는 것을 4일 내내 몰랐다.**
   그 위에 편집실, 발행실, 파생 생성을 얹었다.
4. **회장 발화를 요약본으로만 남기고 위임했다.** 항목 수가 어긋났다(생성실 10 vs 11).
5. **비표준 용어를 10회 지적받고 반복했다.** 규칙을 확대 해석한 결과다.

## 아직 이빨이 없는 것 (다음 스프린트)

- **배포 후 실동작 확인 강제.** 지금은 다짐뿐이다. 완료 판정 위반의 재발 경로다.
- **원문 박제 강제.** 훅이 생겼으나 백필은 사람 손이다.
- **항목별 대조 형식 강제.** 프롬프트 규약일 뿐 검사가 없다.
- **외부 콘솔 의존 항목 목록.** Supabase Redirect URL, Meta 테스터 등록,
  채널별 redirect URI 등록이 어디에도 관리되지 않는다.

## 다음 스프린트 우선순위

1. **실제 LLM 연동 완주.** 이것 없이는 나머지가 전부 껍데기다.
2. **Meta App Review 제출.** 고객이 API 발급 없이 쓰는 유일한 길이다.
3. 배포 환경 전체 플로우를 컨트롤러가 직접 통과.
4. 미충족 48건 + 부분 60건 순차 처리.
5. 위 "이빨 없는 것" 넷 중 완료 판정 강제부터.
