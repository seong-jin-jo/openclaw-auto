# 두 서비스 경계: studio-service와 openclaw-service

> 상태: **회장 확정 진행 중**(2026-08-15). 상세 근거와 기각안은 `docs/제품구조-결정-2026-08-15.md`가 정본이며, 이 페이지는 그 요약이다.

## 제품 구조

| 이름 | 무엇 | 화면 | 데이터베이스 |
|---|---|---|---|
| studio-service | 제작, 편집, 취향 학습 | 1단계 없음(headless). 2단계에 자체 화면과 단독 상품 | 있음 |
| openclaw-service | 채널 연결, 예약, 발행, 성과 수집 | 전부 소유(1단계의 유일한 소비자 화면) | 있음 |
| studio-engine, openclaw | 각 서비스의 엔진 | 해당 없음 | 없음 |

의존 방향은 **openclaw-service에서 studio-service로 단방향**이다. studio는 openclaw를 호출하지 않는다.

## 1차 목표

openclaw-service를 완성하고 studio-service API를 구현해서, 해줘단타와 제로원 인사이트의 콘텐츠를 만들어 여러 채널에 발행한다. 우리 자신이 첫 사용자이고 그 콘텐츠가 제품의 증거물이 된다.

## 관심사 분리의 기준 세 가지 (판정용)

헷갈릴 때 순서대로 던진다. 하나라도 studio에 걸리면 studio다.

1. **유저의 소셜 계정 자격증명이 필요한가.** 필요하면 openclaw. 보안 경계다.
2. **창작 정보(브랜드킷, 금지선, 취향 프로파일, 편집 지시서)를 읽거나 쓰는가.** 그렇다면 studio. 브랜드 일관성 경계다.
3. **미디어 바이트를 직접 만지는가.** 그렇다면 studio. 구현 능력 경계다.

세 기준이 같은 선을 그리므로 그 선이 옳다.

## OpenClaw는 제3자 오픈소스다

`github.com/openclaw/openclaw`, MIT, 2026.6.2. "Multi-channel AI gateway with extensible messaging integrations"이며 우리 레포 `openclaw/`에 벤더링돼 있다. **우리가 만든 것은 `extensions/`(채널 도구), `dashboard/`(화면), `studio/`다.** 우리가 공개할 수 있는 것도 그쪽이다.

OpenClaw가 제공하는 것은 예약 실행, 에이전트 실행, 모델 라우팅과 대체, 플러그인 방식 도구 확장(`extensions/<이름>/openclaw.plugin.json`) 네 가지다. 이 덕에 채널 하나 추가가 폴더 하나 추가가 된다.

**위험**: 상용 서비스가 제3자 런타임 위에 서고, 벤더링 사본의 상류 갱신 절차가 아직 없다. PRD 리스크 장에 반영한다.

**studio-service는 OpenClaw 런타임을 쓰지 않는다.** 개발자용 API로 팔 때 제3자 런타임 설치를 요구하게 되고, 제작은 결정론적 렌더라 에이전트 런타임이 아니라 일반 작업 큐가 맞으며, 런타임 장애가 제작까지 번지지 않아야 하기 때문이다.

## 소유권 경계

기준은 **studio가 미디어 바이트를 다루는 유일한 곳**이라는 것이다.

| 작업 | 소유 |
|---|---|
| 컷 분해, 소재 생성, 편집 지시서 작성 | studio 생성실 |
| 30초에 맞추려고 영상을 다시 만드는 것 | studio 생성실. 새로 만드는 것이므로 |
| 자르기, 크롭, 재인코딩, 자막 합성, 재렌더 | studio 편집실 |
| 크기·재생 시간·비율을 규격에 맞추는 것 | studio 편집실 |
| 롱폼에서 어디를 자를지 고르기 | studio |
| **채널별 제목, 소개, 해시태그, 첫 댓글** | **openclaw 발행실** (2026-08-19 회장 확정으로 studio에서 이동) |
| 채널 규격 정보 제공(글자수 상한, 해시태그 개수, 지원 비율) | openclaw |
| 예약 시각, 계정 선택, 발행 실행, 성과 수집 | openclaw |
| 유저가 올린 완성 파일을 손대지 않고 발행 | openclaw |
| 브랜드 가이드와 톤, 금지선 | 어느 서비스도 소유하지 않는다. **공통 학습 정보**로 두고 생성·편집·발행·성과가 모두 읽는다 |

### 제목과 해시태그를 발행실로 옮긴 이유 (회장 확정 2026-08-19)

회장 원문: "studio service만 단독으로 쓴다고 하면 SNS 발행은 생각하지 않을 수도 있는데 여기에 해시태그 제목 소개까지 나오는게 오히려 역할 분리를 해친다."

- studio는 콘텐츠를 만드는 엔진이다. 나중에 개발자용으로 단독 판매할 때, 그 고객은 SNS 발행을 안 할 수도 있다. 그런 고객에게 해시태그가 딸려 나오면 studio는 콘텐츠 엔진이 아니라 SNS 도구가 된다. 제품 경계가 흐려진다.
- 제목·소개·해시태그는 **발행 시점에만 알 수 있는 것**에 좌우된다. 지금 뜨는 태그, 그 계정의 최근 반응, 올리는 시각. 만들 때 알 수 없다.
- 발행실이 쓰되 최신 상태로 갱신해 내보낸다.

**톤이 갈릴 걱정은 톤을 공통 학습 정보로 올려서 해소한다.** 브랜드 목소리와 금지선이 어느 한 서비스 소유가 아니라 모두가 읽는 헌법이므로, 발행실이 캡션을 써도 같은 목소리가 난다. 그래서 학습 정보의 층계 분리와 계약이 이 구조의 핵심이다.

### 자막 오타를 고칠 때

생성실은 관여하지 않는다. 자막은 영상에 구워진 바이트이므로 **편집실**에서 고쳐 발행실로 보낸다.

### 편집실의 조정 방식 (회장 확정 2026-08-19)

손으로 타임라인을 만지는 편집 프로그램이 되면 안 된다. **대시보드에서 결과를 재생해 보면서 대화로 지시하거나 미리 준비된 선택지를 고르는 방식**으로 조정한다. 규격에서 오는 조정은 자동으로 맞추고, 사람 판단이 필요한 것만 지시로 바꾼다.

## studio의 두 모드

| 모드 | 입력 | 하는 일 |
|---|---|---|
| 생성 | 주제와 취향 프로파일 | 무에서 만든다. A/B/C 후보를 내고 강제 선택으로 학습 |
| 편집 | 이미 있는 결과물과 수정 지시 | 원본을 유지하고 지시만 반영. 수정 지시는 약한 학습 신호 |

### 편집 비용

편집 지시서가 있는 우리 산출물을 고칠 때, 자막과 이펙트와 컷 조정은 **크레딧이 들지 않는다.** 로컬 렌더만 다시 하기 때문이다. 나레이션 문구 수정과 소재 교체만 해당 컷 단위로 과금된다.

경쟁 도구는 완성 파일만 남기므로 수정이 곧 재생성이다. 우리는 수정이 재렌더다. 원가 차이가 여기서 벌어진다.

## 채널 지식과 채널별 생성

openclaw는 **채널 규격 카탈로그**(글자수 상한, 해시태그 개수, 지원 비율, 길이 상한)를 노출하고, studio는 그것을 읽어 규격에 맞게 만든다. 플랫폼이 규칙을 바꾸면 openclaw만 고친다. 플랫폼 지식이 두 곳에 복제되지 않는다.

제작은 **채널 중립 마스터 하나에 채널 파생 여럿** 구조다. 채널을 나중에 추가해도 마스터가 있으므로 파생만 더 뽑으면 된다.

채널을 여러 개 골라도 크레딧은 거의 안 든다. 비율 변경과 길이 변경은 소재를 재사용하므로 재렌더뿐이고, 채널별 텍스트는 한 번 호출로 함께 만든다.

## 시장 범위와 언어 (회장 확정 2026-08-15)

고객면과 출력 언어는 다른 층이다.

| 층 | 결정 |
|---|---|
| 가입, 결제, 지원, 랜딩 | 한국어 하나 |
| 출력 콘텐츠 언어 | 다국어. 한국인 고객 중 영어권, 일본, 태국을 노리는 사람이 실재한다 |

출력 언어는 **요청 파라미터**다. 채널 규격과 같은 급의 제약이며 취향 프로파일이 아니다. 단, 취향 프로파일은 언어별로 갈라진다. 한국어에서 잘 먹은 훅이 일본어에서 그대로 먹지 않는다.

품질 보증 경계: 한국어와 영어만 우리가 판정한다. 그 외 언어는 원어민 검수를 하지 않는다고 제품 문구에 명시한다.

데이터 모델에는 locale, currency, timezone, tax region, policy version을 1단계부터 넣는다. 나중에 붙이면 마이그레이션이 비싸다. 반면 다국가 self-serve 결제와 24시간 지원은 열지 않는다.

## 후보 제시 비용 구조 (회장 확정 2026-08-15)

후보 3개를 모두 완성본으로 뽑으면 해당 컷 원가가 3배가 된다. 그래서 **저해상도 후보 3개, 선택된 하나만 고해상도**다. 선택하지 않은 후보를 나중에 고해상도로 뽑으면 추가 과금이다.

미검증: 저해상도 프리뷰가 판단 가능한 수준인지 실측 전이다. 기술설계 전에 실물 비교 실험이 필요하다.

## openclaw의 본질

발행 버튼이 아니라 **외부 플랫폼과의 계약을 대신 감당하는 층**이다. 토큰 수명 관리, 플랫폼별 예외와 호출 한도, 재시도와 중복 방지, 예약 실행 신뢰성, 성과 지표 정규화가 실제 내용이며 플랫폼이 API를 바꾸면 계속 따라가야 한다.

studio가 직접 발행하지 않는 이유는 세 가지다. studio가 유저 소셜 토큰을 갖게 되면 개발자용 제작 API로 팔 수 없고, 이미 완성된 채널 15종 구현을 버리게 되며, 플랫폼 변경의 충격이 제작 코드로 번진다.

## studio 외부 접점 5개

신호 넣기, 제작 요청, 선택 기록, 취향 상태 조회, 소재 반입.

모든 학습 신호는 입구 하나로 받는다. 공통 봉투는 `{ tenant, source, kind, subject_ref, payload, observed_at }`이다. **생성 경로는 신호를 직접 읽지 않고 취향 프로파일만 읽는다.**

소재와 신호는 다른 것이다. 소재는 만들기의 재료(롱폼 원본, 이미지, 목소리)이고, 신호는 취향을 바꾸는 사건(어느 후보를 골랐는지, 성과가 얼마였는지)이다.

## 인증과 과금

소비자는 openclaw-service에 한 번만 가입한다. 소셜 로그인을 쓴다. openclaw-service가 studio 테넌트를 자동으로 만들며, 두 서비스 사이는 서버 대 서버 키다. 유저 자격증명은 studio로 넘어가지 않는다.

과금은 충전식이다. 발행 자체는 크레딧을 쓰지 않으므로 발행 실패 시 재시도는 무료다.

## 1단계 비범위

자체 화면(studio), 롱폼을 숏폼으로 쪼개기, 음악과 텍스트 매체, 창작 결정(openclaw 쪽).
